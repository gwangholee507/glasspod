# T19 Pod 상세 화면

- 우선순위: P0 · 단계 10 · 선행 작업: T18, T09 · 결정: D8
- 브랜치: `feat/t19-pod-detail`
- 작성: 2026-11-17

## 목표

분할 화면의 오른쪽 상세 자리(`/pods/:namespace/:name`)를 확정안(design.md 5.3, Figma '확정-2 상세')대로 만듭니다. 개발자가 한 Pod에 무슨 일이 있었는지 시간 순으로 보고, 지표를 같은 Deployment의 다른 Pod와 견주고, 지금 상태(snapshot)를 물어볼 수 있게 합니다.

- 머리줄: 상태 배지, Pod 이름, 조치 버튼 자리, 판단 문장 · Deployment · Pod IP · 나이
- '무슨 일이 있었나': SDK event, 쿠버네티스 이벤트, SDK 연결, 판단 변화, 재시작을 늦은 것부터. 재시작 원인 후보에 '후보 N'
- 지표 그래프 4개(uPlot): 이 Pod 선, 같은 Deployment의 다른 Pod 선, 재시작 표시. 기간 5·15·30분(기본 30분)
- snapshot: 처리 중인 요청, 상태 값, 프로세스
- 서버: 그래프용 시계열 API, 쿠버네티스 이벤트 보관(T11 결정 3에서 넘김)

## 결정 사항

1~4는 2026-11-17에 사용자가 정했습니다(착수 전에 보고한 질문 4개). 5~25는 이 작업의 기본값입니다. 26은 구현하며 확인한 것(아래 '구현하며 확인한 것')으로 더했습니다.

| 다시 받기 간격 | 상세와 시계열이 4,968~5,011ms 간격으로 다시 불림(브라우저의 resource timing) |
| `block`(20초) | 서버 시계열에 막히기 직전 점 1ms 뒤의 `null` 점과 23.8초 빈 곳이 들어감. 판단은 정상 → 준비 안 됨(readiness 2번 실패가 3주기보다 먼저) → 앱 멈춤 의심 → 정상, 쿠버네티스 `Unhealthy`(Readiness probe failed) 줄. 막힌 동안 snapshot은 504 `no-response` 문장. 루프 p99는 오르지 않음: 막힘이 풀린 뒤 한 번 잰 20초 지연이 그 주기의 표본 가운데 하나뿐이라 p99에 들지 않고 `runtime.event_loop.lag_max_ms`(20,004ms)에만 보임. 네 번째 그래프를 `lag_max_ms`로 고르면 보임 |
| `errors` 뒤 `crash` | '재시작' 판단, `Error (exit 1) → 컨테이너 재시작` 줄, 처리되지 않은 예외 `DemoCrashError` 줄에 '후보 1', `errors`의 `PaymentError` 줄 둘에 '후보 2'·'후보 3', 쿠버네티스 `Pulled`·`Created`·`Started`, SDK '연결 끊김 (코드 1006)'·'새 instance로 연결됨'. 그래프 4개에 재시작 점선 |
| `slow`(1500ms) | 요청 p99 그래프와 값이 1,004 ms로 오름(DB 시간 제한 1000ms) |
| counter | `app.orders.processed`를 고르면 '180/분'처럼 분당 값. API 값은 초당(약 3) |
| SDK 없는 `demo-load` | 그래프 자리 안내, snapshot 요청 없음(브라우저 요청 목록에 `/snapshot` 없음). 최근 30분에 Event가 없어 쿠버네티스 줄은 없었음 |
| 좁은 창 | 768px에서 세 칸이 쌓이고 그래프는 2열(354px), 390px에서 1열. 가로 스크롤 없음. 그래프 칸은 컨테이너 너비(`@xl`, 576px)로 열 수를 정함 |
| 마우스 값 | 그래프에 마우스를 올리면 칸 머리가 '11:41:28 13 MB'처럼 그 시각의 이 Pod 값으로 바뀜 |
| 브라우저 콘솔 | 앱의 오류 없음. 브라우저가 스스로 남긴 504(snapshot)와 404(없는 Pod)만 |
| 서버 로그 | `store stats`에 `kubeEvents=4 droppedKubeEvents=0` |

## snapshot 문장

| 오류 코드 | 문장 |
| --- | --- |
| `not-connected` | SDK가 연결되어 있지 않습니다. |
| `pod-not-found` | 서버가 이 Pod를 모릅니다. |
| `not-supported` | 이 SDK는 snapshot을 지원하지 않습니다. |
| `busy` | 이 Pod에 기다리는 snapshot 요청이 많습니다. 잠시 뒤에 다시 받습니다. |
| `no-response` | 앱이 5초 안에 답하지 않았습니다. 이벤트 루프가 막혔을 수 있습니다. |
| `disconnected` | 답을 기다리는 동안 SDK 연결이 끊겼습니다. |
| `sdk-error` | SDK가 오류로 답했습니다. |
| `invalid-response` | SDK의 답이 형식에 맞지 않습니다. |
| 그 밖 | 서버에 닿지 못했습니다 (`코드`). |

## 알려진 한계

- SDK가 붙지 않은 Pod는 목록 항목이 쿠버네티스 상태가 바뀔 때만 바뀌므로, 같은 Event의 횟수만 늘어나는 것은 그때까지 늦게 보입니다(결정 11).
- 시계열은 같은 Deployment의 지금 Pod만 그립니다. 바뀐 ReplicaSet(새 버전)의 Pod도 같은 Deployment라 함께 그립니다.
- 받은 시각을 X축으로 쓰므로, 다시 연결한 뒤 한꺼번에 받은 event와 달리 지표는 늦게 받은 그대로 놓입니다(SDK는 끊긴 동안의 metrics를 쌓지 않음, T08).

## 쓰는 법

서버(노트북 또는 클러스터 안 서버의 port-forward)와 웹 개발 서버를 띄운 뒤 목록에서 Pod를 고르거나 `http://localhost:5173/pods/glasspod-demo/<Pod 이름>`을 엽니다. 시계열만 볼 때는 다음처럼 부릅니다.

```bash
curl -s 'localhost:8080/api/pods/glasspod-demo/<Pod 이름>/series?metrics=runtime.heap.used_bytes,app.orders.processed'
```
