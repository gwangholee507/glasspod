# T11 Pod별 앱 상태 보관

- 우선순위: P0 · 단계 6 · 선행 작업: T05, T06 · 결정: D1
- 브랜치: `feat/t11-pod-store`
- 작성: 2026-11-14

## 목표

서버가 SDK에서 받은 metrics와 event를 버리지 않고 Pod별로 들고 있게 합니다(design.md 3장 '서버 데이터 보관', 5.2). T13 상태 판단, T14 조회 API, T19 상세 화면이 이것을 읽습니다.

- **지금 상태**: Pod마다 연결 여부, instanceId, 마지막 metrics를 받은 시각과 마지막 값, `seq`. 서버 메모리에 두고 바로 읽습니다(T13).
- **기록**: 지표 시계열, event, 연결 기록, 지워진 Pod의 마지막 요약. 저장소 어댑터(비동기)에 최근 30분을 둡니다. 1차 범위는 메모리 어댑터뿐입니다(DB는 T32).
- 받은 메시지에서 `seq` 빈틈(누락)과 counter 리셋을 알아냅니다.
- 확인은 단위 테스트와 서버 로그로 합니다. 조회 API는 T14에서 만듭니다.

## 결정 사항

1~15는 2026-11-14에 사용자가 추천안으로 정했습니다(착수 전에 보고한 질문 4개와 기본값). 16~22는 이 작업의 기본값입니다.

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | 지금 상태와 기록 | 나눔. 지금 상태는 `AppStates`(`pods.ts`)가 메모리에 들고 동기로 읽음. 기록은 저장소 어댑터(`store/`)가 비동기로 들고 있음. 조치 기록(T21)도 저장소 | 사용자 결정. DB 어댑터(T32)로 바꿔도 상태 판단이 DB를 기다리지 않음. 지금 상태는 서버가 다시 떠도 SDK가 다시 붙으며 곧 채워짐 |
| 2 | event 상한 | 30분 + Pod당 500건. 넘으면 오래된 것부터 버리고 버린 수를 셈 | 사용자 결정. event 하나는 최대 약 17KB(T06 길이 상한)이고 한도가 분당 120건이라 30분이면 Pod 하나에 최악 3,600건·약 60MB. 서버 메모리 한도는 256Mi. 500건이면 최악 Pod당 약 8.5MB이고 SDK가 끊긴 동안 들고 있는 수와 같음 |

| 4 | 확인 방법 | 보관 규칙은 가짜 시계로 단위 테스트. 실제 실행은 로그(새 instance, counter 리셋, 지워진 Pod, 5분마다 보관 현황) | 사용자 결정. 조회 API를 지금 만들면 T14와 응답 형식을 두 번 정하게 됨 |
| 5 | 어댑터 고르기 | 환경변수 `GLASSPOD_STORE`(기본 `memory`). 지금 받는 값은 `memory`뿐이고 다른 값이면 시작 실패 | 사용자 결정. D1 '변수 이름은 T11 지침서에서'. `postgres`는 T32에서 더함 |
| 6 | 보관 시간 | 30분(`RETENTION_MS`). 코드 상수로 두고 환경변수로 받지 않음 | 사용자 결정. D1이 정한 값. DB의 보관 기간은 아직 정하지 않은 확장 작업의 세부(T32) |
| 7 | 중복과 누락 | 중복 제거는 하지 않음. instance마다 `seq` 빈틈으로 빠진 수를 세고 빈틈마다 경고 한 줄. `seq`가 거꾸로 가거나 같으면 경고만 하고 그대로 기록 | 사용자 결정. T08부터 SDK는 같은 메시지를 다시 보내지 않아 중복이 없음(design.md 7.4 '전달 보장'). `hello`·`response`도 `seq`를 쓰므로 함께 봄 |
| 8 | counter 리셋 | 같은 Pod의 앞 점과 비교해 값이 줄었거나 instanceId가 바뀌었으면 리셋. 리셋이면 그 구간 증가량은 지금 값(0부터 셈). 앞 점이 없으면(서버가 처음 받은 값) 증가량 없음. 누적값과 증가량을 함께 기록 | 사용자 결정. design.md 7.3 'counter는 누적값'. T19가 초당 값을 그릴 수 있게 함 |
| 9 | 시각과 instance | 기록마다 SDK의 `ts`, 서버가 받은 시각(`receivedAt`), instanceId를 붙임. 30분은 받은 시각으로 셈. event는 `ts` 순서로 돌려줌 | 사용자 결정. 다시 연결한 뒤 늦게 온 event(T08)가 받자마자 지워지지 않게 함. instanceId는 T13이 재시작 직전 event를 원인 후보로 찾는 데 씀(design.md 7.5) |
| 10 | 지워진 Pod | watch가 Pod 삭제를 받으면 그 마지막 요약(종료 이유 포함)을 저장소에 넣고 30분 뒤 지움 | 사용자 결정. T12에서 넘김: `ClusterState`는 지워진 Pod를 바로 뺌 |
| 11 | 지표 이름 상한 | Pod당 200개. 넘는 새 이름의 값은 버리고 Pod마다 처음 한 번 경고 | 사용자 결정. Node SDK는 118개(`app.*` 100 + 18)가 상한이지만 다른 SDK나 잘못된 SDK에 대비 |
| 12 | 로그 | SDK 메시지마다 남기던 `message received`(T03)를 없앰. 새 instance, `seq` 빈틈, counter 리셋, 지표 이름 상한, 기록 버림, 기록 만료, 보관 현황(5분마다)만 남김 | 사용자 결정. T16에서 넘김: Pod 3개면 분당 약 36줄 |

### 기록 형식

`store/store.ts`의 타입입니다. 저장소는 받은 기록을 고치지 않고, 돌려준 기록도 부르는 쪽이 고치지 않습니다.

| 기록 | 필드 | 정리 기준 |
| --- | --- | --- |
| 지표(`MetricsRecord`) | `pod`, `instanceId`, `seq`, `ts`(SDK가 보낸 시각), `receivedAt`, `values`(`name`, `kind`, `value`, counter만 `increase`·`reset`) | `receivedAt` |
| event(`EventRecord`) | `pod`, `instanceId`, `seq`, `ts`(일어난 시각), `receivedAt`, `level`, `name`, `message`, `count`, `data` | `receivedAt` |
| 연결(`ConnectionRecord`) | `pod`, `instanceId`, `change`(`connected`·`disconnected`), `at`(서버 시각), connected만 `newInstance`(직전 instance와 다르면 true, 같으면 false, 처음 보는 Pod면 없음)·`sdk`·`app`, disconnected만 `code` | `at` |
| 지워진 Pod(`DeletedPodRecord`) | `pod`(T12의 Pod 요약), `deletedAt` | `deletedAt` |

### 지금 상태

`pods.ts`의 `AppState`입니다. T13이 읽습니다.

| 필드 | 뜻 |
| --- | --- |
| `pod`, `instanceId`, `sdk`, `app` | 마지막으로 받아들인 `hello` |
| `connected`, `connectedAt`, `disconnectedAt` | 그 연결이 열려 있는지와 시각(서버 시계) |
| `lastMessageAt`, `lastMetricsAt` | 그 연결에서 마지막으로 메시지·metrics를 받은 시각. '3주기째 없음'(design.md 7.5)에 씀 |
| `lastSeq`, `missed` | 그 instance의 마지막 `seq`와 빈틈으로 빠진 메시지 수 |
| `values` | 이름마다 마지막 값(`kind`, `value`, `ts`, `receivedAt`). instance가 바뀌면 비움 |

### 메모리 어림

데모 앱 Pod 하나는 metrics 한 건에 값 22개(`runtime.*` 11, `http.*` 7, `app.*` 4)를 5초마다 보내므로 30분이면 360건입니다. event는 같은 이벤트를 SDK가 10초씩 묶으므로 고장이 없으면 거의 없습니다. 실제 크기는 완료 기준의 보관 현황(`heapUsedMb`)으로 봅니다.

## 범위

### 포함

- 서버 설정: `GLASSPOD_STORE`
- 저장소 인터페이스와 기록 타입(`store/store.ts`), 메모리 어댑터(`store/memory.ts`)
- 지금 상태와 기록 만들기(`pods.ts`): `seq` 빈틈, counter 증가량·리셋, 이름 상한, 정리, 보관 현황 로그
- 연결: SDK 메시지(`agent.ts`), Pod 삭제(`watch.ts`), 시작·정리 타이머·종료(`index.ts`)
- 단위 테스트

### 제외

- 상태 판단(T13). 이 작업은 판단에 쓸 값을 들고 있기만 함
- 조회 API와 SSE(T14), 화면(T18·T19)
- 쿠버네티스 이벤트 보관(T19, 결정 3)
- 조치 기록(T21, 결정 13)
- PostgreSQL 어댑터(T32)
- SDK 신원 확인(T25). 지금은 `hello`의 Pod 이름을 그대로 믿으므로, 아무 이름으로 붙는 SDK가 Pod 수를 늘릴 수 있음
- SDK·프로토콜 변경. 이 작업은 서버만 고침

## 만들 파일

```text
apps/server/src/
├─ store/
│  ├─ store.ts          # 저장소 인터페이스, 기록 타입, GLASSPOD_STORE 값, 보관 시간
│  ├─ memory.ts         # 메모리 어댑터(Pod별 기록, 상한, 정리)
│  └─ memory.test.ts
├─ pods.ts              # 지금 상태(AppStates)와 기록 만들기
├─ pods.test.ts
├─ pod-key.ts           # Pod를 Map 키·로그 값으로 바꾸기(agents.ts에서 옮김)
├─ agents.ts            # (고침) podKey를 pod-key.ts에서 가져옴
├─ agent.ts             # (고침) 연결·메시지·끊김을 AppStates에 넘김, message received 로그 없앰
├─ watch.ts             # (고침) Pod 삭제를 알림(onPodDeleted)
├─ cluster.ts           # (고침) 주석
├─ config.ts            # (고침) GLASSPOD_STORE
└─ index.ts             # (고침) 저장소와 AppStates 만들기, 정리·보관 현황 타이머, 종료
```

```text
2026-11-14T09:31:00.000Z INFO  pod history expired pod=glasspod-demo/demo-app-5f7c9-abcde
```

- `counter reset`은 metrics 한 건마다 한 줄이고 `names`는 이름 순서입니다. instance가 바뀐 것은 INFO, 같은 instance에서 값이 준 것은 WARN입니다.
- `records dropped`는 Pod마다 기록 종류별로 처음 한 번입니다. 버린 수는 `store stats`에 나옵니다.
- `pods`는 저장소에 기록이 있는 Pod 수, `apps`는 지금 상태를 들고 있는 Pod 수, `connected`는 그 가운데 연결이 열린 수입니다.

| 데모 앱 Pod 하나에 `crash` | `instance changed`와 `counter reset cause=new-instance` 한 줄(그 Pod의 counter 이름). 다른 Pod는 리셋 없음 |
| 5분 뒤 | `store stats`: `pods=3 apps=3 connected=3`, `metrics`가 약 180(3 × 60), `events`가 `crash`의 event만큼, `dropped*=0` |
| 데모 앱 Pod 삭제(`kubectl delete pod`, 또는 `set env`·`kubectl apply`로 다시 배포) | 지운 Pod마다 `pod deleted`, `store stats`의 `deletedPods`가 지운 수, 대신할 Pod의 `hello accepted` |
| 삭제 30분 뒤 | 지운 Pod마다 `pod history expired` 한 줄(지운 시각 + 30분 뒤 첫 정리) |
| SIGTERM | 오류 로그 없이 끝남 |
| 데모 앱을 클러스터 안 서버로 되돌리고 서버 이미지를 다시 만들어 `rollout restart` | SDK 3개가 클러스터 안 서버에 붙음. 서버 로그에 `message received` 없음. 5분 뒤 `store stats`가 위와 같은 모양, `rssMb`가 메모리 한도(256Mi)보다 한참 작음 |

`seq` 빈틈과 역순, 같은 instance에서 counter가 주는 경우, 상한은 실제 SDK로 만들기 어려워 단위 테스트로만 확인합니다.
