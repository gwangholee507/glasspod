# T10 데모 앱과 고장 스위치

- 우선순위: P0 · 단계 6 · 선행 작업: T05, T06
- 브랜치: `feat/t10-demo-app`
- 작성: 2026-11-13

## 목표

Glasspod를 확인할 때 쓸, 일부러 고장 낼 수 있는 앱을 만듭니다(design.md 2장 핵심 기능 5, 6장 대표 시나리오).

- 평소에는 주문 앱처럼 동작합니다. 주문 조회와 주문 접수 API가 있고, 접수한 주문은 큐에 넣었다가 작업자가 가짜 DB로 처리합니다. SDK로 HTTP 지표, 큐 길이, 상태 값, 예외를 보냅니다.
- 관리 포트의 HTTP API로 고장 다섯 가지를 켜고 끕니다: 느려짐, 이벤트 루프 막힘, 예외 폭주, 크래시, 메모리 증가.
- 부하 스크립트가 앱에 계속 요청을 보내 지표가 실제 요청으로 쌓이게 합니다.
- 클러스터 배포(이미지, 매니페스트, Downward API)는 T15에서 합니다. 이번에는 노트북에서 서버와 함께 띄워 확인합니다.

| 9 | 작업자 | 큐에서 주문을 꺼내 동시에 2건까지 가짜 DB에 씀. 실패한 주문은 다시 넣지 않고 `app.orders.failed`로 세고 `glasspod.exception(error, { job: "process-order" })`로 보고 | 평소 처리량(초당 약 100건)이 부하(기본 초당 5건)보다 훨씬 커서 큐가 비어 있음. 느려지면 처리량이 줄어 큐가 쌓임 |
| 10 | SDK 사용 | `glasspod.start({ app: { name: "demo-app", version: "0.0.0" } })`, `express()`, `expressErrors()`, gauge `app.queue.length`, counter `app.orders.created`·`app.orders.processed`·`app.orders.failed`, state `app.mode`(`ready` → 종료 때 `draining`) | design.md 8장의 쓰는 모습을 모두 씀. 버전은 `package.json`과 같게 둠 |
| 11 | 라우트 오류 응답 | `expressErrors()` 뒤에 앱의 오류 처리기를 두어 `500 { error }`로 답하고 stack을 출력하지 않음 | Express 기본 오류 처리기는 예외마다 stack을 출력해 느려짐 동안 출력이 넘침. 예외는 SDK가 보냄 |
| 12 | 고장을 SDK로 알리는지 | 알리지 않음. 앱 표준 출력 로그에만 남김 | Glasspod가 고장 이름이 아니라 실제 신호(지표, 예외, 연결)로 판단하는지 확인하려는 것 |
| 13 | 스위치 API 모양 | 값은 쿼리 문자열(`?delayMs=1500`). 이어지는 고장(느려짐, 예외 폭주, 메모리 증가)은 `POST`로 켜고 다시 `POST`하면 값을 바꾸며 `DELETE`로 끔, 응답은 200과 지금 고장 상태. 한 번 일어나는 고장(막힘, 크래시)은 202로 먼저 답한 뒤 일으킴. 잘못된 값은 400 `{ error: "invalid-parameter", detail }`. `GET /faults`는 지금 상태, `DELETE /faults`는 모두 끔 | curl 한 줄로 켜고 끔. 막힘과 크래시는 일으키면 답할 수 없어 먼저 답함 |
| 14 | 느려짐 `slow` | 가짜 DB 지연에 `delayMs`(기본 1500, 1~60000)를 더함. 기본값은 시간 제한을 넘어 모든 DB 호출이 timeout. 1000 미만이면 실패 없이 느려지기만 함 | 기본값으로 6장 시나리오(큐가 쌓이고 마지막 예외가 DB timeout)가 바로 나옴 |
| 15 | 메모리 증가 `leak` | 100ms마다 double 65,536칸 배열(힙 0.5MB)을 붙잡아 `mbPerSec`(기본 10, 1~1000)씩 힙을 늘림. 끄면 놓아서 GC가 거둠. 상한 없음 | design.md 7.3 'OOMKilled 직전 metrics에 힙이 늘어나는 모습'. 끝까지 두면 V8 힙 한도에서 죽음(아래 '사전 확인'). 컨테이너의 OOMKilled는 메모리 한도와 힙 한도를 T15·T27에서 맞춰 확인함 |
| 16 | 예외 폭주 `errors` | 앱 안 타이머로 초당 `perSecond`(기본 50, 1~1000)번 `PaymentError`를 만들어 `glasspod.exception(error, { job: "payment-sync" })`로 보고. 메시지는 `distinct`(기본 1, 1~100)가지를 돌아가며 씀 | 부하와 상관없이 일정하게 쏟아짐. `distinct=1`이면 SDK가 묶어 `count`로 보내고(T06), 크게 하면 1분 한도(기본 120)에 닿음. 100이면 다른 예외와 합쳐 SDK가 묶는 서로 다른 이벤트 상한(100, T06)에도 닿아 SDK 경고가 나옴 |
| 17 | 이벤트 루프 막힘 `block` | 202로 답한 뒤 동기 반복문으로 `seconds`(기본 20, 1~300)초 막음. 막힌 동안 관리 API도 답하지 않음 | 기본값은 metrics 기본 주기 5초의 3주기(15초)보다 길어 '앱 멈춤 의심'(design.md 7.5)과 snapshot 504가 나옴 |
| 18 | 크래시 `crash` | 202로 답하고 100ms 뒤 타이머에서 처리되지 않은 예외(`kind=exception`, 기본) 또는 처리되지 않은 Promise 거부(`kind=rejection`). Node 기본대로 오류를 출력하고 종료 코드 1로 끝남 | SDK가 `fatal: true` exception event를 보내고 끝나는지 확인함(T06). 종료 동작은 SDK가 없을 때와 같음 |
| 19 | 부하 요청 | 요청의 반은 `GET /orders/{1~1000}`, 반은 `POST /orders`. 요청마다 새 연결(`agent: false`, `Connection: close`). 기다리는 요청이 200개면 보내지 않고 `skipped`로 셈. 요청마다 10초 시간 제한. 10초마다 요약 한 줄 | keep-alive 연결은 Service 뒤의 한 Pod에 붙어 있어, 격리(T23)한 뒤에도 그 연결로 트래픽이 계속 감. 상한은 앱이 막혔을 때 부하 스크립트가 끝없이 쌓지 않게 함 |
| 20 | 종료 | `SIGTERM`·`SIGINT`를 받으면 `app.mode`를 `draining`으로 하고, 고장을 모두 끄고, 작업자를 멈추고, 두 서버를 닫은 뒤 `glasspod.stop()`. 이벤트 루프가 비어 종료 코드 0으로 끝남. 10초 안에 끝나지 않으면 `process.exit(1)`. 두 번째 신호는 Node 기본 동작 | 내장 WebSocket이 이벤트 루프를 붙잡으므로 이벤트 루프가 비기를 기다려 끝나는 앱은 `stop()`을 불러야 함(design.md 5.1). 그 모습을 데모 앱이 보여 줌 |
| 21 | 로그 | 표준 출력 한 줄(시각, 수준, 내용, key=value, 서버와 같은 모양). 시작, 고장 켜고 끔, 종료만 남기고 요청마다는 남기지 않음 | 부하 동안 출력이 넘치지 않게 함 |
| 22 | 실행과 테스트 | `npm run demo`(앱), `npm run demo:load`(부하). 둘 다 `node --conditions=@glasspod/source --import tsx`로 소스를 바로 실행하고 watch는 쓰지 않음. 단위 테스트는 설정 읽기, 스위치 값 검사, 초당 횟수 나누기만 | 크래시 스위치로 끝나는 모습(종료 코드)을 그대로 보려면 watch가 없어야 함. 데모 앱은 핵심 로직이 아니어서 테스트를 늘리지 않음 |

### 고장 스위치

관리 포트(`http://127.0.0.1:3001`)의 API입니다.

| 요청 | 고장 | 값(기본, 범위) | 응답 |
| --- | --- | --- | --- |
| `POST /faults/slow` | 느려짐 | `delayMs`(1500, 1~60000) | 200, 지금 상태 |
| `DELETE /faults/slow` | 느려짐 끔 | | 200, 지금 상태 |
| `POST /faults/errors` | 예외 폭주 | `perSecond`(50, 1~1000), `distinct`(1, 1~100) | 200, 지금 상태 |
| `DELETE /faults/errors` | 예외 폭주 끔 | | 200, 지금 상태 |
| `POST /faults/leak` | 메모리 증가 | `mbPerSec`(10, 1~1000) | 200, 지금 상태 |
| `DELETE /faults/leak` | 메모리 증가 끔(붙잡은 메모리를 놓음) | | 200, 지금 상태 |
| `POST /faults/block` | 이벤트 루프 막힘 | `seconds`(20, 1~300) | 202 뒤 막힘 |
| `POST /faults/crash` | 크래시 | `kind`(`exception`, `exception`·`rejection`) | 202 뒤 종료 |
| `GET /faults` | 지금 상태 | | 200 |
| `DELETE /faults` | 이어지는 고장 모두 끔 | | 200, 지금 상태 |

### 사전 확인

Node 22.22.0, macOS(메모리 16GB)에서 2026-11-13에 확인했습니다.

| 확인 | 결과 |
| --- | --- |
| `new Array(65536).fill(1.5)` 200개를 붙잡음 | `heapUsed`가 100.0MB 늘고 `external`·`arrayBuffers`는 그대로. 하나에 0.5MB, 힙에 잡힘. 10MB(20개) 만드는 데 약 5ms |
| 힙 한도 | 기본 4144MB(이 노트북). `--max-old-space-size=32`로 계속 늘리면 `JavaScript heap out of memory`와 종료 코드 134(SIGABRT). 컨테이너에서는 이것이 OOMKilled보다 먼저 올 수 있어 T15·T27에서 한도를 맞춤 |
| 처리되지 않은 예외, Promise 거부 | 둘 다 종료 코드 1 |
| `http.get({ agent: false })` | 요청 헤더 `connection: close`, 응답도 `close` |

## 범위

### 포함

- `examples/demo-app`: 주문 API, 큐와 작업자, 가짜 DB, 고장 스위치와 관리 API, 종료 처리, 부하 스크립트, 단위 테스트
- 루트 `package.json`의 `demo`, `demo:load` 스크립트. 데모 앱의 `express` 의존성(서버와 같은 5.3.0)

### 제외

- 컨테이너 이미지, 쿠버네티스 매니페스트, Downward API, 부하 Deployment(T15)
- 관리 포트가 `kubectl port-forward`로 닿는지, 컨테이너에서 OOMKilled가 나는지(T15, T27)
- 서버의 상태 판단(T13)과 화면(T18, T19). 이번에는 서버가 받은 메시지와 snapshot으로 확인함
- SDK와 서버 코드 변경. 고칠 것이 보이면 멈추고 알림

## 쓰는 법

```bash
npm run dev:server
```

```bash
GLASSPOD_SERVER=ws://localhost:8080/agent POD_NAME=demo-1 POD_NAMESPACE=glasspod-demo npm run demo
```

```bash
npm run demo:load
```

고장을 켜고 끕니다.

```bash
curl -s -X POST 'localhost:3001/faults/slow?delayMs=1500'
```

```json
{ "slow": { "delayMs": 1500 }, "errors": null, "leak": null }
```

```bash
curl -s -X DELETE localhost:3001/faults/slow
```

```bash
curl -s -X POST 'localhost:3001/faults/block?seconds=20'
```

```json
{ "accepted": "block", "seconds": 20 }
```

```bash
curl -s -X POST 'localhost:3001/faults/slow?delayMs=abc'
```

```json
{ "error": "invalid-parameter", "detail": "delayMs must be an integer from 1 to 60000 (got \"abc\")" }
```

고장마다 Glasspod에 보이는 것입니다.

| 고장 | 보이는 것 |
| --- | --- |
| 느려짐(기본값) | `http.requests.duration_p99_ms`가 약 1000, `http.requests.errors_total`이 늘어남, `app.queue.length`가 초당 약 3씩 늘어남, exception event `TimeoutError: DB timeout after 1000ms`. 주문 접수(`POST`)는 큐에 넣기만 해 바로 답하므로 p50은 거의 그대로임. 라우트와 작업자에서 난 예외는 같은 이벤트라 SDK가 묶고, `data`에는 먼저 난 쪽의 `route: GET /orders/:id` 또는 `job: process-order`가 들어감 |
| 막힘 | metrics가 막힌 동안 오지 않고, 풀린 뒤 첫 metrics의 `runtime.event_loop.lag_max_ms`가 막힌 시간만큼. 막힌 동안 snapshot은 504 |
| 예외 폭주 | exception event `PaymentError`가 첫 건 바로, 그 뒤 10초마다 `count`로. `distinct`가 크면 1분에 `maxEventsPerMinute`개까지 |
| 메모리 증가 | `runtime.heap.used_bytes`가 초당 `mbPerSec`MB씩 늘어남 |
| 크래시 | exception event(`fatal: true`, `origin`) 뒤 연결이 끊기고 프로세스가 종료 코드 1로 끝남 |

- 막힘이 부하 스크립트의 요청 시간 제한(10초)보다 길면, 막힌 동안 보낸 요청은 부하 스크립트에서 `failed`로 셉니다.
- 1분 한도에 닿아 있을 때 종료하면, 마지막 state event(`draining`)는 SDK가 묶음에서 세다가 `stop()`에서 버려 서버에 가지 않습니다(T06 결정 11).

## 로그 형식

데모 앱의 표준 출력입니다.

```text
2026-11-13T08:00:00.000Z INFO  demo-app started port=3000 admin=127.0.0.1:3001
2026-11-13T08:00:10.000Z INFO  fault on name=slow delayMs=1500
2026-11-13T08:00:40.000Z INFO  fault off name=slow
2026-11-13T08:01:00.000Z INFO  fault on name=block seconds=20
2026-11-13T08:01:20.000Z INFO  fault off name=block blockedMs=20000
2026-11-13T08:02:00.000Z INFO  fault on name=crash kind=exception
2026-11-13T08:03:00.000Z INFO  shutting down signal=SIGTERM
2026-11-13T08:03:00.050Z INFO  demo-app stopped
```

부하 스크립트의 표준 출력입니다. 숫자는 지난 10초 동안의 것이고 `inFlight`는 지금 기다리는 요청 수입니다.

```text
2026-11-13T08:00:00.000Z INFO  load started target=http://localhost:3000 rps=10
2026-11-13T08:00:10.000Z INFO  load sent=100 2xx=100 4xx=0 5xx=0 failed=0 skipped=0 inFlight=0
```

## 도구 버전

새로 내려받는 패키지가 없습니다. 데모 앱의 `dependencies`에 서버가 이미 쓰는 `express` 5.3.0을 적습니다(루트 `node_modules`에 있음). 타입은 루트의 `@types/express` 5.0.6을 씁니다.

## 완료 기준

실제 동작은 저장소에 넣지 않는 확인 스크립트로 확인했습니다(68개 항목). 스크립트는 `ws`로 만든 가짜 서버(받은 메시지를 모두 기록하고 `parseSdkMessage`로 검증, metrics 주기 1초, 실제 서버처럼 15초마다 heartbeat)에 데모 앱을 붙이고, 부하 스크립트와 관리 API로 고장을 일으켜 받은 메시지를 봅니다. 끝으로 실제 서버(`npm run dev:server`)와 위 '쓰는 법'의 명령으로 직접 확인했습니다.

| 확인 | 기대 결과 |
| --- | --- |
| `npm run typecheck` | exit 0 |
| `npm test` | 모든 테스트 통과. 설정 읽기, 스위치 값 검사, 초당 횟수 나누기 테스트 포함 |
| `npm run format:check` | `All matched files use Prettier code style!` |
| 시작 | `hello`의 `app`이 `{ name: "demo-app", version: "0.0.0" }`, `capabilities`가 `["snapshot"]`. state event `app.mode` `ready`. 로그 `demo-app started` |
| 평소 부하 | metrics에 `http.requests.total`이 늘고 `errors_total`은 0, `app.queue.length`는 0 근처, `app.orders.processed`가 늚. `/healthz`는 세지 않음 |
| 관리 포트 | `127.0.0.1`로는 닿고, 노트북의 다른 주소로는 닿지 않음 |
| 느려짐(기본값) | GET이 약 1초 뒤 500, exception event `TimeoutError`(`data`에 `route` 또는 `job`), `duration_p99_ms`가 약 1000, `app.queue.length`가 늘어남. 끄면 큐가 비고 오류가 멈춤 |
| 느려짐(`delayMs=300`) | 예외 없이 `duration_p99_ms`가 300 이상 |
| 막힘(`seconds=5`) | 202 뒤 metrics 사이가 약 5초 벌어지고, 풀린 뒤 `lag_max_ms`가 약 5000 |
| 예외 폭주(`distinct=1`) | `PaymentError` 첫 건 `count: 1`, 약 10초 뒤 묶음 `count`가 약 `perSecond × 10` |
| 예외 폭주(`distinct=100`) | 1분 동안 받은 event가 가짜 서버의 `maxEventsPerMinute`를 넘지 않음 |
| 메모리 증가(`mbPerSec=50`) | `runtime.heap.used_bytes`가 초당 약 50MB씩 늘어남. 끄면 더 늘지 않음 |
| 메모리 증가로 죽음(`--max-old-space-size=64`) | `JavaScript heap out of memory`와 SIGABRT(셸에서는 종료 코드 134). 죽기 전 metrics에 힙이 늘어나는 모습 |
| 크래시(`kind=exception`, `kind=rejection`) | 종료 코드 1, stderr에 Node 기본 오류 출력, exception event `fatal: true`와 `origin`(`uncaughtException`, `unhandledRejection`) |
| 잘못된 값, `GET /faults`, `DELETE /faults` | 400 `invalid-parameter`, 지금 상태, 모두 꺼짐 |
| `SIGTERM` | state event `app.mode` `draining`(1분 한도에 여유가 있을 때), 연결이 종료 코드 1000으로 닫히고 프로세스가 종료 코드 0으로 끝남. 서버가 없어 다시 붙는 중에도 같음 |
| 잘못된 설정(`PORT=abc`) | 시작하지 않고 종료 코드 1과 오류 한 줄 `ERROR start failed detail=...` |
| SDK 환경변수 없음 | 앱은 동작하고 SDK 경고 한 줄 |
| 부하 스크립트 | 요청이 `Connection: close`, GET과 POST가 반씩. 10초마다 요약 한 줄. 앱이 없으면 `failed`로 셈. 잘못된 설정(`LOAD_RPS=0`)은 종료 코드 1 |
| 실제 서버와 함께 | 서버 로그 `hello accepted ... pod=glasspod-demo/demo-1`. snapshot API가 200이고 `state`에 `app.mode`, 느려짐 동안 `inFlight`에 `GET /orders/:id`, 막힘 동안 약 5초에 504와 풀린 뒤 `response ignored`. 서버 로그에 `message ignored`와 ERROR 없음 |
| 위 모든 경우 | 크래시 스위치 말고는 데모 앱에 처리되지 않은 예외 없음(표준 오류에는 SDK 경고만) |
