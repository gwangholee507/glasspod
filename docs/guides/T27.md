# T27 상태 판단 시나리오 점검

- 우선순위: P1 · 단계 12 · 선행 작업: T26 · 결정: 없음(아래 결정 1~2는 착수 전 사용자 결정)
- 브랜치: `chore/t27-status-scenarios`
- 작성: 2026-11-28

## 목표

데모 앱의 고장 스위치로 이벤트 루프 막힘, 예외 폭주, 크래시, OOM을 로컬 클러스터에서 일으키고, 클러스터 안 서버의 판단(design.md 7.5)과 지표 비교(7.6), 화면이 맞게 보이는지 확인합니다. T13은 같은 판단을 노트북 서버의 로그로 확인했고, 이번에는 클러스터 안 서버와 화면으로 봅니다.

앞 작업에서 넘긴 것:

- T06·T15: 클러스터 안에서 처리되지 않은 예외 event가 서버에 도착하고 그 내용(`fatal`, `origin`)이 맞는지
- T15: 서버의 OOM 판단(`OOMKilled`, 137)
- T08: 서버가 다시 시작되는 동안 SDK가 event를 보관했다가 원래 시각으로 보내는지
- T34·T26: 예외 폭주는 판단이 아니라 예외/분 강조. 부하는 초당 20건

## 결정 사항

1~2는 2026-11-28에 사용자가 정했습니다(질문 2개, 모두 추천안). 3~15는 이 작업의 기본값입니다.

| 하는 일 | 기대 결과 |
| --- | --- |
| B에 `crash`(예외) | 종료 코드 1, 컨테이너 재시작. 판단이 (잠깐 `disconnected` →) `restarted`(근거 `Error`, exit 1). 원인 후보 1번이 `DemoCrashError: demo crash: uncaught exception`(`fatal`, `origin=uncaughtException`, 이전 instance). 상세 머리줄 '재시작', '무슨 일이 있었나'에 'Error (exit 1) → 컨테이너 재시작'과 '후보 1' |

| 하는 일 | 기대 결과 |
| --- | --- |

| 하는 일 | 기대 결과 |

### 끝에

- 고장을 모두 끔(`DELETE /faults`), 데모 앱 3개가 재시작 30분 창 밖에서는 '정상'
- 서버 로그에 예상한 `pod status`·`pod outlier`·`restart cause`·`kube event` 말고 경고·오류 없음, 브라우저 콘솔에 앱 오류 없음
- `npm run typecheck`, `npm test`, `npm run format:check` 통과

### 확인 중 고친 것

결정 2의 작은 문제입니다. 서버·SDK는 바꾸지 않았습니다.

- snapshot이 실패하면 시각이 없어, 지난 실패(504)가 지금 일처럼 보였음(snapshot은 열 때와 '다시 받기' 때만 물음) → 실패에도 답을 받은 시각을 제목 옆에 붙임(`SnapshotPanel.tsx`). 고친 뒤 '12:22:50' 확인
- 처리되지 않은 Promise 거부도 '처리되지 않은 예외'로 나옴 → `origin`이 `unhandledRejection`이면 '처리되지 않은 Promise 거부'(`detailView.ts`의 `eventRow`). 고친 뒤 B를 한 번 더 크래시해 확인(세 번째라 `pod-failing` 약 25초)
- 새 Pod가 '시작 중 → 준비 안 됨 → 정상'이면 마지막 줄이 '다시 정상입니다'(T26은 앞 판단이 시작 중·SDK 없음일 때만 고침) → 판단 변화 목록에서 시작 중을 본 뒤 정상인 적이 없던 Pod의 첫 정상을 고르는 `firstOkChanges`(`podText.ts`)로 '이상 신호가 없습니다'. 한눈에 보기 타임라인(`podView.ts`의 `OverviewEntry.firstOk`)과 상세 '무슨 일이 있었나'에 씀. 시작을 30분 창 밖에서 한 Pod는 그대로 '다시'. 고친 뒤 replica 4로 띄운 Pod에서 확인

### 넘길 것(고치지 않음)

- 시계 점프(사전 확인, 결정 2): 서버가 멈춤 판단의 침묵 시간을 벽시계(`Date.now()`)로 잼. 노드 시계가 앞으로 뛰면 모든 Pod가 다음 metrics까지 `stalled`가 되고 판단 변화가 남음. 단조 시계(`performance.now()`)로 재도록 `pods.ts`·`status.ts`를 바꾸는 후속 작업으로 제안. 같은 벽시계를 쓰는 지표 비교의 '3주기보다 오래된 값'과 시계열 끊김도 함께 봐야 함
- OOM의 원인 후보: SIGKILL이라 SDK가 마지막 event를 보내지 못해, 시작 때의 `app.mode: ready`(info)가 '후보 1'로 나옴. 정해진 동작(T13 결정 9)이지만 OOMKilled에서는 힙 그래프를 가리키는 편이 나음. 원인 후보 고르기나 화면 문장을 바꿀지 정해야 함
- 예외 폭주를 끈 뒤 강조가 약 100초 남음: SDK가 1분 한도로 묶어 둔 것을 늦게 보내고, 서버는 받은 시각으로 60초를 셈. 정해진 동작(T06·T34)
- 서버를 다시 시작하면 원인 후보·판단 변화가 사라져, 쿠버네티스 쪽 재시작은 '재시작'이지만 후보가 없음. 메모리 저장소의 정해진 동작(D1), DB 어댑터(T32)에서 남음

## 쓰는 법

판단 시나리오를 다시 해 볼 때의 순서입니다. 쿠버네티스 명령 전에 context를 확인합니다(`docker-desktop`이어야 함).

```bash
kubectl config current-context
```

서버 API와 화면을 엽니다(README '로컬 클러스터에서 띄워 보기').

```bash
kubectl -n glasspod port-forward service/glasspod-server 8080:8080
```

```bash
npm run dev:web
```

`http://localhost:5173/?namespace=glasspod-demo`를 열고 데모 앱 Pod 하나의 관리 포트를 엽니다.

```bash
kubectl -n glasspod-demo port-forward pod/<Pod> 3001:3001
```

| 고장 | 명령 | 화면에서 볼 것 |
| --- | --- | --- |
| 이벤트 루프 막힘 | `curl -s -X POST localhost:3001/faults/block` | 15초 뒤 '앱 멈춤 의심' |
| 예외 폭주 | `curl -s -X POST 'localhost:3001/faults/errors?perSecond=50'` | 약 30초 안에 '다른 Pod보다 높음 · 예외 N/분'. 끌 때 `DELETE /faults/errors` |
| 크래시 | `curl -s -X POST localhost:3001/faults/crash` | '재시작', 원인 후보 1번이 처리되지 않은 예외 |
| CrashLoopBackOff | 크래시 뒤 SDK가 다시 붙으면 바로 `curl -s -X POST 'localhost:3001/faults/crash?kind=rejection'` | 잠깐 'Pod 이상'(CrashLoopBackOff) 뒤 '재시작' |
| OOM | `curl -s -X POST 'localhost:3001/faults/leak?mbPerSec=2'` | 힙이 다른 Pod보다 높음, 약 90초 뒤 'OOMKilled (exit 137)로 재시작' |

- 크래시·OOM으로 컨테이너가 다시 시작되면 관리 포트 port-forward가 끊길 수 있어 다시 엽니다.
- 재시작한 Pod는 30분 동안 '재시작'으로 남습니다.
