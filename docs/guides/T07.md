# T07 SDK HTTP 자동 수집

- 우선순위: P1 · 단계 6 · 선행 작업: T05
- 브랜치: `feat/t07-sdk-http`
- 작성: 2026-11-12

## 목표

Node.js SDK가 Express 앱의 HTTP 요청을 스스로 세고 응답 시간을 잽니다(design.md 5.1, 7.3). 앱은 두 줄만 넣습니다.

- `app.use(glasspod.express())`: 요청 수, 오류, 끊긴 요청, 응답 시간 p50·p99·max, 처리 중인 요청 수를 `http.*` 지표로 모아 metrics에 함께 보냅니다.
- `app.use(glasspod.expressErrors())`: 라우트에서 난 예외를 Express가 잡아 500으로 답할 때, 그 예외를 `route`와 함께 exception event로 보냅니다(T06에서 넘긴 일).

## 결정 사항

1~3은 2026-11-12에 사용자가 정했습니다. 4~16은 이 작업의 기본값입니다.

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | 수집 방법 | Express 미들웨어 `glasspod.express()` | 사용자 결정. TODO와 design.md 8장 그대로. 이 줄보다 앞에 둔 라우트는 세지 않으므로 등록 위치로 뺄 요청을 정함. Node `diagnostics_channel`로 모든 HTTP 서버를 자동으로 세는 방식은 probe와 다른 포트의 서버가 섞여 쓰지 않음 |
| 2 | 지표 세트 | 기본 7개(아래 'http 지표') | 사용자 결정. 막힘(처리 중 증가), 느려짐(p99), 서버 오류(5xx), 클라이언트 시간 초과(끊긴 요청)를 서로 구분함. v1 프로토콜에 라벨이 없어 경로별 지표는 없음 |
| 3 | Express가 잡은 예외 | 오류 미들웨어 `glasspod.expressErrors()`를 라우트 뒤에 둠. 예외를 `data.route`와 함께 exception event로 보내고 `next(err)`로 넘김 | 사용자 결정. 앱 동작은 그대로. `AsyncLocalStorage`는 Node 22에서 켜는 순간 앱 전체 Promise가 느려져(아래 '사전 확인') 쓰지 않음 |
| 4 | 요청의 끝 | 응답의 `close` 이벤트. 그때 `res.writableFinished`가 참이면 응답을 마친 요청, 거짓이면 끊긴 요청 | Node 22에서 `close`는 응답을 마쳤을 때도, 그 전에 연결이 끊겼을 때도 옴(사전 확인) |
| 5 | 응답 시간 | 미들웨어에 들어온 때부터 `close`까지. 끊긴 요청도 포함 | 클라이언트가 기다리다 포기한 가장 느린 요청이 p99에서 빠지지 않게 함 |
| 6 | 오류 | 응답을 마친 요청 가운데 상태 코드 500 이상. 4xx는 세지 않고, 끊긴 요청은 오류가 아니라 `aborted_total`로만 셈 | 4xx는 대개 클라이언트 잘못. 서버 오류와 시간 초과를 섞지 않음 |
| 7 | 응답 시간 계산 | `perf_hooks.createHistogram()`에 마이크로초로 기록하고, 주기마다 p50·p99·max를 보낸 뒤 비움. 그 주기에 끝난 요청이 없으면 세 값은 보내지 않음. 연결될 때(welcome) 비움 | runtime 이벤트 루프 지연(T05)과 같은 방식. 히스토그램은 크기가 정해져 있어 요청이 많아도 메모리가 늘지 않음 |
| 8 | 보내는 때 | `express()`를 한 번이라도 부른 뒤부터 metrics에 `http.*`를 넣음. counter는 연결과 상관없이 미들웨어를 만든 뒤 계속 셈 | HTTP를 쓰지 않는 앱(작업자 등)에는 쓸모없는 0 값을 보내지 않음. counter는 누적값이라 끊긴 동안에도 셈 |
| 9 | 같은 요청 | 미들웨어가 두 번 등록돼도(같은 `req`) 한 번만 셈 | 앱과 하위 Router에 함께 넣는 실수로 값이 두 배가 되지 않음 |
| 10 | 세지 않는 요청 | `app.use(glasspod.express())` 앞에 둔 라우트와 미들웨어에서 끝난 요청. 따로 제외 옵션은 두지 않음 | probe(`/healthz`)와 SSE처럼 오래 열린 요청은 앞에 두면 됨. WebSocket upgrade는 Express를 거치지 않아 세지 않음 |
| 11 | route 모양 | `METHOD 마운트경로+라우트경로`(예: `GET /orders/:id`). 경로가 배열이면 `,`로 잇고 정규식이면 문자열로 씀. 마운트된 Router의 `/` 라우트는 `GET /orders`. 200자 상한. 라우트가 정해지기 전(라우트 앞 미들웨어)에 난 예외는 `route` 없이 보냄 | 실제 경로(`/orders/7`)는 id 때문에 종류가 끝없이 늘고 개인 정보가 들어갈 수 있음 |
| 12 | 마운트 경로 알아내기 | `express()`가 `req.route`를 같은 값을 돌려주는 접근자(getter·setter)로 바꾸고, Express가 대입하는 순간의 `req.baseUrl`을 함께 기억함(`WeakMap`). 앱이 읽고 쓰는 `req.route` 값은 그대로 | Express는 오류 미들웨어를 부르기 전에 `req.baseUrl`을 되돌려, 오류 미들웨어에서는 `/orders`가 빠진 `/:id`만 보임(사전 확인). `express()` 없이 `expressErrors()`만 쓰면 마운트 경로 없이 보냄 |
| 13 | 오류 미들웨어가 보내지 않는 것 | 예외의 `status` 또는 `statusCode`가 400~499인 것(예: JSON 본문 오류 400, 404) | Express 기본 오류 처리기와 같은 기준. 클라이언트 잘못을 예외로 쌓지 않음. 같은 예외 묶기와 1분 한도는 T06 그대로 |
| 14 | 타입과 의존성 | SDK는 Express에 의존하지 않음. 미들웨어 타입은 `node:http`의 `IncomingMessage`, `ServerResponse`로 정의함. Express 5.3.0(서버가 쓰는 버전)으로 확인하고 Express 4는 확인하지 않음 | 앱이 고른 Express 버전을 따름 |
| 15 | 앱 보호 | `next()`는 SDK의 `try` 밖에서 정확히 한 번 부름. `close` 리스너와 setter는 `guard`로 감쌈. 두 공개 함수는 예외를 던지지 않음 | `next()`를 `try` 안에서 부르면 앱의 다음 미들웨어에서 난 예외를 SDK가 삼켜 Express 오류 처리가 바뀜 |
| 16 | 브랜치 | T06이 이미 `main`에 병합·push되어 있어 `main`에서 `feat/t07-sdk-http`를 만듦. 커밋하지 않은 T06 병합 기록(`docs/logs/2026-11-10.md`)을 함께 가져감 | T06 로그에 '다음 작업 브랜치에서 함께 커밋'으로 적음 |

### http 지표

| 이름 | 종류 | 뜻 |
| --- | --- | --- |
| `http.requests.total` | counter | 끝난 요청 수(응답을 마쳤거나 그 전에 끊김) |
| `http.requests.errors_total` | counter | 상태 코드 500 이상으로 응답을 마친 요청 수 |
| `http.requests.aborted_total` | counter | 응답을 마치기 전에 연결이 끊긴 요청 수 |
| `http.requests.duration_p50_ms` | gauge | 지난 주기에 끝난 요청의 응답 시간 중앙값 |
| `http.requests.duration_p99_ms` | gauge | 지난 주기에 끝난 요청의 응답 시간 p99 |
| `http.requests.duration_max_ms` | gauge | 지난 주기에 끝난 요청의 가장 긴 응답 시간 |
| `http.requests.in_flight` | gauge | 지금 처리 중인 요청 수 |

- 응답 시간은 마이크로초까지(소수 셋째 자리) 보냅니다.
- 끝나지 않는 요청은 응답 시간에 잡히지 않습니다. 이벤트 루프는 돌지만 요청이 걸려 있으면 `in_flight`가 늘어나는 것으로 보입니다.

### 사전 확인

Node 22.22.0, Express 5.3.0, macOS에서 2026-11-12에 확인했습니다.

| 확인 | 결과 |
| --- | --- |
| Express 오류 미들웨어에서 본 `req` | `/orders`에 마운트한 Router의 `/:id`에서 난 예외: `req.baseUrl`은 `""`, `req.route.path`는 `/:id`. 마운트 경로가 이미 빠져 있음 |
| `req.route` 접근자로 대입을 지켜봄 | Express가 대입할 때 `req.baseUrl`은 `/orders`라 `GET /orders/:id`를 얻음. 앱이 읽는 `req.route.path`는 그대로(`/:id/ok`) |
| 응답의 `close` | 정상 응답(200, 404, 500)은 `finish` 뒤에 `close`, `writableFinished` 참. 클라이언트가 100ms에 끊은 느린 요청은 `close`만 오고 `writableFinished` 거짓 |
| `AsyncLocalStorage` 비용 | 요청마다 `await` 20번인 함수 20만 번: 끔 약 237ms, `als.run()`으로 켬 약 790ms(약 3.3배). 켜면 그 안이 아닌 Promise도 함께 느려짐 |

## 범위

### 포함

- 요청 집계, 응답 시간 히스토그램, 미들웨어, 오류 미들웨어, route 모양(`http.ts`)과 단위 테스트
- metrics 전송(`metrics.ts`): `http.*` 값을 runtime 값과 app 값 사이에 넣음, 연결될 때 응답 시간을 비움
- 공개 API(`index.ts`): `glasspod.express()`, `glasspod.expressErrors()`

### 제외

- 경로별 지표. 프로토콜 v1에 라벨이 없음(design.md 11장 '히스토그램 지표'와 함께 나중에)
- 진행 중인 요청 목록(snapshot의 `inFlight`, T09). 이번에는 수만 셈
- 끊긴 동안 값 유지와 재연결 직후 전송(T08)
- Express가 아닌 프레임워크(Fastify, Koa 등)
- 요청 밖에서 부른 `glasspod.exception()`에 `route`를 자동으로 붙이는 일
- 데모 앱(T10). 실제 동작은 저장소에 넣지 않는 확인 스크립트로 확인함

## 쓰는 법

```ts
import express from "express";
import { glasspod } from "@glasspod/sdk";

glasspod.start({ app: { name: "orders", version: "1.4.2" } });

const app = express();
// probe처럼 세지 않을 요청은 미들웨어보다 앞에 둡니다.
app.get("/healthz", (req, res) => res.send("ok"));

// 이 뒤의 요청을 셉니다. 가능한 한 앞에 둡니다.
app.use(glasspod.express());

app.use("/orders", ordersRouter);

// 라우트 뒤, 앱의 오류 처리기 앞에 둡니다. 예외를 보낸 뒤 그대로 넘깁니다.
app.use(glasspod.expressErrors());
app.use((err, req, res, next) => {
  res.status(500).json({ error: "internal" });
});
```

`ordersRouter`의 `GET /:id`에서 예외가 나면 보내는 event의 예입니다.

```json
{ "type": "event", "seq": 31, "ts": 1793873733870, "level": "error", "name": "exception",
  "message": "DB timeout after 5000ms", "count": 1,
  "data": { "errorType": "TimeoutError", "stack": "TimeoutError: DB timeout ...", "route": "GET /orders/:id" } }
```

## 도구 버전

새로 설치하는 패키지가 없습니다. `node:http` 타입과 `node:perf_hooks`의 `createHistogram()`은 Node 22.22.0 내장입니다. 확인 스크립트는 서버가 이미 쓰는 Express 5.3.0을 루트 `node_modules`에서 불러옵니다(SDK의 의존성에는 넣지 않음).

## 완료 기준

실제 동작은 저장소에 넣지 않는 확인 스크립트로 확인했습니다(33개 항목). 스크립트는 SDK를 소스 참조 조건(`@glasspod/source`)과 tsx로 불러오는 Express 앱을 띄우고, 실제 서버(`apps/server/src/index.ts`)와 `ws`로 만든 가짜 서버(받은 메시지를 모두 기록하고 `parseSdkMessage`로 검증)에 붙여 봅니다. 같은 요청 목록을 SDK를 넣지 않은 같은 앱에도 보내 응답(상태 코드와 본문)을 비교합니다. 타입 검사는 두 미들웨어를 쓰는 작은 Express 앱 파일을 `tsc`(`skipLibCheck` 끔)로 검사합니다.

| 확인 | 기대 결과 |
| --- | --- |
| `npm run typecheck` | exit 0 |
| `npm test` | 모든 테스트 통과. 요청 집계, 응답 시간, 끊긴 요청, 오류 미들웨어의 route와 4xx 판단 테스트 포함 |
| `npm run format:check` | `All matched files use Prettier code style!` |
| Express 앱의 타입 | `app.use(glasspod.express())`, `app.use(glasspod.expressErrors())`가 `@types/express` 5.0.6으로 타입 검사를 통과 |
| 실제 서버 | 서버 로그에 `message received type=metrics`와 `type=event`. `message ignored` 없음 |
| 가짜 서버: 메시지 모양 | 모든 metrics가 `parseSdkMessage`를 통과. `http.*` 7개가 runtime 값과 app 값 사이에 들어 있음 |
| 요청 수와 오류 | 200 응답 N번, 500 응답 M번 뒤 `total`이 N+M, `errors_total`이 M. 404는 오류로 세지 않음 |
| 응답 시간 | 300ms 걸리는 요청 뒤 그 주기의 `duration_max_ms`가 300 이상. 요청이 없는 주기에는 응답 시간 세 값이 없음 |
| 끊긴 요청 | 클라이언트가 응답 전에 끊으면 `aborted_total`이 늘고, `errors_total`은 늘지 않음 |
| 처리 중 | 응답하지 않는 요청 3개가 걸려 있는 동안 `in_flight`가 3 |
| 미들웨어 앞의 라우트 | `/healthz`는 세지 않음 |
| 미들웨어 두 번 등록 | 같은 요청을 한 번만 셈 |
| `express()`를 부르지 않은 앱 | metrics에 `http.*`가 없음 |
| 오류 미들웨어 | 마운트된 Router의 라우트(동기 `throw`, `async` 거부, `next(err)`)에서 난 예외가 `route: "GET /orders/:id"`로 옴. 앱의 오류 처리기가 그대로 불리고 응답도 같음 |
| 4xx 오류 | `status: 404` 오류와 잘못된 JSON 본문(400)은 event를 보내지 않음 |
| 같은 예외 반복 | T06 규칙대로 묶임 |
| 앱이 읽는 `req.route` | `express()`가 있어도 라우트 안에서 `req.route.path`가 같음 |
| 서버가 없을 때 | 요청 처리와 응답이 SDK 없는 같은 앱과 같고, 앱이 스스로 끝남(`server.close()` 뒤) |
| 위 모든 경우 | SDK 때문에 생긴 처리되지 않은 예외 없음 |

직접 해 볼 때는 서버를 짧은 주기로 띄운 뒤 다른 터미널에서 실행합니다.

```bash
GLASSPOD_METRICS_INTERVAL_MS=1000 npm run dev:server
```

```bash
GLASSPOD_SERVER=ws://localhost:8080/agent POD_NAME=orders-1 POD_NAMESPACE=shop NODE_DEBUG=glasspod node --conditions=@glasspod/source --import tsx --input-type=module -e 'import express from "express"; import { glasspod } from "@glasspod/sdk"; glasspod.start(); const app = express(); app.use(glasspod.express()); app.get("/orders/:id", (req, res) => (req.params.id === "0" ? Promise.reject(new Error("DB timeout")) : res.json({ id: req.params.id }))); app.use(glasspod.expressErrors()); app.listen(3000, () => setInterval(() => fetch(`http://localhost:3000/orders/${Math.floor(Math.random() * 5)}`), 200));'
```

서버 로그에 `type=metrics`가 약 1초마다, `type=event`가 처음 한 번과 약 10초 뒤 한 번(묶음) 나옵니다. SDK 디버그 로그에는 `metrics sent seq=... values=17`, `express error reported route=GET /orders/:id`, 묶음 `event sent ... count=11` 같은 줄이 나옵니다. 이 명령은 앱의 오류 처리기가 없어 Express 기본 오류 처리기가 예외마다 `Error: DB timeout`과 stack을 출력하는데, SDK가 없을 때와 같습니다. 끝낼 때는 Ctrl+C로 멈춥니다.
