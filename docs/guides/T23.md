# T23 트래픽에서 빼기(격리)와 격리된 Pod 목록

- 우선순위: P0 · 단계 10 · 선행 작업: T18, T21 · 결정: 없음(아래 결정 1~4는 착수 전 사용자 결정)
- 브랜치: `feat/t23-isolate`
- 작성: 2026-11-23

## 목표

이상한 Pod를 지우지 않고 트래픽에서만 빼서, 살아 있는 채로 원인을 조사하게 합니다(design.md 5.4 '격리', 6장 4~5단계).

- 서버: '트래픽에서 빼기'(`isolate-pod`) — Service와 ReplicaSet이 함께 고르는 라벨을 떼고 격리 표시를 붙임. 격리된 Pod만 지우는 'Pod 삭제'(`delete-pod`). 서랍이 쓰는 미리 보기 API.
- 웹: '트래픽에서 빼기' 버튼과 서랍, 격리된 Pod 화면(Figma 확정-4, `/isolated`), 가운데 목록의 '격리됨' 묶음, '격리됨' 배지, 왼쪽 메뉴 링크.
- 로컬 클러스터에서 데모 앱 Pod 하나를 빼고, 새 Pod가 트래픽을 받는 동안 뺀 Pod를 계속 본 뒤 지웁니다.

## 결정 사항

1~4는 2026-11-23에 사용자가 정했습니다(착수 전에 보고한 질문 4개, 모두 추천안). 5~25는 이 작업의 기본값입니다.

ReplicaSet에서도 빠져야 대신할 Pod가 생김. 최소로 떼어 다른 라벨(버전 등)은 남김 |
| 7 | 뺄 수 없는 Pod | 이 Pod를 고르는 Service가 없음, 또는 ReplicaSet selector에 `matchLabels`가 없어 떼어 낼 키가 없음 → 409 `cannot-isolate`. 컨트롤러(ReplicaSet)가 없는 Pod는 허용(Service에서만 빠지고 대신할 Pod는 생기지 않음, 서랍에 경고) | 트래픽이 없는 Pod를 '트래픽에서 빼기'할 까닭이 없음. 직접 만든 Pod도 조사할 수 있음 |
| 8 | 실행 | 검사(결정 9)를 통과하면 Pod를 새로 읽어 uid·지워지는 중·격리 여부를 다시 보고, ReplicaSet을 읽고, Service를 list해 결정 6으로 계획한 뒤 merge patch 한 번(뗄 라벨 `null`, 표시 라벨, 주석, 읽은 `resourceVersion`). 그사이 Pod가 바뀌면 쿠버네티스가 409 → `target-changed`. 성공은 patch가 받아들여진 때(ReplicaSet이 놓아주고 새 Pod를 만드는 것은 그 뒤) | `resourceVersion`으로 읽은 그대로의 Pod에만 적용. ReplicaSet 컨트롤러는 selector가 맞지 않는 Pod의 ownerReference를 떼고(release) 모자란 수를 채움 |
| 9 | 검사 순서 | T21 결정 6의 ⑤ 다음에 격리 검사: `restart-pod`·`isolate-pod`는 격리된 Pod면 409 `target-isolated`, `delete-pod`는 격리되지 않은 Pod면 409 `target-not-isolated`. 그 뒤 ⑥ 실행 중, ⑦ 쿠버네티스. 계획 실패는 ⑦에서 409 `cannot-isolate`(기록함) | 서버가 거부할 조치를 화면도 미리 끄지만(결정 17) 서버가 한 번 더 막음 |
| 10 | 미리 보기 API | `GET /api/pods/:namespace/:name/isolation-plan` → 200 `IsolationPlanBody { serverTime, pod, uid, plan: { labels, services, replicaSet?, deployment? } }`. 실패는 `{ error, detail }`(조치와 같은 코드, 기록하지 않음): 403 `action-not-allowed`, 503 `kube-unavailable`, 404 `target-not-found`, 409 `target-terminating`·`target-isolated`·`cannot-isolate`, 쿠버네티스 오류(결정 8과 같은 바꾸기). 실행과 같은 함수로 계산 | 서랍이 보여 준 계획과 실행이 같은 규칙. 실행 때 다시 계산하므로 그사이 Service가 바뀌어도 실제로 뗀 라벨이 기록에 남음 |
| 11 | 조치 기록 | `ActionItem.isolation { labels, services }`(성공한 `isolate-pod`). `replicaSet`·`deployment`는 재시작과 같이 실행할 때의 것 | 무엇을 떼었는지 조치 기록과 타임라인에 남음 |

## 알려진 한계

- 되돌리기가 없습니다(결정 23). 다시 트래픽을 받게 하려면 손으로 라벨을 붙여야 하고, 그러면 ReplicaSet이 Pod 하나를 지웁니다.
- 미리 보기와 실행 사이에 Service가 바뀌면 실행이 다시 계산한 라벨을 뗍니다(기록에는 실제로 뗀 라벨).
- 격리된 Pod는 Deployment가 관리하지 않으므로 Deployment를 지워도 남습니다. 격리된 Pod 화면에서 지워야 합니다.
- 라벨을 떼도 이미 맺은 연결(keep-alive)은 끊기지 않습니다. 새 연결만 다른 Pod로 갑니다.

## 쓰는 법

```bash
curl -s 'localhost:8080/api/pods/glasspod-demo/<Pod>/isolation-plan'
```

```bash
curl -s -X POST localhost:8080/api/actions -H 'Content-Type: application/json' -d '{"action":"isolate-pod","target":{"namespace":"glasspod-demo","name":"<Pod>"},"expectedUid":"<uid>"}'
```

```bash
kubectl -n glasspod-demo get pods -l glasspod/isolated=true -L app
```

지울 때는 `"action":"delete-pod"`입니다. uid는 `GET /api/pods`의 `pods[].kube.uid`에 있습니다.
