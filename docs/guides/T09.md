# T09 snapshot 요청과 응답

- 우선순위: P1 · 단계 5 · 선행 작업: T04
- 브랜치: `feat/t09-snapshot`
- 작성: 2026-11-13

## 목표

개발자가 Pod 하나의 "지금 이 순간"을 물어볼 수 있게 합니다(design.md 7.3 request / response).

- 서버: HTTP `GET /api/pods/:namespace/:name/snapshot`을 받으면 그 Pod의 SDK에 `request`를 보내고, 5초까지 답을 기다렸다가 JSON으로 돌려줍니다. 5초 안에 답이 없으면 "응답 없음"(504)입니다. 이것도 이벤트 루프가 막혔다는 단서입니다.
- SDK: `request`를 받으면 그 자리에서 snapshot(상태 값, 진행 중인 요청과 경과 시간, 프로세스 정보)을 만들어 `response`로 답합니다. `hello`의 `capabilities`에 `snapshot`을 넣습니다.
- 진행 중인 요청 목록(`inFlight`)은 T07의 HTTP 미들웨어가 모읍니다(T07에서 넘긴 일).

## 결정 사항

1~2는 2026-11-13에 사용자가 정했습니다. 3~18은 이 작업의 기본값입니다.

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | 요청 입구 | HTTP `GET /api/pods/:namespace/:name/snapshot` 하나를 지금 만듦 | 사용자 결정. curl로 바로 확인할 수 있고, T19 상세 화면이 그대로 씀. 웹 화면용 조회 API(T14)의 경로 하나를 먼저 만드는 것이므로 T14에서 다른 API와 형식을 맞춤 |
| 2 | 라우트가 정해지기 전 요청의 `route` | 메서드만 씀(예: `GET`). 라우트가 정해진 요청은 T07과 같은 라우트 모양(예: `GET /orders/:id`) | 사용자 결정. T07 결정 11과 같은 기준. 실제 경로(`/orders/7`)에는 id와 개인 정보가 들어갈 수 있음 |
| 3 | 브랜치 | T08이 이미 `main`에 병합·push되어 있어 `main`에서 `feat/t09-snapshot`을 만듦. 커밋하지 않은 T08 병합 기록(`docs/logs/2026-11-12.md`)을 함께 가져감 | T08 로그에 '다음 작업 브랜치에서 함께 커밋'으로 적음 |
| 4 | 시간 제한 | 서버가 `request`를 보낸 뒤 5초. 서버 상수(`REQUEST_TIMEOUT_MS`)로 두고 환경변수로 받지 않음 | design.md 7.3. hello 대기 10초처럼 프로토콜이 정한 값이고 환경에 따라 달라지지 않음 |
| 5 | 늦게 온 답 | 5초가 지난 뒤 온 `response`, 기다리지 않는 `replyTo`는 경고 한 줄을 남기고 버림. 연결은 유지 | 막혔던 앱이 풀리면 늦게 답함. 이미 504로 답한 요청이라 쓸 곳이 없음 |
| 6 | 요청 id | 서버 프로세스에서 1부터 세는 `r-1`, `r-2`… | 연결마다 겹치지 않으면 충분함. 로그에서 요청과 답을 짝짓기 쉬움 |
| 7 | 동시 요청 상한 | 연결마다 답을 기다리는 요청 5개까지. 넘으면 보내지 않고 429 | HTTP API에 아직 인증이 없음(D4). 막힌 앱에 요청이 쌓이지 않게 하고, 풀린 뒤 앱이 한꺼번에 답하느라 바쁘지 않게 함 |
| 8 | 같은 Pod의 연결이 둘 이상 | 가장 최근에 `hello`를 받아들인 연결로 보냄. 예전 연결이 나중에 닫혀도 새 연결은 그대로 둠 | SDK가 다시 붙는 동안 예전 소켓이 잠깐 남을 수 있음(T08 응답 없는 연결). 새 연결이 지금 살아 있는 프로세스 |
| 9 | `capabilities` | SDK는 `hello`에 `["snapshot"]`을 넣음. 서버는 `capabilities`에 `snapshot`이 없으면 보내지 않고 501 | design.md 7.3. 예전 SDK(T04~T08)는 `capabilities`가 없고 `request`를 무시하므로, 보내면 5초 기다린 뒤 504로 앱 멈춤처럼 보임 |
| 10 | 서버의 답 검증 | `ok: true`인 답의 `data`를 `snapshot.schema.json`으로 검증(`validateSnapshotData`, `@glasspod/protocol`). 실패하면 502와 경고 한 줄 | T02에서 넘긴 일(snapshot `data` 검증 함수). 받은 값은 프로토콜 검증 함수로 확인한다는 규칙 |
| 11 | `inFlight` 목록 | `glasspod.express()` 미들웨어가 센 요청 가운데 아직 끝나지 않은 것(응답의 `close` 전). 시작한 순서(경과 시간이 긴 것부터)로 100개까지. `elapsedMs`는 정수 ms. `express()`를 부르지 않은 앱은 빈 배열 | `http.requests.in_flight` 값과 같은 기준. 막힌 요청은 오래된 것이 원인 후보. 시작한 순서로 들고 있어 정렬하지 않고 앞에서 100개만 읽음 |
| 12 | `process` | 스키마 그대로 `uptimeSec`(`process.uptime()`, 소수 셋째 자리까지)와 `heapUsedBytes`(`process.memoryUsage().heapUsed`)만 | 메모리·CPU는 metrics에 이미 있음. 필드는 나중에 더해도 버전을 올리지 않음 |
| 13 | SDK가 답하는 때 | `welcome`을 받은 연결에서 `request`가 오면 그 자리에서(동기로) 만들어 바로 보냄. `welcome` 전의 `request`는 무시 | 가볍고 동기로 끝남. 서버는 `welcome` 뒤에만 보냄 |
| 14 | SDK의 실패 답 | 모르는 `action`이면 `ok: false`, `error`는 `unknown action: "threadDump"`(action은 100자까지). snapshot을 만들다 예외가 나면 `ok: false`, `error`는 `snapshot failed` | design.md 7.3. 내부 오류 내용은 디버그 로그에만 남김 |
| 15 | 응답 없는 SDK | 서버는 504로 답하고 연결은 닫지 않음 | T08 결정 17과 같음. 연결을 닫으면 '앱 멈춤 의심'(design.md 7.5)을 구분할 수 없음 |
| 16 | 보관 | 서버는 받은 snapshot을 보관하지 않고 HTTP로 돌려주기만 함 | 보관 방식은 D1(T11) |
| 17 | HTTP 응답 | 성공은 200과 아래 '쓰는 법'의 JSON. 실패는 `{ "error": 코드, "detail": 설명 }`과 아래 상태 코드. 모두 `Cache-Control: no-store` | 조회 결과가 매번 다름. 상태 코드로 curl과 웹 화면이 바로 구분함 |
| 18 | 앱 보호 | SDK의 request 처리는 `guard`로 감쌈. 새 타이머 없음. 공개 API는 그대로 | SDK 원칙 |

### HTTP 상태 코드

| 상태 | `error` | 뜻 |
| --- | --- | --- |
| 200 | | SDK가 답함 |
| 404 | `not-connected` | 그 Pod의 SDK 연결이 없음(`hello`를 받아들인 연결 기준) |
| 501 | `not-supported` | SDK의 `capabilities`에 `snapshot`이 없음 |
| 429 | `busy` | 그 연결에서 답을 기다리는 요청이 이미 5개 |
| 504 | `no-response` | 5초 안에 답이 없음. 앱 멈춤의 단서 |
| 502 | `disconnected` | 기다리는 동안 연결이 끝남 |
| 502 | `sdk-error` | SDK가 `ok: false`로 답함. `detail`은 SDK의 `error` |
| 502 | `invalid-response` | SDK의 답이 snapshot 스키마와 맞지 않음 |

### 사전 확인

Node 22.22.0, Express 5.3.0, macOS에서 2026-11-13에 확인했습니다. 완료 기준의 확인 스크립트(실제 서버와 Express 앱)로 봤습니다.

| 확인 | 결과 |
| --- | --- |
| 라우트 핸들러 안에서 기다리는 요청의 `req.route` | Express가 핸들러를 부르기 전에 대입하므로 T07의 접근자로 라우트 모양을 얻음. 라우트 앞 미들웨어에서 기다리는 요청은 대입 전이라 없음 |
| `Map`의 순서 | 넣은 순서대로 돌므로 시작 시각 순서와 같음(`performance.now()`는 줄지 않음) |

## 범위

### 포함

- 프로토콜: snapshot `data` 검증 함수 `validateSnapshotData`와 테스트, `snapshot.schema.json` 설명(정렬, route 모양, 단위)
- SDK: 진행 중인 요청 목록(`http.ts`), snapshot 만들기와 request 답하기(`snapshot.ts`), `hello`의 `capabilities`와 request 받기(`connection.ts`), 연결(`index.ts`)과 단위 테스트
- 서버: SDK 연결 목록과 request 보내기·답 기다리기(`agents.ts`, `requests.ts`), snapshot HTTP API(`snapshot.ts`, `app.ts`)와 단위 테스트

### 제외

- 웹 화면의 snapshot 표시(T19)
- 받은 snapshot 보관(D1, T11)
- 응답 없음을 상태 판단에 넣는 일(T13)
- HTTP API 인증과 접속 방식(D4, T20). 다른 조회 API(T14)
- 쿠버네티스에서 Pod가 있는지 확인(T12). 서버는 SDK 연결만 봄
- `snapshot` 말고 다른 action(예: Spring Boot의 `threadDump`, design.md 11장)
- 데모 앱(T10). 실제 동작은 저장소에 넣지 않는 확인 스크립트로 확인함

## 쓰는 법

앱 코드는 바뀌지 않습니다. 진행 중인 요청 목록은 `app.use(glasspod.express())`를 넣은 앱에서만 나옵니다.

```bash
curl -s localhost:8080/api/pods/shop/orders-7d9f8-x2kq1/snapshot
```

```json
{
  "pod": { "namespace": "shop", "name": "orders-7d9f8-x2kq1" },
  "instanceId": "4f1c2a9e-0b7d-4c55-9a52-7f3e1d2c8b10",
  "ts": 1793873740020,
  "elapsedMs": 3,
  "snapshot": {
    "state": { "app.mode": "draining" },
    "inFlight": [
      { "route": "GET /orders/:id", "elapsedMs": 8200 },
      { "route": "POST", "elapsedMs": 950 }
    ],
    "process": { "uptimeSec": 3600.125, "heapUsedBytes": 48234496 }
  }
}
```

- `ts`는 SDK가 답을 보낸 시각(SDK 시계), `elapsedMs`는 서버가 `request`를 보낸 때부터 답을 받을 때까지입니다.
- 두 번째 요청은 라우트 앞 미들웨어(예: 본문 파싱)에서 기다리는 중이라 메서드만 나옵니다.

```bash
curl -si localhost:8080/api/pods/shop/orders-7d9f8-x2kq1/snapshot   # 앱이 막혀 있으면 5초 뒤
```

```text
HTTP/1.1 504 Gateway Timeout
Cache-Control: no-store

{"error":"no-response","detail":"no response within 5000ms"}
```

SDK와 서버 사이의 메시지입니다.

```json
{ "type": "request", "id": "r-7", "action": "snapshot" }
```

```json
{ "type": "response", "seq": 51, "ts": 1793873740020, "replyTo": "r-7", "ok": true, "data": { "state": {}, "inFlight": [], "process": { "uptimeSec": 12.5, "heapUsedBytes": 9437184 } } }
```

```json
{ "type": "response", "seq": 52, "ts": 1793873741020, "replyTo": "r-8", "ok": false, "error": "unknown action: \"threadDump\"" }
```

## 완료 기준

실제 동작은 저장소에 넣지 않는 확인 스크립트로 확인했습니다(40개 항목). 스크립트는 SDK를 소스 참조 조건(`@glasspod/source`)과 tsx로 불러오는 작은 Express 앱(느린 라우트, 라우트 앞에서 기다리는 미들웨어, 이벤트 루프를 막는 스위치)을 띄우고, 실제 서버(`apps/server/src/index.ts`)와 `ws`로 만든 가짜 SDK·가짜 서버에 붙여 봅니다.

| 확인 | 기대 결과 |
| --- | --- |
| `npm run typecheck` | exit 0 |
| `npm test` | 모든 테스트 통과. 답 기다리기(5초, 상한, 늦은 답, 연결 끝), 상태 코드 만들기, 연결 목록, inFlight 목록, request 답하기, snapshot 검증 테스트 포함. 생성한 타입이 스키마와 같음 |
| `npm run format:check` | `All matched files use Prettier code style!` |
| SDK의 `hello` | `capabilities`가 `["snapshot"]` |
| 연결된 앱에 snapshot | 200. `state`에 정한 상태 값, `inFlight`에 느린 라우트가 `GET /slow/:id` 모양으로, 라우트 앞에서 기다리는 요청은 `POST`로, 오래된 것부터. `process` 값이 있음. `Cache-Control: no-store` |

| 연결이 없는 Pod | 404 `not-connected` |
| 앱의 이벤트 루프를 7초 막고 snapshot | 약 5초 뒤 504 `no-response`. 풀린 뒤 늦게 온 답은 서버 로그 `response ignored`. 연결은 유지되고 다음 snapshot은 200 |

| 위 모든 경우 | SDK 때문에 생긴 처리되지 않은 예외 없음. 서버 로그에 `message ignored` 없음 |
