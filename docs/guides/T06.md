# T06 SDK event

- 우선순위: P0 · 단계 5 · 선행 작업: T04
- 브랜치: `feat/t06-sdk-events`
- 작성: 2026-11-10

## 목표

Node.js SDK가 일이 생기자마자 `event` 메시지를 보냅니다(design.md 5.1, 7.3). 이벤트는 세 가지입니다.

- 예외(`exception`): 처리되지 않은 예외는 SDK가 스스로 잡고, 앱이 잡은 예외는 `glasspod.exception()`으로 보고합니다.
- 상태 전환(`state`): `glasspod.state(name, value)`로 정한 상태 값이 바뀔 때 보냅니다.
- 개발자가 정의한 이벤트(`app.*`): `glasspod.event(name, options)`

같은 이벤트가 쏟아지면 묶어서 `count`로 보내고, 서버가 정한 1분 한도(`welcome`의 `maxEventsPerMinute`)를 넘지 않습니다. 처리되지 않은 예외로 프로세스가 끝날 때는 그 예외를 서버로 먼저 보내므로, 컨테이너가 바뀌어도 직전 예외가 서버에 남습니다.

| 11 | 예외 이벤트 모양 | `name: exception`, `level: error`, `message`는 예외 메시지, `data`에 `errorType`, `stack`. 처리되지 않은 예외는 `origin`(`uncaughtException` 또는 `unhandledRejection`)과, 프로세스가 끝나면 `fatal: true`를 더함. `exception()`의 `data`는 이 키들 앞에 넣음(같은 키는 SDK 값이 이김) | design.md 7.3의 예와 같음. 서버가 재시작 원인 후보(7.5)를 고를 때 `fatal`을 씀 |
| 12 | `errorType` | `error.name`이 `Error`가 아니면 그 값, 아니면 생성자 이름(`class TimeoutError extends Error`), 둘 다 없으면 `Error`. `Error`가 아닌 값을 던지면 그 값의 종류(`string` 등)를 쓰고 `message`는 `String(value)`. `message`가 문자열인 객체는 `Error`를 상속하지 않아도 예외로 봄. `stack`은 V8이 만든 그대로 보냄(`name`을 정하지 않은 사용자 정의 예외는 첫 줄이 `Error: ...`) | `name`을 따로 정하지 않은 사용자 정의 예외도 구분됨 |
| 13 | 길이 상한 | `message` 1000자, `stack` 50줄·8000자, `data`는 JSON으로 8192자. 넘는 `message`와 `stack`은 잘라서 끝에 `...`. `data`가 JSON으로 바꿀 수 없거나(순환, BigInt) 너무 크면 `data` 없이 보내고 이름마다 처음 한 번 경고 | 처리되지 않은 예외는 기다리지 않으므로 메시지가 소켓 버퍼에 한 번에 들어가야 함(실험에서 100KB까지 도착) |
| 14 | `event()` 규칙 | 이름은 metrics와 같은 `app.*` 규칙(`^app(\.[a-z][a-z0-9_]*)+$`). `level`은 `info`(기본)·`warn`·`error`. 이름, `level`, `message`(문자열이 아님)에 문제가 있으면 보내지 않고 이름마다 처음 한 번 경고 | `exception`, `state`와 앞으로 SDK가 만들 이름이 겹치지 않음 |
| 15 | `state()` 규칙 | 이름은 `app.*` 규칙, 값은 200자 이하 문자열. 값이 바뀔 때만 `name: state`, `level: info` 이벤트를 보냄. 처음 정할 때도 보냄. `message`는 `app.mode: ready -> draining`(처음은 `app.mode: ready`), `data`는 `{ name, from?, to }`. 상태는 100개까지 | design.md 7.3. snapshot의 `state` 값은 문자열(snapshot.schema.json) |
| 16 | 부르는 때 | 세 함수는 `start()` 전, SDK가 꺼졌을 때, `stop()` 뒤에도 부를 수 있음. 연결이 없으면 이벤트는 버리고 상태 값만 기억. 처리되지 않은 예외 감시는 `start()`가 연결을 만들 때 켜고 `stop()`에서 끔 | 앱 코드가 SDK 상태를 몰라도 됨. SDK가 꺼져 있으면 `process`에 리스너를 달지 않음 |
| 17 | 앱 보호 | 세 함수는 예외를 던지지 않음. 묶음 타이머(1초 간격, 묶는 이벤트가 있을 때만)는 `unref()`하고, 타이머 콜백과 예외 감시 리스너는 `guard`로 감쌈 | SDK 원칙 |

### 처리되지 않은 예외 보내기 비교

Node 22.22.0, macOS, 같은 컴퓨터의 `ws` 8.22.0 서버로 2026-11-10에 확인했습니다.

| 방식 | 서버 도착 | 오류 출력과 종료 코드 | 그 밖에 |
| --- | --- | --- | --- |
| `uncaughtExceptionMonitor`에서 `send()`만 하고 끝냄 | `ws://`·`wss://` 모두 1KB, 20KB, 100KB는 도착. 1MB는 도착하지 않음 | SDK가 없을 때와 같음(소스 위치 표시 포함). 종료 코드 1 | 기다리지 않음. 앱이 자기 `uncaughtException` 리스너를 가지면 보고만 하고 앱은 계속 돎(종료 코드 0) |
| `uncaughtException` 리스너로 잡고 전송을 기다린 뒤 리스너를 떼고 다시 던짐 | 도착 | 종료 코드는 같지만 소스 위치 표시가 다시 던진 SDK 줄로 바뀜 | 기다리는 동안 앱 코드가 계속 돎. 앱이 자기 리스너를 가졌는지 따로 따져야 함 |

내장 WebSocket의 `send()`는 소켓에 바로 쓰기를 시도하므로, 운영체제의 소켓 버퍼에 들어가는 크기면 프로세스가 끝나도 운영체제가 마저 보냅니다. 처리되지 않은 Promise 거부도 Node 기본 모드(`--unhandled-rejections=throw`)에서는 같은 길로 와서 `origin`이 `unhandledRejection`으로 나옵니다. 다른 컴퓨터로 보낼 때(클러스터 안)는 T15 이후 시나리오 점검에서 다시 확인합니다.

## 묶는 규칙

```text
같은 이벤트 A가 0초, 1초, 2초, ... 25초에 한 번씩 일어날 때 (한도 안)

 0초  A 첫 건            -> 바로 보냄 count=1 (ts=0초)
 1~9초 A 9번             -> 셈
10초  창 끝, 센 것 9번   -> 보냄 count=9 (ts=1초), 다시 10초를 셈
11~20초 A 10번           -> 셈
20초  창 끝              -> 보냄 count=10 (ts=11초) ...
```

- 창 끝은 1초 간격 타이머로 확인하므로 10~11초 사이에 보냅니다.
- 창이 끝났는데 센 것이 없으면 그 이벤트는 잊습니다. 다음에 일어나면 다시 첫 건으로 바로 보냅니다.
- 한도에 걸린 묶음은 창이 끝난 뒤에도 남아 1초마다 다시 시도하고, 그동안 일어난 것도 계속 셉니다.

## 범위

### 포함

- 같은 이벤트 묶기와 1분 한도(`events.ts`)와 단위 테스트
- 예외와 `event()` 인자를 이벤트 내용으로 바꾸기, 검사, 자르기(`reports.ts`)와 단위 테스트
- 상태 값 보관과 전환(`states.ts`)과 단위 테스트
- 처리되지 않은 예외 감시(`crash.ts`)
- 공개 API(`index.ts`): `glasspod.exception`, `glasspod.state`, `glasspod.event`
- `registry.ts`: `app.*` 이름 검사를 함께 쓰도록 내보냄

### 제외

- 끊긴 동안 event 보관과 재전송 (T08)
- snapshot 응답에서 상태 값 돌려주기 (T09). 이번에는 값을 들고 있기만 함
- HTTP 요청 중 난 예외의 `route` 자동 채우기 (T07)
- 서버의 보관과 표시 (T11, T14). 서버는 지금처럼 받은 종류와 `seq`만 로그에 남김
- 데모 앱 (T10). 실제 전송은 저장소에 넣지 않는 확인 스크립트로 확인함

## 쓰는 법

```ts
import { glasspod } from "@glasspod/sdk";

glasspod.start({ app: { name: "orders", version: "1.4.2" } });

// 앱이 잡은 예외를 보고합니다. errorType과 stack은 SDK가 채웁니다.
try {
  await db.query(sql);
} catch (error) {
  glasspod.exception(error, { route: "GET /orders" });
}

// 상태 값을 정합니다. 바뀔 때만 state 이벤트가 나갑니다.
glasspod.state("app.mode", "ready");
process.on("SIGTERM", () => glasspod.state("app.mode", "draining"));

// 직접 정의한 이벤트입니다. level은 info(기본), warn, error입니다.
glasspod.event("app.cache.cleared", {
  level: "warn",
  message: "evicted 1200 keys",
  data: { keys: 1200 },
});

// 처리되지 않은 예외는 따로 할 일이 없습니다. SDK가 보낸 뒤 Node가 원래대로 끝냅니다.
```

보내는 메시지의 예입니다.

```json
{ "type": "event", "seq": 12, "ts": 1793873733870, "level": "error", "name": "exception",
  "message": "DB timeout after 5000ms", "count": 1,
  "data": { "route": "GET /orders", "errorType": "TimeoutError", "stack": "TimeoutError: DB timeout after 5000ms\n    at ..." } }
```

```json
{ "type": "event", "seq": 13, "ts": 1793873734100, "level": "info", "name": "state",
  "message": "app.mode: ready -> draining", "count": 1,
  "data": { "name": "app.mode", "from": "ready", "to": "draining" } }
```

## 도구 버전

새로 설치하는 패키지가 없습니다. `process`의 `uncaughtExceptionMonitor`와 `node:util`의 `types.isNativeError`는 Node 22.22.0 내장 API입니다.

## 완료 기준

실제 전송은 저장소에 넣지 않는 확인 스크립트로 확인했습니다(49개 항목). 스크립트는 SDK를 소스 참조 조건(`@glasspod/source`)과 tsx로 불러오는 작은 앱을 띄우고, 실제 서버(`apps/server/src/index.ts`)와 `ws`로 만든 가짜 서버(받은 메시지를 모두 기록하고 `parseSdkMessage`로 검증, welcome 값을 바꿀 수 있음)에 붙여 봅니다. 처리되지 않은 예외를 일으키는 시나리오는 SDK를 끈 같은 앱도 돌려 표준 오류와 종료 코드를 비교합니다(`[glasspod]` 경고 줄은 빼고 비교).

| 확인 | 기대 결과 |
| --- | --- |
| `npm run typecheck` | exit 0 |
| `npm test` | 모든 테스트 통과. 묶기·한도, 예외 내용 만들기, 상태 전환 테스트 포함 |
| `npm run format:check` | `All matched files use Prettier code style!` |
| 실제 서버 | 서버 로그에 `message received type=event`. `message ignored` 없음 |
| 가짜 서버: 메시지 모양 | 모든 event가 `parseSdkMessage`를 통과. `exception()`은 `errorType`, `stack`, 넘긴 `data`가 들어 있음 |
| 같은 예외 120번(1초 안) | 바로 한 건(`count` 1), 약 10초 뒤 한 건(`count` 119). 두 `count`의 합이 120 |
| 같은 예외가 25초 동안 계속 | 약 10초에 한 건씩, `count` 합이 일어난 횟수와 같음 |
| 1분 한도(welcome `maxEventsPerMinute` 5) | 60초 동안 5건을 넘지 않음. 경고 한 줄. 한도가 풀린 뒤 남은 것이 묶여 나감 |
| 서로 다른 이벤트 101개(10초 안) | 100개까지 셈, 경고 한 줄 |
| `state()` | 처음 정할 때와 값이 바뀔 때만 한 건씩. 같은 값은 보내지 않음 |
| `event()`, `state()` 사용 실수 | 문제마다 경고 한 줄, 예외 없음. `data` 문제는 `data` 없이 보냄 |
| 처리되지 않은 예외(`throw`) | 서버에 `origin: uncaughtException`, `fatal: true` 이벤트. 오류 출력과 종료 코드(1)가 SDK 없는 같은 앱과 같음 |
| 처리되지 않은 Promise 거부 | 서버에 `origin: unhandledRejection`, `fatal: true` 이벤트. 종료 코드 1 |
| 세고 있던 같은 예외 뒤에 처리되지 않은 예외 | 마지막 이벤트의 `count`에 세던 횟수가 더해짐. 다른 묶음도 함께 나감 |
| 앱이 자기 `uncaughtException` 리스너를 가짐 | `fatal` 없는 이벤트를 보내고 앱은 계속 돎. 반복되면 묶임 |
| `--unhandled-rejections=warn` | Node 동작대로 끝나지 않고, SDK도 보내지 않음 |
| 서버가 없을 때 | 세 함수가 예외 없이 끝나고 앱이 스스로 끝남. 처리되지 않은 예외의 출력과 종료 코드는 SDK 없는 앱과 같음 |
| `maxEventsPerMinute` 0 | 처리되지 않은 예외를 포함해 아무 event도 보내지 않음. 경고 한 줄 |
| `stop()` 뒤 | event를 보내지 않음. 처리되지 않은 예외도 보내지 않음 |
| 위 모든 경우 | SDK 때문에 생긴 처리되지 않은 예외 없음 |

직접 해 볼 때는 서버를 띄운 뒤 다른 터미널에서 실행합니다.

```bash
npm run dev:server
```

```bash
GLASSPOD_SERVER=ws://localhost:8080/agent POD_NAME=orders-1 POD_NAMESPACE=shop NODE_DEBUG=glasspod node --conditions=@glasspod/source --import tsx --input-type=module -e 'import { glasspod } from "@glasspod/sdk"; glasspod.start(); setTimeout(() => { glasspod.state("app.mode", "ready"); setInterval(() => glasspod.exception(new Error("DB timeout after 5000ms")), 200); }, 1000); setTimeout(() => { throw new Error("boom"); }, 13000);'
```

서버 로그에 `message received type=event`가 처음에 두 번(state, 첫 예외), 약 11~12초에 한 번(묶음), 13초에 두 번(처리되지 않은 예외, 그 뒤 세고 있던 묶음) 나옵니다. 앱은 `Error: boom`을 출력하고 종료 코드 1로 끝납니다. SDK 디버그 로그에는 `event sent ... count=49` 같은 묶음과 `crash reported ... pending=1`이 나옵니다.

`start()` 바로 뒤에 부른 `state()`는 아직 연결되기 전(welcome 전)이라 보내지 않고 버립니다(결정 9). 값은 기억하므로 다음 전환부터는 `from`이 맞게 나갑니다. 연결 전에 일어난 이벤트를 들고 있다가 보내는 일은 T08에서 합니다.
