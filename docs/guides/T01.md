## 목표

npm workspaces 모노레포 골격을 만듭니다. 이후 작업(T02 프로토콜, T03 서버, T04 SDK, T17 웹)이 같은 명령으로 타입 검사와 테스트를 할 수 있어야 합니다.

## 결정 사항

2026-11-05에 사용자가 추천안으로 정했습니다. npm workspaces, TypeScript strict, Node 22.22.0, Vitest는 그 전에 정해져 있었습니다.

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | 모듈 방식 | ESM만 사용. `"type": "module"`, `module`/`moduleResolution`은 `NodeNext` | Node 22.12부터 CommonJS 앱도 `require()`로 ESM 패키지를 불러올 수 있어 두 방식으로 배포할 필요가 없음 |
| 2 | 실행 도구 | 개발할 때는 `tsx watch`, 빌드할 때는 `tsc` | 개발 중에는 빌드 없이 바로 실행 |
| 3 | 타입 검사 | TypeScript project references, `tsc -b` | `npm run typecheck` 하나로 모든 워크스페이스와 그 사이의 참조를 검사 |
| 4 | 린트·포맷 | Prettier만. ESLint는 나중에 | 설정 비용이 작음 |
| 5 | 패키지 이름 | `@glasspod/protocol`, `@glasspod/sdk`, `@glasspod/server`, `@glasspod/web`, `@glasspod/demo-app`. 지금은 모두 `"private": true` | npm에 `@glasspod/sdk`가 없는 것을 확인함(design.md 12장) |
| 6 | T01 범위 | 워크스페이스 5개는 빈 껍데기만 만듦 | Express는 T03, React와 Vite는 T17에서 설치 |

## 워크스페이스 사이 참조

의존 관계:

```text
@glasspod/sdk      → @glasspod/protocol
@glasspod/server   → @glasspod/protocol
@glasspod/web      → @glasspod/protocol
@glasspod/demo-app → @glasspod/sdk
```

- **타입 검사**: 루트 `tsconfig.json`이 다섯 프로젝트를 `references`로 묶습니다. `tsc -b`가 의존 순서대로 검사하고, 결과물은 각 워크스페이스의 `dist/`에 둡니다. `dist/`는 커밋하지 않습니다.
  - 웹(`apps/web`)은 나중에 Vite가 빌드하므로 `noEmit`으로 검사만 합니다. 모듈 해석은 `Bundler`입니다.
  - `npm run clean`은 `tsc -b --clean`을 실행한 뒤 `dist/`를 지웁니다. `tsc -b --clean`은 지금 있는 소스의 결과물만 지우기 때문에, 이미 지운 소스의 결과물이 남습니다.
- **실행(개발, 테스트)**: 빌드하지 않고 소스를 바로 씁니다.
  - 라이브러리 패키지(`protocol`, `sdk`)의 `exports`에 사용자 조건 `@glasspod/source`를 두고, 이 조건이 `src/index.ts`를 가리키게 합니다.
  - Vitest(`vitest.config.ts`의 `ssr.resolve.conditions`)와 tsx(`--conditions`)가 이 조건을 켭니다.
  - Vitest는 `dist/`를 테스트 대상에서 뺍니다. Vitest 4부터 기본 제외 목록에 `dist/`가 없어서, 빼지 않으면 빌드된 테스트 파일까지 두 번 실행합니다.
  - 조건을 켜지 않은 쪽은 `dist/`를 씁니다. 배포한 SDK를 설치한 앱이나 `node`로 직접 실행하는 경우가 여기에 해당합니다.
- **ESM 규칙**: 상대 경로 import에는 `.js` 확장자를 붙입니다(`import { x } from "./x.js"`). 타입만 가져올 때는 `import type`을 씁니다(`verbatimModuleSyntax`).

## 도구 버전

devDependencies는 루트 `package.json`에 두고 정확한 버전으로 고정합니다(`--save-exact`). 버전은 `package-lock.json`으로도 고정됩니다. 공급망 위험을 줄이려고 공개된 지 2주가 지난 버전만 고릅니다.

| 도구 | 버전 | 메모 |
| --- | --- | --- |
| `typescript` | 7.0.2 | Go로 다시 만든 컴파일러. ESLint를 붙일 때 typescript-eslint가 7을 지원하는지 확인 |
| `vitest` | 5.0.5 | 5.1.0은 공개된 지 4일이라 쓰지 않음 |
| `vite` | 8.3.5 | Vitest의 필수 peer. 아래 `.npmrc` 설정 때문에 직접 설치함. T17에서 웹에 Vite를 넣을 때 버전을 맞춤 |
| `tsx` | 4.23.15 | |
| `prettier` | 3.9.10 | |
| `@types/node` | 22.20.5 | 실행 환경인 Node 22에 맞춤 |

### `.npmrc`의 `legacy-peer-deps=true` (2026-11-06 사용자 결정)

Node 22.22.0에 들어 있는 npm 10.9.4에 peer 의존성 버그가 있습니다.

1. Vite 8의 선택 peer `@vitejs/devtools-vitest`가 `vitest@*`로 최신 Vitest를 끌어옵니다.
2. 그 버전이 고정한 Vitest와 다르면 npm이 충돌을 알리지 못하고 `Cannot read properties of null (reading 'edgesOut')`로 멈춥니다.

Vitest 5.0.5와 4.1.12 모두 같은 오류가 났고, 최신 5.1.0만 설치되었습니다. 그래서 npm이 peer를 자동으로 설치하지 않게 했습니다. 이제 필요한 peer는 `package.json`에 직접 적어야 합니다(예: T17의 `react`, `react-dom`).
