# T22 Pod 재시작

- 우선순위: P0 · 단계 10 · 선행 작업: T18, T21 · 결정: 없음(아래 결정 1~2는 착수 전 사용자 결정)
- 브랜치: `feat/t22-pod-restart`
- 작성: 2026-11-22

## 목표

Pod 재시작의 서버 처리, `pods: delete` 권한, 상세 머리줄의 '재시작' 버튼과 서랍은 T21에서 만들었습니다(T21 결정 1). 이 작업은 T15에서 넘긴 두 가지만 다룹니다.

- 데모 앱 Pod를 지우거나 바꿀 때 부하 요청이 실패하는지와 그 원인을 확인합니다.
- 실패를 줄이려고 종료를 늦출지(preStop 지연) 정하고 매니페스트에 넣습니다.

## 결정 사항

1~2는 2026-11-22에 사용자가 정했습니다(사전 확인 결과를 보고한 질문 2개, 모두 추천안). 3~8은 이 작업의 기본값입니다.

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | 종료를 늦추는 방법 | 데모 앱 Deployment(`deploy/demo/demo-app.yaml`)에 `lifecycle.preStop.sleep`. 앱 코드는 그대로 둠 | 사용자 결정(추천안). 쿠버네티스 1.34에 들어 있는 sleep 동작이라 이미지에 셸이 없어도 됨. Pod가 Service에서 빠진 것이 퍼지는 동안 앱이 그대로 답하고, 그 뒤 SIGTERM을 받아 T10의 종료 처리(`draining` → 서버 닫기 → `glasspod.stop()`)를 그대로 함. 앱이 SIGTERM 뒤에 기다리는 방법은 코드·테스트를 고쳐야 하고 노트북의 Ctrl+C도 따로 다뤄야 함 |
| 2 | 지연 시간 | 5초 | 사용자 결정(추천안). 사전 확인에서 0건이 된 값. 5초와 앱의 강제 종료 한도(`SHUTDOWN_TIMEOUT_MS` 10초)를 합쳐도 유예 시간(기본 30초) 안 |
| 3 | 브랜치 | `main`에서 `feat/t22-pod-restart`를 만듦. 커밋하지 않은 T21 병합 기록(`docs/logs/2026-11-21.md`)을 함께 가져감 | T21 로그에 '다음 작업 브랜치에서 함께 커밋'으로 적음 |
| 4 | 유예 시간 | `terminationGracePeriodSeconds`는 적지 않음(기본 30초) | 지연 5초 + 종료 최대 10초 = 15초라 기본값으로 충분함 |
| 5 | 부하 스크립트 | 그대로 둠. 실패한 요청을 다시 보내지 않음 | 다시 보내면 Pod를 바꿀 때 생기는 실패가 숨겨짐. 이 작업은 실패가 없어졌는지를 보는 것 |
| 6 | 서버 Deployment | `deploy/server/server.yaml`에는 넣지 않음 | 서버 앞의 트래픽은 port-forward(Pod에 바로 붙음)와 SDK WebSocket뿐이고 둘 다 끊기면 다시 붙음. `Recreate`라 새 서버가 뜨기 전에 옛 서버가 끝나야 함 |
| 7 | 서버·화면 | 고치지 않음. 지연 동안 서버의 판단은 이미 `terminated`(근거 `terminating`)이고 SDK는 연결된 채로 지표를 보냄. 재시작 서랍의 '실행하면' 1번('Pod를 지웁니다. 앱은 종료 신호(SIGTERM)를 받고 유예 시간 안에 끝납니다.')도 그대로 맞음 | Pod마다 preStop과 유예 시간을 읽어 서랍에 보이는 것은 범위 밖 |
| 8 | 확인 방법 | 완료 기준은 클러스터의 `demo-load` 요약(초당 10건, 10초마다 `failed` 수). 더 촘촘한 확인은 `demo-load` Pod 안에서 `kubectl exec`로 돌린 탐침(초당 50건, 실패를 종류·시각별로 셈)으로 하고, 탐침 스크립트는 저장소에 넣지 않음 | 탐침은 이번 원인 확인용. 다시 쓸 일이 생기면 그때 부하 스크립트에 실패 종류를 더함 |

## 사전 확인

로컬 클러스터(context `docker-desktop`, Kubernetes 1.34.1, kube-proxy iptables 모드), 데모 앱 Pod 3개와 `demo-load` 1개, 클러스터 안 서버 `glasspod-server:dev`에서 2026-11-22에 확인했습니다. 탐침은 `demo-load` Pod 안에서 `http://demo-app:3000/orders/1`에 20ms마다 새 연결(`agent: false`)로 요청하고 10초에 끊었습니다.

| 확인 | 결과 |
| --- | --- |
| Pod 하나 삭제(재시작 조치와 같음), preStop 없음 | `demo-load` 요약으로 3번, 탐침으로 1번(1,885건) 모두 실패 0건 |
| `rollout restart`, preStop 없음 | `demo-load` 요약에 `failed` 7건(T15의 8~11건과 비슷함). 탐침은 2,119건 가운데 60건 실패: 59건이 10초 시간 초과(`ABORT_ERR`), 1건이 `ECONNREFUSED`. 대부분 롤아웃 중 3초 동안이고, 롤아웃이 끝난 뒤 약 30초 동안도 드문드문 있었음 |
| 롤아웃 뒤 평상시 | 끝난 지 1분쯤 뒤 탐침 1,866건 가운데 13건 실패(`ABORT_ERR`, `EHOSTUNREACH`). 2분쯤 뒤에는 1,881건 모두 성공 |
| 실패 원인(추정) | 연결 거부가 아니라 시간 초과가 대부분이라, 앱이 리스너를 닫은 것보다 Pod가 끝나 IP가 없어진 뒤에도 그 IP로 새 연결이 간 것으로 보임. 롤아웃 뒤 1~2분의 실패는 노드의 연결 추적(conntrack)에 남은 옛 Pod IP 기록 때문으로 추정함. 노드 안은 들여다보지 않아 확인하지 못함 |
| preStop 지원 | `kubectl explain pod.spec.containers.lifecycle.preStop.sleep`에 `seconds`(필수)가 있음 |
| preStop sleep 5초를 `kubectl patch`로 넣고 `rollout restart` | 탐침 4,689건(롤아웃 뒤 90초 포함) 모두 성공, `demo-load` 요약 `failed` 0건. 롤아웃은 4초 만에 끝나고 옛 Pod는 약 5초 동안 `Terminating` |
| 같은 설정에서 클러스터 안 서버에 `POST /api/actions`(restart-pod) | 200(25ms). 1초 뒤 같은 요청은 409 `target-terminating`(T21에서 클러스터로 보지 못한 경우). 약 5초 동안 판단 `terminated`(근거 `terminating`), SDK 연결됨, 그 뒤 `deleted`. 탐침 2,786건 모두 성공 |
| `kubectl apply`로 되돌리기 | `kubectl patch`로 더한 `lifecycle`은 `kubectl apply -f deploy/demo/demo-app.yaml`이 `unchanged`로 남겨 둠(apply는 자기가 적용한 적 없는 필드를 지우지 않음). `kubectl patch --type=json`의 `remove`로 지움. T15 '쓰는 법'의 `kubectl set env`는 매니페스트에 있는 `env`를 바꾸므로 apply로 되돌아감 |

## 쓰는 법

쿠버네티스 명령 전에 context를 확인합니다(`docker-desktop`이어야 함).

```bash
kubectl config current-context
```

매니페스트를 적용합니다. Pod 템플릿이 바뀌어 새 Pod가 뜹니다.

```bash
kubectl apply -f deploy/demo/demo-app.yaml
```

롤아웃 때 부하 실패가 없는지 봅니다. 요약은 10초마다 한 줄입니다.

```bash
kubectl -n glasspod-demo rollout restart deployment/demo-app
```

```bash
kubectl -n glasspod-demo logs deploy/demo-load --since=60s
```

- Pod를 지우면 약 5초 동안 `Terminating`으로 남고, 그동안 Glasspod 화면에는 '종료됨'이면서 SDK가 연결된 채로 보입니다. 그 뒤 앱이 SIGTERM을 받아 끝납니다.
- 다른 앱에 Glasspod를 붙일 때도 같은 이유로 preStop 지연을 권합니다(design.md 8장).
