# T16 서버 배포

- 우선순위: P0 · 단계 8 · 선행 작업: T12, T15
- 브랜치: `feat/t16-server-deploy`
- 작성: 2026-11-14

## 목표

Glasspod 서버를 로컬 클러스터의 `glasspod` namespace에 Deployment로 띄웁니다(design.md 4장, 5.2). 서버는 자기 ServiceAccount로 쿠버네티스 API를 부르고, 데모 앱의 SDK는 매니페스트에 이미 적힌 클러스터 안 주소로 붙습니다.

- 서버 컨테이너 이미지를 데모 앱(T15)과 같은 방식으로 만듭니다.
- 서버에 줄 권한을 감시 대상 namespace(`glasspod-demo`)에 한정된 Role로 둡니다(design.md 9장). ClusterRole은 쓰지 않습니다.
- 서버 코드는 바꾸지 않습니다. T12에서 만든 접속 설정 고르기(`GLASSPOD_KUBE_CONTEXT`가 없고 `KUBERNETES_SERVICE_HOST`가 있으면 클러스터 안)를 클러스터 안에서 처음 확인합니다.
- 노트북에서는 `kubectl port-forward`로 서버 API에 닿습니다(D4). 서버가 웹 화면을 제공하는 것은 T20입니다.

## 사전 확인

Docker Desktop 4.59.1(엔진 29.2.0), Kubernetes 1.34.1(context `docker-desktop`), `@kubernetes/client-node` 2.0.1에서 2026-11-14에 확인했습니다.

| 확인 | 결과 |
| --- | --- |
| client-node의 클러스터 안 설정 | `loadFromCluster()`가 `KUBERNETES_SERVICE_HOST`·`KUBERNETES_SERVICE_PORT`로 주소를 만들고(`https://10.96.0.1:443`), 마운트된 `ca.crt`로 검증하고, 토큰은 `tokenFile` 인증으로 붙임. 토큰 파일은 마지막으로 읽은 지 60초가 지나면 다시 읽음(`file_auth.js`). 그래서 ServiceAccount 토큰이 바뀌어도 그대로 씀 |
| 베이스 이미지 | 빌드 로그에 `load metadata`(1.4초)와 `resolve ... done`만 있고 내려받기 없음. 데모 앱 빌드의 캐시를 씀 |
| 이미지 | 압축 88.4MB(디스크 451MB). 데모 앱보다 큰 것은 `node_modules` 92MB 중 client-node 65MB. 사용자 uid 1000, Node 22.22.0, `dist/`에 테스트 파일 없음, `node_modules/.bin`은 client-node가 끌어온 `js-yaml`·`jsonpath`뿐(TypeScript·tsx 없음). `npm ci` 두 번 모두 `found 0 vulnerabilities` |
| 읽기 전용 파일 시스템 | `docker run --read-only --cap-drop ALL --security-opt no-new-privileges`로 `/health` 200, 없는 Pod의 snapshot 404, `kube watch disabled` 경고 한 줄, SIGTERM에 `shutting down`과 종료 코드 0. Pod 안에서 `/app`·`/tmp`에 쓰기는 `Read-only file system` |
| 시작 시간 | 컨테이너 시작에서 `server listening`까지 약 1초. `initialDelaySeconds` 없이는 첫 readiness가 그 전에 나가 시작할 때마다 `Readiness probe failed: ... connection refused` 경고가 한 줄 남음. 2초를 두니 경고 없이 시작 2초 뒤 Ready |
| 메모리 | 시작하고 SDK 3개가 붙은 뒤 cgroup `memory.current` 약 84MB, `memory.peak` 약 86MB. 프로세스 `VmRSS`는 약 128MB(공유하는 파일 페이지를 포함해 cgroup 값보다 큼) |

## 범위

### 포함

- `apps/server/Dockerfile`, 루트 스크립트 `npm run server:image`
- `deploy/server/`: namespace, `glasspod-demo`용 Role·RoleBinding, ServiceAccount·Deployment·Service
- 로컬 클러스터에서 배포, 권한, SDK 연결, port-forward 접속, 서버 다시 띄우기, Role이 없는 namespace 확인

### 제외

- 조치 권한과 조치 API(T21~T24)
- 서버가 웹 화면을 제공하는 것(T20). 이번에는 port-forward 뒤 웹 개발 서버로 확인함
- 접속 IP와 Pod IP 대조 구현(T25). 이번에는 로그로 보기만 함
- 서버의 기록 보관(T11), 상태 판단(T13), 조회 API(T14)
- 서버 로그 줄이기. 지금 서버는 SDK 메시지마다 `message received` 한 줄(T03)을 남겨 Pod 3개면 분당 약 36줄임(아래 '쓰는 법')

## 만들 파일

```text
package.json                  # (고침) server:image 스크립트

apps/server/
└─ Dockerfile                 # 다단계 빌드: 빌드 → 실행 의존성 → 실행 이미지

deploy/server/
├─ 00-namespace.yaml          # glasspod namespace(Pod Security Standards restricted)
├─ rbac-glasspod-demo.yaml    # glasspod-demo의 관찰 권한 Role과 RoleBinding
└─ server.yaml                # ServiceAccount, Deployment(1개, Recreate), Service
```

## 쓰는 법

쿠버네티스 명령 전에 context를 확인합니다(`docker-desktop`이어야 함).

```bash
kubectl config current-context
```

데모 앱을 먼저 배포합니다(권한을 만들 `glasspod-demo` namespace가 있어야 함). 이미 있으면 건너뜁니다.

```bash
kubectl apply -f deploy/demo/
```

서버 이미지를 만들고 배포합니다.

```bash
npm run server:image
```

```bash
kubectl apply -f deploy/server/
```

```bash
kubectl -n glasspod rollout status deployment/glasspod-server
```

서버 코드를 고쳐 이미지를 다시 만들었으면 새 Pod를 띄웁니다(태그가 같아 apply만으로는 바뀌지 않음). 예전 Pod가 먼저 끝나고(Recreate), SDK는 몇 초 안에 다시 붙습니다.

```bash
kubectl -n glasspod rollout restart deployment/glasspod-server
```

서버 로그를 봅니다.

```bash
kubectl -n glasspod logs deploy/glasspod-server -f
```

노트북에서 서버 API를 부릅니다. port-forward를 띄워 둔 채로 다른 터미널에서 씁니다.

```bash
kubectl -n glasspod port-forward service/glasspod-server 8080:8080
```

```bash
curl -s localhost:8080/api/pods/glasspod-demo/demo-app-7bbbcdc59b-62qcr/snapshot
```

웹 화면은 port-forward를 띄운 채로 `npm run dev:web`을 실행하고 `http://localhost:5173/pods/glasspod-demo/<Pod 이름>`을 엽니다. 노트북 서버(`npm run dev:server`)도 8080을 쓰므로 함께 띄우지 않습니다.

서버가 가진 권한을 확인합니다(관찰은 `yes`, 조치와 다른 namespace는 `no`).

```bash
kubectl auth can-i list pods -n glasspod-demo --as=system:serviceaccount:glasspod:glasspod-server
```

```bash
kubectl auth can-i delete pods -n glasspod-demo --as=system:serviceaccount:glasspod:glasspod-server
```

서버만 지웁니다. `00-namespace.yaml`까지 지정하면 namespace가 지워지므로 지정하지 않습니다. 권한도 지우려면 `rbac-glasspod-demo.yaml`을 함께 지정합니다.

```bash
kubectl delete -f deploy/server/server.yaml
```

- 다른 namespace도 보려면 `rbac-glasspod-demo.yaml`을 복사해 namespace만 바꾸고, `server.yaml`의 `GLASSPOD_NAMESPACES`에 쉼표로 더합니다. Role이 없으면 그 namespace만 `kube watch failed ... detail="http 403"`이 나고 다른 namespace는 그대로 봅니다.
- 노트북 서버로 개발할 때는 T15처럼 `kubectl -n glasspod-demo set env deployment/demo-app GLASSPOD_SERVER=ws://host.docker.internal:8080/agent`로 데모 앱을 옮기고, `kubectl apply -f deploy/demo/demo-app.yaml`로 되돌립니다. 클러스터 안 서버는 띄워 둔 채로 둬도 됩니다(둘 다 읽기만 함).
- 서버 로그는 SDK 메시지마다 한 줄이라 길어집니다. 앞부분만 볼 때는 `kubectl -n glasspod logs deploy/glasspod-server | grep -v 'message received'`처럼 거릅니다.

## 로그 형식

클러스터 안에서 시작하면 `source=in-cluster`와 API 서버 주소가 나옵니다. `remote`는 SDK Pod의 IP입니다(IPv4를 IPv6 모양으로 적은 `::ffff:` 접두어가 붙음).

```text
2026-11-14T06:24:02.058Z INFO  server listening port=8080 agentPath=/agent protocol=1 metricsIntervalMs=5000 maxEventsPerMinute=120 heartbeatIntervalMs=15000
2026-11-14T06:24:02.060Z INFO  kube watch starting source=in-cluster server=https://10.96.0.1:443 namespaces=glasspod-demo
2026-11-14T06:24:02.131Z INFO  kube watch synced resource=pods namespace=glasspod-demo count=4
2026-11-14T06:24:04.278Z INFO  hello accepted remote=::ffff:10.1.0.26 pod=glasspod-demo/demo-app-7bbbcdc59b-dj95x instance=e984e632-54f5-4c5a-adba-c2c0bf88aa75 sdk=node@0.0.0 protocol=1
```

Role이 없는 namespace를 `GLASSPOD_NAMESPACES`에 넣었을 때입니다. 자원마다 한 줄이고, 그 뒤 같은 오류는 남기지 않습니다(T12 결정 10).

```text
2026-11-14T06:23:30.271Z WARN  kube watch failed resource=pods namespace=default detail="http 403" retryInMs=1000
```

## 도구 버전

새로 설치한 npm 패키지는 없습니다. 이미지가 쓰는 의존성은 `package-lock.json` 그대로이고, 베이스 이미지는 T15와 같습니다(`node:22.22.0-bookworm-slim@sha256:dd9d2197…`).

- 만든 이미지 `glasspod-server:dev`는 압축 88.4MB(디스크 451MB)입니다.

| port-forward | `localhost:8080/health` 200, 데모 앱 Pod의 snapshot 200(`state`에 `app.mode: ready`), SDK가 없는 부하 Pod는 404 `not-connected` |
| 웹 개발 서버 | port-forward를 띄운 채 `npm run dev:web`, `/pods/glasspod-demo/<Pod>`에 snapshot `HTTP 200` |
| 서버 다시 띄우기(`rollout restart`) | 이벤트가 `Scaled down ... from 1 to 0` 다음에 `Scaled up ... from 0 to 1`(둘이 함께 뜨지 않음). 예전 Pod 로그 끝에 `shutting down signal=SIGTERM`, `shutdown timed out` 없음. SDK 3개가 같은 instance로 다시 `hello accepted`(예전 Pod 종료부터 약 5초) |
| Role이 없는 namespace(`kubectl set env ... GLASSPOD_NAMESPACES=glasspod-demo,default`) | `default`의 자원 4개만 `kube watch failed ... detail="http 403"`, `glasspod-demo`는 `synced`, SDK 연결과 `/health` 그대로. `kubectl apply -f deploy/server/`로 되돌림 |
| 1분 그대로 둠 | 서버 로그에 `message received` 말고 아무것도 없음(다시 붙기·WARN·ERROR 없음). 부하 요약 `failed=0` |
