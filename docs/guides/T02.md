# T02 프로토콜 v1 JSON Schema, 타입 생성, 메시지 검증

- 우선순위: P0 · 단계 2 · 선행 작업: T01 · 결정: D7
- 브랜치: `feat/t02-protocol-schema`
- 작성: 2026-11-08

## 목표

design.md 7장의 SDK–서버 메시지를 JSON Schema로 정의하고, 그 스키마에서 TypeScript 타입을 만듭니다. SDK와 서버가 받은 메시지를 같은 함수로 검증할 수 있게 `@glasspod/protocol`에 검증 함수를 둡니다.

## 결정 사항

1~3은 2026-11-08에 사용자가 추천안으로 정했습니다(D7). 4~8은 그에 따라 이 작업에서 정한 구현 방식입니다.

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | 타입 만드는 방식 (D7) | `packages/protocol/schema/*.schema.json`이 기준. json-schema-to-typescript로 `.ts` 타입을 만듦 | design.md 7.2 그대로. 다른 언어 SDK(Spring Boot)도 같은 파일을 씀. 생성 도구는 개발용이라 SDK 사용자에게 설치되지 않음 |
| 2 | 검증 라이브러리 | Ajv | JSON Schema 검증의 사실상 표준. 2026-04 버전 이후 안정적 |
| 3 | 생성한 파일 | 커밋함 | clone한 뒤 바로 typecheck, test, dev:server가 돌아감. 리뷰에서 타입 변화가 보임. 스키마와 어긋나면 테스트가 실패함 |
| 4 | 스키마 문법 | JSON Schema draft-07 | 생성 도구, Ajv, Java 쪽 생성 도구가 모두 지원하는 가장 넓은 버전 |
| 5 | 스키마 파일 | 받는 쪽 기준으로 나눔: `sdk-message`(SDK → 서버), `server-message`(서버 → SDK), `snapshot`(snapshot 응답의 `data`) | 파일 하나가 검증 함수 하나와 맞음. 생성 도구는 루트가 `oneOf`이면 가리키지 않는 정의를 만들지 않으므로 snapshot을 따로 뺌 |
| 6 | 모르는 필드 | 스키마에 `additionalProperties: false`를 쓰지 않음. 생성할 때만 `additionalProperties: false` 옵션을 줘서 타입에는 아는 필드만 둠 | 받는 쪽은 모르는 필드를 무시함(design.md 7.2). 필드를 추가해도 예전 쪽이 거부하지 않음 |
| 7 | 메시지 종류 구분 | 루트 `oneOf`에 Ajv `discriminator`(`type` 필드)를 씀 | 오류가 해당 메시지 하나에 대해서만 나와 읽기 쉬움. 표준 키워드가 아니지만 다른 검증기는 모르는 키워드를 무시함 |
| 8 | 검증 시점 | 스키마 컴파일은 처음 검증할 때 한 번 | SDK를 불러오는 것만으로 앱 시작이 느려지지 않게 함 |

검토한 다른 방식:

- TypeBox(스키마를 TS 코드로 작성): 생성 단계가 없지만 기준이 TS 코드로 바뀌어 design.md 7.2와 맞지 않음. 1.x는 최근 릴리스가 잦음
- json-schema-to-ts(스키마 객체에서 타입 추론): 2024-08 이후 릴리스가 없음

## 범위

### 포함

- 스키마 3개(`schema/`)와 생성 스크립트(`scripts/`), 생성한 파일(`src/generated/`)
- 검증 함수 `parseSdkMessage`, `parseServerMessage`와 결과 타입 `ParseResult`
- 단위 테스트: design.md 7.3 예시 통과, 모르는 필드 무시, 잘못된 메시지 거부, 생성한 파일이 스키마와 같은지 확인
- `npm run generate`(루트), `scripts/`의 타입 검사(`tsc -b`에 포함)

### 제외

- 서버와 SDK에서 검증 함수를 쓰는 일 (T03, T04)
- snapshot `data` 검증 함수 (T09). 스키마와 타입만 만듦
- Java 타입 생성 (T31)
- 프로토콜 버전 협상. `protocol` 값이 서버가 아는 버전인지 보는 일은 서버(T03)가 함

## 만들 파일

```text
packages/protocol/
├─ schema/
│  ├─ sdk-message.schema.json      # SDK → 서버: hello, metrics, event, response
│  ├─ server-message.schema.json   # 서버 → SDK: welcome, reject, request
│  └─ snapshot.schema.json         # snapshot 응답의 data
├─ scripts/
│  ├─ codegen.ts                   # 스키마에서 파일 내용을 만드는 코드
│  ├─ codegen.test.ts              # 커밋된 생성 파일이 스키마와 같은지 확인
│  ├─ generate.ts                  # npm run generate가 실행. src/generated/에 씀
│  └─ tsconfig.json                # scripts/ 타입 검사(noEmit). 루트 tsconfig.json이 참조
└─ src/
   ├─ generated/                   # 생성한 파일. 직접 고치지 않음. 커밋함
   │  ├─ sdk-message.ts, server-message.ts, snapshot.ts   # 타입
   │  └─ schemas.ts                # 검증에 쓰는 스키마 객체
   ├─ validate.ts                  # parseSdkMessage, parseServerMessage
   ├─ validate.test.ts
   └─ index.ts                     # 타입, 검증 함수, PROTOCOL_VERSION을 내보냄
```

- 스키마 객체를 `.json` import로 읽지 않고 `schemas.ts`로 만들어 둡니다. `schema/`가 `src/` 밖이라 `tsc`의 `rootDir`을 벗어나고, JSON import는 Node와 번들러마다 설정이 다르기 때문입니다.
- `generate.ts`는 이번에 만들지 않는 파일을 `src/generated/`에서 지웁니다. 스키마를 없애도 예전 결과물이 남지 않게 하려는 것입니다.

## 필드 규칙

design.md 7.3의 예시에 없던 규칙은 이 작업에서 정했습니다(표의 '정한 것'). 바꿀 때는 스키마를 먼저 고칩니다.

| 메시지 | 필수 | 선택 | 정한 것 |
| --- | --- | --- | --- |
| 공통 (SDK → 서버) | `type`, `seq`(0 이상 정수), `ts`(0 이상 정수, epoch ms) | | `seq`는 보낸 순서, `ts`는 보낸 시각. event의 `ts`만 일어난 시각(T06, T08에서 설명을 고침) |
| hello | `protocol`(1 이상), `sdk.lang`, `sdk.version`, `pod.namespace`, `pod.name`, `instanceId` | `app`(`name` 필수, `version` 선택), `capabilities` | `app`과 `capabilities`는 선택. `sdk.lang`과 `capabilities`는 정해진 값 목록 없이 문자열 |
| metrics | `values`(빈 배열 허용) | | 이름은 `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`: 소문자·숫자·`_`, 두 단계 이상. 접두어(`runtime`, `http`, `app`)는 검사하지 않음 |
| metrics 값 | `name`, `kind`(`gauge`·`counter`), `value`(수) | | |
| event | `level`, `name`, `count`(1 이상) | `message`, `data`(객체) | `level`은 `info`·`warn`·`error`. `count`는 필수 |
| response | `replyTo`, `ok` | `data`(객체), `error` | `ok`가 `false`면 `error` 필수 |
| welcome | `metricsIntervalMs`(1 이상), `maxEventsPerMinute`(0 이상) | `heartbeatIntervalMs`(1 이상) | 두 값 모두 필수. `heartbeatIntervalMs`는 T08에서 더함. 없으면 heartbeat를 보내지 않는 서버 |
| reject | `reason` | | 정해진 값 목록 없이 문자열(예: `unknown-pod`) |
| request | `id`, `action` | | `action`은 정해진 값 목록 없이 문자열. 모르는 action이 와도 검증은 통과하고 SDK가 `ok: false`로 답함 |
| heartbeat | | | T08에서 더함. `type` 말고 필드가 없음. SDK는 답하지 않음 |
| snapshot data | `state`(값이 문자열인 객체), `inFlight`(`route`, `elapsedMs`), `process`(`uptimeSec`, `heapUsedBytes`) | | 모두 필수 |

값 목록을 정하지 않은 문자열(`action`, `reason`, `capabilities`, `sdk.lang`)은 새 값이 생겨도 예전 쪽 검증이 실패하지 않게 하려는 것입니다. 반대로 `kind`와 `level`은 값 목록이 있으므로, 새 값을 넣으면 의미가 바뀌는 것으로 보고 `protocol` 번호를 올립니다.

## 쓰는 법

```ts
import { parseSdkMessage } from "@glasspod/protocol";

const result = parseSdkMessage(text); // WebSocket 텍스트 프레임 하나
if (!result.ok) {
  // result.error 예: "message/pod must have required property 'name'", "unknown message type: \"ping\""
} else if (result.message.type === "hello") {
  result.message.pod.name; // HelloMessage로 좁혀짐
}
```

스키마를 바꿀 때:

1. `packages/protocol/schema/`의 스키마를 고칩니다.
2. 루트에서 `npm run generate`를 실행합니다.
3. `docs/design.md` 7장을 함께 고칩니다.
4. 필드를 없애거나 의미를 바꿨으면 `PROTOCOL_VERSION`(`src/index.ts`)을 올립니다.

| 명령 | 기대 결과 |

| `node`로 `dist/` 불러오기 | 소스 참조 조건 없이 `@glasspod/protocol`을 불러와 검증 함수가 동작함 |
