# T13 상태 판단

- 우선순위: P0 · 단계 7 · 선행 작업: T11, T12
- 브랜치: `feat/t13-pod-status`
- 작성: 2026-11-14

## 목표

서버가 SDK 신호(T11의 지금 상태)와 쿠버네티스 Pod 상태(T12의 요약)를 합쳐 Pod마다 상태를 판단합니다(design.md 7.5). T14 조회 API와 SSE, T18 목록 화면의 강조, T28 자동 규칙이 이 판단을 씁니다.

- 판단은 순수 함수(`judgePod`)로 만들고 design.md 7.5 표를 단위 테스트로 확인합니다.
- 서버는 1초마다 모든 Pod를 판단해 들고 있고, 바뀌면 로그에 한 줄 남깁니다. 조회 API는 T14에서 만듭니다.
- 컨테이너가 재시작되면 직전 instance의 event를 원인 후보로 찾습니다.
- 쿠버네티스에서 지워진 Pod의 SDK 연결이 남아 있으면 서버가 닫습니다(T08에서 넘김).

## 결정 사항

1~4는 2026-11-14에 사용자가 정했습니다(착수 전에 보고한 질문 4개). 5~18은 이 작업의 기본값입니다.

### 판단 표

위가 먼저입니다. '강조'는 화면이 쓰는 수준(`PodSeverity`)입니다.

| 판단(`status`) | 이름 | 조건 | 근거(`reason`) | 강조 |
| --- | --- | --- | --- | --- |
| `terminated` | 종료됨 | Pod가 종료 중(`terminating`), 또는 쿠버네티스에서 지워짐(SDK 상태의 `deletedAt`이 있고 쿠버네티스에 없음), 또는 phase `Succeeded` | `terminating`, `deleted`, `Succeeded` | `none` |
| `pod-failing` | Pod 이상 | phase `Failed`, 또는 시작 중이 아닌 waiting 이유(결정 12) | phase 또는 waiting 이유 | `critical` |
| `stalled` | 앱 멈춤 의심 | SDK 연결이 열려 있는데 metrics가 3주기 동안 없음(결정 6) | `no-metrics` | `critical` |
| `disconnected` | 연결 끊김 | SDK 연결이 끊겼고 Pod가 시작 중이 아님(SDK 연결 문제 또는 앱 멈춤) | | `critical` |
| `restarted` | 재시작 | 30분 안에 재시작(결정 7) | 쿠버네티스 종료 이유(있으면) | `warning` |
| `not-ready` | 준비 안 됨 | SDK 연결이 정상이고 Pod가 Ready가 아님 | | `warning` |
| `starting` | 시작 중 | SDK 상태가 없거나 끊겼고, Pod가 Pending이거나 waiting 이유가 `ContainerCreating`·`PodInitializing` | phase 또는 waiting 이유 | `none` |
| `no-sdk` | SDK 없음 | Pod는 있는데 SDK 상태가 없음 | | `none` |
| `ok` | 정상 | SDK 연결이 정상이고 Pod가 Running·Ready(또는 쿠버네티스에 없음) | | `none` |

- 7.5 표와 맞추면: 정상 → `ok`, 연결은 열렸는데 metrics 없음 → `stalled`, 연결 끊김 + Running → `disconnected`, 연결 끊김 + 종료 중이거나 없음 → `terminated`, 새 instance + 재시작 횟수 증가 → `restarted`.
- 서버가 다시 시작된 직후에는 SDK가 다시 붙기 전까지(보통 1~2초) `no-sdk`입니다.
- 크래시 뒤에는 새 컨테이너의 SDK가 붙기 전까지 잠깐 `disconnected`가 나옵니다(쿠버네티스는 Running 그대로). 끊김과 다시 붙음이 1초 판단 주기 안에 끝나면 나오지 않습니다(OOMKilled 확인 때).
- 새 Pod는 SDK가 readiness(5초 주기)보다 먼저 붙어 1~2초 `not-ready`가 나올 수 있습니다(2026-11-14 노트북 서버에서 확인, 클러스터 안 서버에서는 판단 주기 사이에 끝나 안 보임). 화면이나 자동 규칙에서 짧은 것을 걸러야 하면 그쪽에서 지속 시간으로 거릅니다.
- SDK 신원 확인(T25) 전에는 다른 프로세스가 같은 Pod 이름으로 붙으면 새 instance라 `restarted`로 보입니다.
- 이벤트 루프가 막히면 readiness(5초·2번)가 먼저 실패해 `not-ready`가 되고, 15초가 지나면 `stalled`가 됩니다. 풀리면 readiness가 다시 통과할 때까지 `not-ready`입니다.

## 범위

### 포함

- 판단 함수와 원인 후보 고르기(`status.ts`), 1초마다 판단하고 로그를 남기는 `StatusMonitor`(`status-monitor.ts`)
- 지금 상태에 판단이 쓸 값 더하기(`pods.ts`): `previousInstanceId`, `instanceSince`, `deletedAt`
- 지워진 Pod의 연결 닫기(`agents.ts`, `agent.ts`, `index.ts`)
- 판단 코드 타입(`packages/protocol/src/http.ts`)
- 단위 테스트

### 제외

- 지표로 하는 판단(결정 1). TODO에 새 작업으로 제안
- 조회 API와 SSE(T14), 화면(T18·T19)
- 자동 규칙(T28)
- SDK 신원 확인(T25). 지금은 `hello`의 Pod 이름을 그대로 믿음
- SDK·프로토콜 메시지 변경. 이 작업은 서버와 HTTP 타입만 고침

## 쓰는 법

설정은 늘지 않습니다. 판단은 서버가 시작되면 1초마다 돌고, 결과는 로그로 봅니다.

```bash
GLASSPOD_KUBE_CONTEXT=docker-desktop npm run dev:server
```

클러스터의 데모 앱을 노트북 서버에 붙이고 되돌리는 법은 `docs/guides/T15.md` '쓰는 법'에 있습니다.

```bash
kubectl -n glasspod-demo set env deployment/demo-app GLASSPOD_SERVER=ws://host.docker.internal:8080/agent
```

```bash
kubectl apply -f deploy/demo/demo-app.yaml
```

- `previous`는 바로 앞 판단입니다. 서버가 처음 판단한 Pod는 없습니다. 판단은 같고 근거나 재시작 정보만 바뀌면 `previous`가 `status`와 같습니다.
- `silentMs`는 `stalled`일 때만, `restart*`·`exitCode`·`previousInstance`는 30분 안의 재시작이 있을 때만 붙습니다.
- `restart cause`는 직전 instance마다 한 번, 원인 후보 하나에 한 줄이고 `at`은 일어난 시각, `message`는 200자까지입니다. 이어서 `restart causes`(후보 수)가 한 줄 나옵니다.
- 재시작의 두 신호는 따로 30분이 지나므로, 끝날 때 재시작 정보만 바뀐 줄(`previous=restarted`)이 먼저 나오고 곧 `ok`가 될 수 있습니다.
