# T28 자동 규칙(알림만 → 자동)

- 우선순위: P2 · 선행 작업: T26 · 결정: D5(2026-11-26), 아래 결정 1~4는 착수 전 사용자 결정
- 브랜치: `feat/t28-auto-rules`
- 작성: 2026-11-27

## 목표

같은 일이 반복되면 규칙으로 등록하고, 처음에는 '알림만'으로 받다가 판단이 맞는 것을 본 뒤 '자동'으로 바꿉니다(design.md 6장 6단계, 5.5).

- 규칙은 YAML로 적어 서버 매니페스트의 ConfigMap(`deploy/server/rules.yaml`)에 두고 `kubectl apply`로 바꿉니다(D5). 서버는 다시 시작하지 않고 바뀐 규칙을 씁니다.
- 서버는 판단 주기(1초)마다 규칙의 조건(판단, 다른 Pod보다 높은 값, 지표 임계)을 Pod마다 보고, 지속 시간을 채우면 '알림만'은 기록만, '자동'은 조치(재시작, 트래픽에서 빼기, 스케일)를 실행합니다.
- 화면은 규칙과 그 기록을 보여 주기만 합니다(고치지 않음). 왼쪽 메뉴 '자동 규칙' 화면과 한눈에 보기 타임라인, Pod 상세 '무슨 일이 있었나'에 규칙 줄이 들어갑니다.

## 결정 사항

1~4는 2026-11-27에 사용자가 정했습니다(착수 전에 보고한 질문 4개, 모두 추천안). D5(2026-11-26)는 문법의 큰 틀(ConfigMap YAML, 모드는 파일에, 정해진 칸·AND, 신호 3종, JSON Schema 검증)입니다. 5~27은 이 작업의 기본값입니다.

확인 중 고친 것:

- 규칙 파일이 틀리면 Ajv가 첫 오류만 보여 오타(`cooldwon`)가 '빠진 cooldown'으로만 보임 → 규칙 검증은 `allErrors`를 켠 따로 Ajv를 쓰고, 문구를 '경로 + 내용'으로 다듬음(모르는 필드는 이름, enum은 받는 값, 조건·조치가 어느 갈래에도 맞지 않으면 한 줄 설명, 갈래 안 값이 틀리면 그 값). 결정 8 보충
- 조건을 곧 채우는 Pod가 '0초 뒤 발동'으로 보임 → 남은 시간을 초 단위로 올림
- 격리된 Pod 화면 안내 '상세에서 트래픽에서 빼기를 실행하면' → '실행하거나 자동 규칙이 빼면'

지침서와 다른 점:

- 웹에 `apps/web/src/rules/RuleParts.tsx`(모드·결과 배지, 기록의 대상 칸)를 더함. 규칙 화면과 한눈에 보기 타임라인이 함께 씀
- 규칙 검증 오류 문구는 위 '확인 중 고친 것'

## 범위

### 포함

- `packages/protocol`: 규칙 스키마와 생성 타입, `validateRulesFile`, HTTP 본문(`RuleItem`, `RuleFiring`, `RulesBody`, SSE `changes`, 상세 `ruleFirings`, `PodIsolation.outliers`)
- `apps/server`: 규칙 파일 읽기, 규칙 엔진, 저장소의 규칙 기록, `GET /api/rules`, SSE, 상세, 격리 주석, 환경변수 `GLASSPOD_RULES_FILE`, 로그, 단위 테스트
- `apps/web`: '자동 규칙' 화면, 타임라인·'무슨 일이 있었나' 규칙 줄, 격리된 Pod 카드의 강조 이름, 단위 테스트
- `deploy/server/`: `rules.yaml`(ConfigMap), `server.yaml`(볼륨과 환경변수)

### 제외

- 화면에서 규칙 고치기, 모드 바꾸기(D5)
- OR 조건, Deployment 전체 값(평균·합) 조건(조건은 Pod마다)
- 규칙의 알림 보내기(메일·Slack), 규칙 상태를 서버 재시작 뒤에도 남기기(D1 메모리)
- 지표 비교 강조의 켜짐·꺼짐을 타임라인에 남기기(T34 결정 14 그대로)
- 전체 재시작·롤백을 규칙 조치로(T29)

## 알려진 한계

- `kubectl apply` 뒤 kubelet이 볼륨 파일을 바꾸기까지 보통 1분 안팎(시각을 잰 5번은 3~61초) 걸립니다(결정 1). 화면의 '받아들임' 시각으로 확인합니다.
- 조건은 Pod마다입니다. '모든 Pod의 큐가 길면 늘림'은 쓸 수 없고 '한 Pod라도 길면'입니다(스케일 규칙에서 주의).
- 규칙 상태(조건 시각, 쉬는 시간, 시간당 횟수)와 기록은 서버 메모리라 서버를 다시 시작하면 사라집니다. 조건 시간을 처음부터 다시 세므로 시작하자마자 실행하지는 않지만, 쉬는 시간도 사라집니다.
- 넓은 영향 막기 ②는 원하는 replica 수가 1인 Deployment에서 Pod 조치를 하지 않습니다(유일한 Pod를 빼면 끊김).
