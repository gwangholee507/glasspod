# T08 SDK 끊김 처리

- 우선순위: P1 · 단계 6 · 선행 작업: T05, T06
- 브랜치: `feat/t08-sdk-disconnect`
- 작성: 2026-11-12

## 목표

서버와의 연결이 끊기거나 아직 붙지 않았을 때도 SDK가 모은 것을 잃지 않게 합니다(design.md 7.4).

- event: 연결이 없는 동안 보낼 차례가 된 event를 500개까지 들고 있다가, 다시 연결되면 원래 `ts` 그대로 보냅니다. `start()` 바로 뒤, 첫 `welcome` 전에 일어난 event도 같습니다(T06에서 넘긴 일).
- metrics: 측정은 연결과 상관없이 이어 가고, 다시 연결되면 바로 한 건 보냅니다. 끊긴 동안의 막힘과 느려짐이 그 한 건에 남습니다.
- 응답 없는 연결(반쯤 열린 연결): 서버가 주기마다 `heartbeat`를 보내고, SDK는 서버 메시지가 한동안 없으면 끊고 다시 붙습니다(T04에서 넘긴 일).
- `seq`와 `ts`: `seq`는 보낸 순서, event의 `ts`는 일어난 시각이라는 것을 스키마 설명에 적습니다(T06에서 넘긴 일).

## 결정 사항

1~4는 2026-11-12에 사용자가 정했습니다. 5~18은 이 작업의 기본값입니다.

| --- | --- | --- | --- |
| 1 | 보관한 event와 1분 한도 | 다시 연결되면 보관한 것을 오래된 것부터 원래 `ts`로 보내되 `maxEventsPerMinute` 안에서만 보냄. 남은 것은 한도가 풀리면 보냄 | 사용자 결정. 서버가 재시작돼도 모든 Pod가 한도를 넘겨 한꺼번에 몰려 보내지 않음 |

| 6 | 보관하는 때 | `start()`가 연결을 만든 뒤부터 `stop()`까지, 연결(`welcome`)이 없으면 보관함. `start()` 전, SDK가 꺼졌을 때, `stop()` 뒤에는 지금처럼 버림 | `start()`를 부르지 않는 앱이 500개를 계속 들고 있지 않게 함. 상태 값은 지금처럼 늘 기억함 |
| 7 | 보관 중 묶기 | 연결이 없어도 T06 묶기 규칙(첫 건 바로, 10초 창, 서로 다른 이벤트 100개)을 그대로 씀. 보낼 차례가 된 것(첫 건, 창 끝의 묶음)이 보관함으로 감 | 같은 예외가 쏟아져도 보관함은 이벤트마다 10초에 한 건씩만 늘어남. 일어난 순서와 시각이 남음 |
| 8 | 보관함이 넘칠 때 | 500개가 차면 가장 오래된 것을 버림. 끊긴 동안 처음 한 번 경고 한 줄 | design.md 7.4. 최근 일이 원인 찾기에 더 쓸모 있음 |
| 9 | 다시 연결된 뒤 | `welcome`을 받자마자 보관분을 오래된 것부터 한도 안에서 보내고, 남은 것은 1초마다 다시 시도함. 보관분을 다 보낼 때까지 새 event는 보내지 않고 묶음에서 셈(T06의 한도 규칙과 같음). 새 서버의 한도가 `0`이면 보관분을 버림 | 결정 1. 보내는 순서가 일어난 순서와 같음 |
| 10 | 처리되지 않은 예외 | 연결돼 있으면 그 예외를 먼저 보내고, 보관분, 세던 묶음 순서로 한도와 상관없이 보냄. 연결이 없으면 보내지 못함 | T06 결정 10을 넓힘. 가장 중요한 것이 소켓 버퍼에 먼저 들어감. 프로세스가 끝나므로 보관해도 소용없음 |
| 11 | `stop()` | 보관분과 세던 묶음을 버림 | T06과 같음. `stop()` 뒤에는 보낼 연결이 없음 |
| 12 | 메모리 | event 하나가 `message` 1000자 + `data` 8192자 상한이므로 500개는 최악의 경우 약 5MB(영문 기준, 한글 등은 약 2배). 보통 event는 수백 바이트 | SDK 원칙 '메모리 사용에 상한' |
| 13 | heartbeat 메시지 | 서버 → SDK `{ "type": "heartbeat" }`. `welcome`에 선택 필드 `heartbeatIntervalMs`(1 이상 정수)를 더함. 프로토콜 번호는 그대로 | 메시지 종류와 선택 필드를 더하는 것은 하위 호환. 예전 SDK는 모르는 종류라 무시하고, 새 SDK는 `heartbeatIntervalMs`가 없는 `welcome`을 받으면 감지하지 않음 |
| 14 | 서버 설정 | 환경변수 `GLASSPOD_HEARTBEAT_INTERVAL_MS`(기본 15000, 1000~2147483647). 잘못된 값이면 시작 실패. `welcome`을 보낸 뒤부터 연결마다 보내고 연결이 끝나면 멈춤 | 서버의 다른 설정과 같음. 하한은 서버가 모든 앱을 heartbeat로 바쁘게 만들지 않게, 상한은 Node 타이머 상한 |
| 15 | SDK의 판단 | `welcome` 뒤 서버 메시지(종류와 상관없이 무엇이든)가 마지막으로 온 때부터 `3 × max(heartbeatIntervalMs, 1000)`ms가 지나면 끊고 재연결 간격대로 다시 붙음. 1초마다 확인함 | 한두 번 늦는 것은 넘김. 하한은 metrics 주기 하한과 같음 |
| 16 | 이벤트 루프가 막혔다 풀린 직후 | 확인 타이머가 1초 넘게 늦게 깨어나면 그 확인은 건너뜀 | 막힌 동안 도착한 메시지가 아직 처리되지 않았을 수 있음(아래 '사전 확인'). 앱이 막힌 것을 연결이 죽은 것으로 보지 않음 |
| 17 | 서버 쪽 감지 | 이번에는 하지 않음. 서버는 SDK의 응답을 기다리지 않고, 응답이 없다고 연결을 닫지 않음 | 앱의 이벤트 루프가 막히면 SDK가 답하지 못함. 서버가 닫아 버리면 design.md 7.5의 '연결은 열려 있는데 metrics가 3주기째 없음(앱 멈춤 의심)'을 구분할 수 없음. 서버의 판단은 T13 |
| 18 | 앱 보호 | 새 타이머(heartbeat 확인)는 `unref()`하고 콜백은 `guard`로 감쌈. 공개 함수는 예외를 던지지 않음 | SDK 원칙 |

### 사전 확인

Node 22.22.0(undici 6.23.0), macOS, 같은 컴퓨터의 `ws` 8.22.0 서버로 2026-11-12에 확인했습니다. 서버 프로세스를 `SIGSTOP`으로 멈춰 응답 없는 연결을 흉내 냈습니다(운영체제는 TCP에 계속 답함).

| 확인 | 결과 |
| --- | --- |
| 멈춘 서버로 `send()` | 계속 성공하고 `readyState`는 1(OPEN). `close`·`error` 이벤트가 없음. `bufferedAmount`도 늘지 않아 단서가 되지 않음 |
| 그 상태에서 `close()` | `readyState`가 2(CLOSING)에 머물고 `close` 이벤트가 오지 않음. 서버가 다시 돌자(`SIGCONT`) 바로 `close`(1005). 그동안 이 소켓이 이벤트 루프를 붙잡아 프로세스가 끝나지 않음 |
| 멈춘 서버에 새 연결 | TCP는 붙지만 `open`도 `error`도 오지 않음. SDK의 열림 제한 시간(10초)이 끊음 |
| 이벤트 루프 3초 막힘(서버는 0.5초마다 보냄) | 막힌 동안 도착한 메시지 6개가 1초 확인 타이머보다 먼저 처리됨. 타이머는 2208ms 늦게 깨어남. 막힌 곳이 타이머 콜백인지 I/O 콜백인지에 따라 순서가 바뀔 수 있어 결정 16으로 막음 |

- 끊은 소켓이 CLOSING에 머무는 동안(실제 반쯤 열린 연결이면 운영체제가 끊을 때까지, 리눅스 기본 약 15분) 그 소켓이 이벤트 루프를 붙잡습니다. 그동안 `stop()`을 부르고 이벤트 루프가 비기를 기다려 끝나는 앱은 끝나지 않습니다(쿠버네티스는 유예 시간 뒤 SIGKILL). 내장 WebSocket에는 소켓을 바로 끊는 API가 없습니다.

## 보관과 보내기

```text
서버가 0~20초 동안 꺼져 있고, 한도(maxEventsPerMinute)가 3일 때

 0초  start(), state("app.mode", "ready")    -> 보관 [ready]
 2초  예외 A 첫 건                           -> 보관 [ready, A×1]
 3~9초 예외 A 7번                            -> 묶음에서 셈
12초  A의 창 끝                              -> 보관 [ready, A×1, A×7]
14초  예외 B 첫 건                           -> 보관 [ready, A×1, A×7, B×1]
20초  welcome                                -> ready, A×1, A×7 을 보냄(한도 3). B×1은 남음
21초  예외 B                                 -> 보관분이 남아 있어 묶음에서 셈
80초  한도가 풀림                            -> B×1(ts=14초), 그 뒤 창이 끝난 B 묶음
```

- 보관한 event의 `ts`는 일어난 시각이고, `seq`는 보낸 때 붙습니다. 그래서 다시 연결한 뒤의 event는 `ts`가 그 연결의 `hello`보다 이를 수 있습니다.
- metrics는 `welcome`을 받자마자 한 건 나갑니다. 그 값은 지난 metrics 뒤(첫 연결이면 `start()` 뒤)의 이벤트 루프 지연, 사용률, HTTP 응답 시간을 덮습니다.

## 범위

### 포함

- 프로토콜: `heartbeat` 메시지, `welcome`의 `heartbeatIntervalMs`, `Seq`·`Timestamp` 설명(스키마, 생성한 타입, 검증 테스트)
- 서버: `GLASSPOD_HEARTBEAT_INTERVAL_MS`, `welcome`에 넣기, 연결마다 주기 전송
- SDK event: 보관함(500개), 다시 연결된 뒤 한도 안에서 보내기, 처리되지 않은 예외 때 보관분도 보내기(`events.ts`)와 단위 테스트
- SDK 연결: 서버 메시지가 끊겼는지 판단(`liveness.ts`)과 단위 테스트, 연결 관리에 붙이기(`connection.ts`)
- SDK metrics: 측정은 `start()`부터, `welcome` 직후 바로 한 건(`metrics.ts`)

### 제외

- 서버 쪽 응답 없는 SDK 연결 감지와 상태 판단(T13)
- 서버의 `seq` 누락·중복 판단과 보관(T11)
- ack와 재전송 보장(결정 2)
- 끊은 소켓을 바로 닫는 일(내장 WebSocket에 API 없음, '사전 확인')
- 데모 앱(T10). 실제 동작은 저장소에 넣지 않는 확인 스크립트로 확인함

## 쓰는 법

앱 코드는 바뀌지 않습니다. 서버를 띄우기 전에 앱을 먼저 띄워도 됩니다.

```ts
import { glasspod } from "@glasspod/sdk";

glasspod.start({ app: { name: "orders" } });
// 아직 연결 전이지만 보관했다가 welcome 뒤에 보냅니다(T06에서는 버렸음).
glasspod.state("app.mode", "ready");
```

서버가 보내는 메시지의 예입니다.

```json
{ "type": "welcome", "metricsIntervalMs": 5000, "maxEventsPerMinute": 120, "heartbeatIntervalMs": 15000 }
```

```json
{ "type": "heartbeat" }
```

## 로그 형식

SDK가 표준 오류에 남기는 줄입니다. 연결이 끊긴 때와 복구된 때의 경고는 T04 그대로입니다.

```text
[glasspod] event buffer full (500 events while disconnected); dropping the oldest
[glasspod] connection lost (no message from server within 45000ms); reconnecting
```

`NODE_DEBUG=glasspod`이면 다음이 더 나옵니다.

```text
GLASSPOD 57390: welcome metricsIntervalMs=5000 maxEventsPerMinute=120 heartbeatIntervalMs=15000
GLASSPOD 57390: event held (not connected) name=state held=1
GLASSPOD 57390: event dropped (buffer full) name=exception count=1
GLASSPOD 57390: sending held events held=12
GLASSPOD 57390: held event sent seq=5 name=state count=1
GLASSPOD 57390: held events dropped (limit 0) held=12
GLASSPOD 57390: heartbeat received
GLASSPOD 57390: heartbeat check skipped (timer was 2208ms late)
GLASSPOD 57390: metrics sent seq=6 values=13
```

서버의 시작 로그에 `heartbeatIntervalMs=15000`이 더해집니다.

## 완료 기준

실제 동작은 저장소에 넣지 않는 확인 스크립트로 확인했습니다(76개 항목). 스크립트는 SDK를 소스 참조 조건(`@glasspod/source`)과 tsx로 불러오는 작은 앱을 띄우고, 실제 서버(`apps/server/src/index.ts`)와 `ws`로 만든 가짜 서버(받은 메시지를 모두 기록하고 `parseSdkMessage`로 검증, `welcome` 값과 heartbeat를 바꿀 수 있음)에 붙여 봅니다. 서버를 늦게 띄우거나, 끄고 다시 띄우거나, `SIGSTOP`으로 멈춰 봅니다.

| `npm test` | 모든 테스트 통과. 보관·넘침·한도 안에서 보내기, heartbeat 판단, metrics 바로 보내기 테스트 포함. 생성한 타입이 스키마와 같음 |
| `npm run format:check` | `All matched files use Prettier code style!` |
| 실제 서버 | 시작 로그에 `heartbeatIntervalMs`. SDK 디버그 로그에 `heartbeat received`가 주기마다. 서버 로그에 `message ignored` 없음 |
| 서버 설정 | `GLASSPOD_HEARTBEAT_INTERVAL_MS`가 999나 숫자가 아니면 서버가 시작하지 않음 |
| `start()` 바로 뒤의 `state()` | `welcome` 뒤에 도착. `ts`는 `welcome` 전 |
| 서버를 늦게 띄움 | 서버가 없는 동안 일어난 event가 일어난 순서대로, 원래 `ts`로 도착. `seq`는 `hello` 다음부터 이어짐 |
| 서버를 끄고 다시 띄움 | 끊긴 동안의 event가 도착. 끊기기 전과 뒤의 `seq`가 이어짐(`hello` 하나 포함) |
| 보관함 넘침 | 끊긴 동안 보관할 event가 500개를 넘으면 가장 최근 500개만 도착. 경고 한 줄 |
| 한도 안에서 보내기(`maxEventsPerMinute` 5, 보관 8개) | 다시 연결 직후 5개, 약 60초 뒤 나머지. 그동안 새 event는 묶임 |
| 새 서버의 한도 0 | 보관분이 도착하지 않음 |
| 보관분이 남은 채 처리되지 않은 예외 | 그 예외가 먼저, 이어 보관분 도착. 오류 출력과 종료 코드(1)가 SDK 없는 같은 앱과 같음 |
| metrics | `welcome` 직후 바로 한 건, 그 뒤 한 주기마다. 끊긴 동안 앱을 2초 막으면 다시 연결 직후 metrics의 `lag_max_ms`가 약 2000(20ms 측정 간격 안에서 막힘이 시작되므로 1980~2000). 끊긴 동안 끝난 HTTP 요청의 응답 시간이 다시 연결 직후 metrics에 들어감 |
| 서버를 `SIGSTOP` | heartbeat 3배 시간 안에 `connection lost (no message from server within ...)`. `SIGCONT` 뒤 다시 붙고 멈춘 동안의 event가 도착 |
| 앱 이벤트 루프를 heartbeat 3배보다 오래 막음 | 연결을 끊지 않음 |
| `heartbeatIntervalMs` 없는 `welcome`(가짜 서버) | 서버 메시지가 오래 없어도 끊지 않음 |
| SDK가 꺼짐, `stop()` 뒤 | event를 보관하지 않음. 측정 타이머가 돌지 않음. 서버가 없을 때 앱이 스스로 끝남 |
| 위 모든 경우 | SDK 때문에 생긴 처리되지 않은 예외 없음 |

직접 해 볼 때는 앱을 먼저 띄우고, 몇 초 뒤 다른 터미널에서 서버를 짧은 주기로 띄웁니다.

```bash
GLASSPOD_SERVER=ws://localhost:8080/agent POD_NAME=orders-1 POD_NAMESPACE=shop NODE_DEBUG=glasspod node --conditions=@glasspod/source --import tsx --input-type=module -e 'import { glasspod } from "@glasspod/sdk"; glasspod.start(); glasspod.state("app.mode", "ready"); setInterval(() => glasspod.exception(new Error("DB timeout")), 1000);'
```

```bash
GLASSPOD_METRICS_INTERVAL_MS=1000 GLASSPOD_HEARTBEAT_INTERVAL_MS=1000 npm run dev:server
```

SDK 디버그 로그에 서버가 없는 동안 `event held ...`가 나오고, 서버가 뜨면 `sending held events`, `held event sent ...`, 바로 이어 `metrics sent ...`가 나옵니다. 그 뒤 `heartbeat received`가 약 1초마다 나옵니다. 서버 로그에는 `type=event`(state, 첫 예외, 묶음)와 `type=metrics`가 나옵니다. 서버를 Ctrl+C로 끄면 SDK가 다시 보관하기 시작하고, 다시 띄우면 보냅니다.
