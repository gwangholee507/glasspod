# T24 스케일 조정(HPA 경고)

- 우선순위: P1 · 단계 10 · 선행 작업: T18, T21 · 결정: 없음(아래 결정 1~3은 착수 전 사용자 결정)
- 브랜치: `feat/t24-scale`
- 작성: 2026-11-24

## 목표

개발자가 화면에서 Deployment의 replica 수를 바꾸게 합니다(design.md 5.4 '스케일 조정', 1차 범위의 수동 조치 3번째). HPA가 붙은 Deployment는 바꾼 값을 HPA가 다시 덮어쓰므로 버튼과 서랍에 경고합니다.

- 서버: 조치 `scale-deployment` — Deployment의 scale 하위 자원을 읽고 replica 수를 merge patch. HPA를 watch해 Deployment 항목에 붙임. 조치 대상에 Deployment를 더함.
- 웹: 한눈에 보기의 Deployment 카드에 '스케일 조정' 버튼과 HPA 표시, 스케일 서랍(replica 수 고르기), 조치 기록·타임라인의 Deployment 대상.
- 로컬 클러스터에서 데모 앱을 3 → 5 → 3으로 바꾸고, HPA를 붙여 경고와 HPA가 되돌리는 것을 봅니다.

## 결정 사항

1~3은 2026-11-24에 사용자가 정했습니다(착수 전에 보고한 질문 3개, 모두 추천안). 4~20은 이 작업의 기본값입니다.

## 서랍 문장

지금 replica 수 `N`, 고른 수 `M`, Deployment `demo-app`입니다.

| 경우 | '실행하면' |
| --- | --- |
| 늘림(M > N) | ① Deployment `demo-app`의 replica 수를 N개에서 M개로 바꿉니다. ② ReplicaSet이 새 Pod M−N개를 만듭니다. 준비되면 트래픽을 받습니다. |
| 줄임(0 < M < N) | ① 같음. ② ReplicaSet이 Pod N−M개를 지웁니다. 준비 안 된 Pod와 늦게 만든 Pod를 먼저 고릅니다. ③ 지운 Pod의 기록은 이 화면에 30분 남습니다. |
| 0 | ① 같음. ② ReplicaSet이 Pod N개를 모두 지웁니다. ③ 같음. |
| 같음 | ① 바꿀 replica 수를 고릅니다. |
| 격리된 Pod가 있음 | 마지막에: 격리된 Pod K개는 Deployment가 관리하지 않아 이 수에 들지 않고 그대로 남습니다. |

경고(코랄):

- HPA: `HPA X(최소 a · 최대 b)가 이 Deployment의 replica 수를 관리합니다. 바꾼 값은 HPA가 다시 바꿀 수 있습니다.` 뒤에 M이 1 이상이고 범위 밖이면 ` M개는 범위 밖이라 HPA가 곧 a개(또는 b개)로 되돌립니다.`, M이 0이면 ` 0개면 HPA가 이 Deployment를 조정하지 않습니다.`
- M이 0: `replica를 0개로 하면 이 Deployment의 Pod가 모두 지워져 트래픽을 받을 Pod가 없습니다.`

안내(회색): 늘림 `새 Pod는 readiness probe를 통과한 뒤에 트래픽을 받습니다.`, 줄임·0 `Pod를 지우면 메모리 상태와 처리 중이던 요청이 사라집니다. 원인을 조사하려면 먼저 snapshot을 받아 둡니다.`, 같음 `replica 수는 0~20개로 고릅니다.`

| 스케일 조정 성공 | Deployment `demo-app`의 replica 수를 3개에서 5개로 바꿨습니다. (from을 모르면 '5개로 바꿨습니다.') HPA가 있었으면 뒤에 ' HPA가 다시 바꿀 수 있습니다(`X`).' |

## 범위

### 포함

- `packages/protocol/src/http.ts`: `ActionKind`에 `scale-deployment`, `ActionTarget` 합집합, `ActionRequest.replicas`, `ActionItem.scale`, `DeploymentItem.uid`·`hpa`
- `apps/server`: 요청 검사, 스케일 실행, HPA watch와 요약, Deployment 항목, 저장소 거르기, 로그, 단위 테스트

- `deploy/server/rbac-glasspod-demo.yaml`: `deployments/scale: get, patch`, `horizontalpodautoscalers: get, list, watch`

### 제외

## 알려진 한계

- HPA는 지표가 있으면 범위 안에서도 다음 평가 때 replica 수를 바꿉니다. 로컬 클러스터에는 metrics-server가 없어 HPA가 범위만 지킵니다(결정 18).
- 줄일 때 지울 Pod는 쿠버네티스(ReplicaSet 컨트롤러)가 고릅니다. 서랍은 어느 Pod인지 맞히지 않습니다.
- 롤아웃 중(ReplicaSet 둘)에 바꾸면 Deployment가 두 ReplicaSet에 나눠 맞춥니다.
- 서랍을 연 뒤 다른 사람(HPA, kubectl)이 바꾼 수는 덮어씁니다. 기록의 from은 서버가 읽은 실제 수입니다(결정 7, 8).

## 쓰는 법

```bash
curl -s -X POST localhost:8080/api/actions -H 'Content-Type: application/json' -d '{"action":"scale-deployment","target":{"namespace":"glasspod-demo","name":"demo-app"},"expectedUid":"<uid>","replicas":5}'
```

uid는 `GET /api/pods`의 `deployments[].uid`에 있습니다. 확인용 HPA:

```bash
kubectl -n glasspod-demo autoscale deployment demo-app --min=3 --max=5
```

```bash
kubectl -n glasspod-demo delete hpa demo-app
```
