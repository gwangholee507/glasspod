# T12 쿠버네티스 watch

- 우선순위: P0 · 단계 4 · 선행 작업: T03 · 결정: D3
- 브랜치: `feat/t12-k8s-watch`
- 작성: 2026-11-14

## 목표

서버가 쿠버네티스 API를 watch해 Pod, Deployment, ReplicaSet, 클러스터 이벤트를 받고, Pod마다 지금 상태를 들고 있게 합니다(design.md 5.2). T13 상태 판단이 이 상태와 SDK 신호(T11)를 합칩니다.

- 처음에는 클러스터 밖(노트북)에서 kubeconfig로 개발합니다. 클러스터 안 실행(ServiceAccount)은 같은 코드로 T16에서 확인합니다.
- 이 작업은 읽기만 합니다. list와 watch 말고 쿠버네티스 API를 부르지 않습니다.
- 확인은 서버 로그로 합니다. 웹 화면용 조회 API는 T14에서 만듭니다.

## 결정 사항

1~6은 2026-11-14에 사용자가 추천안으로 정했습니다. 7~16은 이 작업의 기본값입니다.

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | 쿠버네티스 클라이언트 | `@kubernetes/client-node` 2.0.1(`apps/server`의 dependency). informer(list + watch)를 씀 | 사용자 결정. kubeconfig와 클러스터 안 ServiceAccount를 모두 처리하고, watch가 끊기면 마지막 `resourceVersion`에서 다시 붙고 410 Gone이면 다시 list함. T21~T24 조치에도 그대로 씀. 2.0.2(2026-11-02)는 2주가 안 됨 |
| 2 | 볼 namespace | 환경변수 `GLASSPOD_NAMESPACES`(쉼표로 나눈 목록, 기본 `glasspod-demo`). 이름은 DNS-1123 label(소문자·숫자·`-`, 63자까지)이어야 하고 아니면 시작 실패. 빈 항목도 시작 실패, 같은 이름은 한 번만 | 사용자 결정. namespace마다 watch를 따로 두면 T16에서 namespace에 한정된 Role로 권한을 줄 수 있음(ClusterRole 불필요) |
| 3 | 클러스터에 닿지 않을 때 | 경고를 남기고 서버는 계속 동작. watch마다 1초부터 2배씩 30초까지 기다렸다 다시 시작 | 사용자 결정. 클러스터가 잠깐 없어도 SDK 연결과 snapshot은 그대로 씀. 설정 값이 잘못된 경우는 지금 규칙대로 시작 실패 |
| 4 | 접속 설정 고르기 | `GLASSPOD_KUBE_CONTEXT`가 있으면 kubeconfig(`KUBECONFIG` 또는 `~/.kube/config`)에서 그 context를 씀. kubeconfig에 그 context가 없으면 시작 실패. 없고 `KUBERNETES_SERVICE_HOST`가 있으면 클러스터 안 ServiceAccount. 둘 다 없으면 watch를 끄고 경고 한 줄. kubeconfig의 current-context는 쓰지 않음 | 사용자 결정. current-context를 따라가면 context를 바꿨을 때 다른 클러스터를 보게 되고, T21부터는 거기에 조치까지 함. 시작 로그에 API 서버 주소를 남김 |
| 5 | T12가 들고 있는 것 | 지금 있는 Pod·Deployment·ReplicaSet의 요약(아래 '요약')만 메모리에. 지워진 Pod는 바로 뺌. 클러스터 이벤트는 들고 있지 않고 로그만 남김 | 사용자 결정. 지워진 Pod를 30분 남기는 일과 이벤트 이력은 T11의 저장소(D1) |
| 6 | 확인 방법 | 서버 로그. 확인용 Deployment는 `glasspod-demo` namespace에 임시로 띄우고 매니페스트는 저장소에 넣지 않음 | 사용자 결정. 조회 API는 T14, 데모 앱 배포는 T15 |
| 7 | watch하는 자원 | namespace마다 4개: `pods`(core/v1), `deployments`·`replicasets`(apps/v1), `events`(core/v1). Deployment → ReplicaSet → Pod 순서로 시작(앞의 것이 실패해도 다음 것은 시작함) | design.md 5.4의 관찰 권한과 같음. `kubectl get events`와 같은 core/v1이라 RBAC가 단순함. 순서를 정하면 Pod 로그에 Deployment가 나옴 |
| 8 | Pod와 Deployment 잇기 | Pod의 controller owner(`ReplicaSet`) → ReplicaSet의 controller owner(`Deployment`). Deployment는 물어볼 때 찾음 | ReplicaSet이 Pod보다 늦게 와도 맞게 나옴. 격리(T23)한 Pod는 owner가 그대로라 같은 방법으로 원래 Deployment를 앎 |
| 9 | 로그 | 요약이 바뀔 때만 한 줄(`pod added`·`pod changed`·`pod deleted` 등). 바뀐 항목은 `changed=`. 클러스터 이벤트는 처음 list는 개수만, 그 뒤 새로 생기거나 바뀐 것을 한 줄씩(`message`는 200자까지) | 쿠버네티스는 요약과 상관없는 필드(예: `managedFields`)로도 update를 보냄. 이벤트 처음 list는 한 시간치가 한꺼번에 옴 |
| 10 | 실패 로그 | watch마다 실패가 이어지는 동안 첫 실패만 경고(`kube watch failed`), 다시 되면 `kube watch recovered`. 오류 내용이 바뀌면 다시 경고 | 30초 상한이어도 namespace마다 4개가 실패하면 로그가 많아짐 |
| 11 | 조용한 watch | client-node가 30초 동안 데이터가 없으면 watch를 끊고 마지막 `resourceVersion`으로 다시 붙음. 로그를 남기지 않음 | client-node 2.0.1의 동작(아래 '사전 확인'). 실패가 아님 |
| 12 | 종료 | SIGTERM·SIGINT에 watch를 모두 멈춤. 멈춘 뒤 오는 오류(요청 취소)는 무시 | `stop()`이 요청을 끊으면 informer가 오류를 한 번 보냄 |
| 13 | 시작 순서 | HTTP·WebSocket을 먼저 열고 watch는 뒤에서 시작. 서버 시작을 기다리게 하지 않음 | 결정 3과 같음 |
| 14 | HTTP API | 바꾸지 않음. T09에서 넘긴 'snapshot API에서 Pod가 있는지 확인'은 T14로 | 사용자 결정(추천안). 다른 조회 API와 오류 형식을 맞출 때 함께 함 |
| 15 | 브랜치 | `main`에서 `feat/t12-k8s-watch`를 만듦. 커밋하지 않은 결정 정리 문서(`docs/design.md`, `docs/guides/T17.md`, `docs/logs/2026-11-14.md`)를 함께 가져감 | 2026-11-14 로그에 '다음 작업 브랜치에서 함께 커밋'으로 적음 |
| 16 | 테스트 | 요약 만들기(Pod·Deployment·ReplicaSet), 바뀐 항목, Pod → Deployment 잇기, 접속 설정 고르기, 오류 설명 | 핵심 로직만. informer와 재시도는 실제 클러스터와 `kubectl proxy`로 확인 |

### 요약

| 자원 | 들고 있는 값 |
| --- | --- |
| Pod | `phase`, `ready`(Ready condition이 True), `terminating`(`deletionTimestamp`가 있음), `restarts`(컨테이너 `restartCount` 합), `waiting`(기다리는 컨테이너의 이유, 예: `CrashLoopBackOff`), `lastTermination`(가장 최근에 끝난 컨테이너의 `reason`·`exitCode`·`finishedAt`·컨테이너 이름, 예: `OOMKilled`), `ip`(Pod IP, T25), `replicaSet`, `createdAt` |
| Deployment | `desired`(`spec.replicas`, 없으면 1), `ready`, `available` |
| ReplicaSet | `deployment`, `revision`(`deployment.kubernetes.io/revision` 주석), `desired` |

- 이름과 namespace, `uid`도 함께 듭니다. Pod의 init 컨테이너는 세지 않습니다.
- ReplicaSet의 `ready`는 Pod 수에 따라 자주 바뀌므로 들고 있지 않습니다(Deployment에 있음).

### 사전 확인

`@kubernetes/client-node` 2.0.1, Node 22.22.0, Docker Desktop Kubernetes 1.34.1에서 2026-11-14에 확인했습니다. `kube-system`의 Pod를 읽기만 하는 확인 스크립트(저장소에 넣지 않음)로 봤습니다.

| 확인 | 결과 |
| --- | --- |
| 모듈 | ESM(`"type": "module"`). `CoreV1Api`는 객체 인자(`listNamespacedPod({ namespace })`) |
| `makeInformer(kc, path, listFn)` | `start()`가 list를 끝내고 watch를 연 뒤 끝남. list 결과는 `add`로 옴(9개, 96ms) |
| 조용한 watch | 30초 동안 데이터가 없으면 클라이언트가 끊고 같은 `resourceVersion`으로 다시 붙음(`connect`가 30초마다). bookmark는 요청하지 않음 |
| 실패 | list나 watch가 실패하면 `error`를 보내고 informer가 멈춤. 다시 시작하지 않음. 410과 30초 시간 초과만 스스로 이어 감 |
| `start()`와 실패 | list가 실패해도 `start()`는 예외 없이 끝나고 `error`로 알림 |
| `stop()` | 요청을 끊으면서 `error`(`AbortError`)를 한 번 보냄 |
| 닿지 않는 API 서버 | `TypeError: fetch failed`, `cause`에 이유. undici가 막는 포트(예: 1번)는 `bad port` |
| 인증 실패 | `ApiException`, `code` 401 |
| kubeconfig | `setCurrentContext()`는 이름을 검사하지 않음. `getContextObject(name)`이 `null`이면 없는 context |
| 타입 | client-node가 dependency로 `@types/node` 26.6.6을 끌어와 그 아래에 따로 설치됨(루트는 22.20.5). `skipLibCheck`가 켜져 있어 `npm run typecheck`가 그대로 통과함 |
| 날짜 | list 결과는 날짜가 `Date`, watch로 온 객체는 JSON 그대로라 문자열. 요약에서 둘 다 ISO 문자열로 바꿈 |
| `http://` API 서버 | kubeconfig에 `insecure-skip-tls-verify: true`가 없으면 요청 전에 `HTTP protocol is not allowed when skipTLSVerify is not set or false`로 실패함. `kubectl proxy`로 확인할 때 넣음 |

## 범위

### 포함

- 서버 설정: `GLASSPOD_NAMESPACES`, `GLASSPOD_KUBE_CONTEXT`
- 접속 설정 고르기와 오류 설명(`kube.ts`), 요약과 지금 상태(`cluster.ts`), informer와 다시 시작·로그(`watch.ts`), 시작과 종료(`index.ts`)와 단위 테스트

### 제외

- 지워진 Pod 30분 보관, 이벤트 이력, `seq` 누락 판단(T11)
- SDK 신호와 합친 상태 판단(T13)
- 조회 API, SSE, snapshot API의 Pod 확인(T14)
- 서버 배포와 RBAC(T16). 이 작업은 kubeconfig 사용자(`system:masters`)로 확인함
- 조치(T21~T24), Service·HPA 읽기(T23·T24)
- 접속 IP와 Pod IP 대조(T25). 이 작업은 Pod IP를 들고 있기만 함

## 만들 파일

```text
apps/server/
├─ package.json        # (고침) @kubernetes/client-node 2.0.1
└─ src/
   ├─ config.ts        # (고침) GLASSPOD_NAMESPACES, GLASSPOD_KUBE_CONTEXT
   ├─ kube.ts          # 접속 설정 고르기(kubeconfig context / 클러스터 안 / 끔), 오류 설명
   ├─ kube.test.ts
   ├─ cluster.ts       # Pod·Deployment·ReplicaSet 요약, 지금 상태, 바뀐 항목, Pod → Deployment
   ├─ cluster.test.ts
   ├─ watch.ts         # namespace마다 informer 4개, 실패 뒤 다시 시작, 로그
   └─ index.ts         # (고침) watch 시작과 종료
package-lock.json      # (고침)
```

## 쓰는 법

클러스터 밖에서 볼 때는 context를 정해 줍니다. 정하지 않으면 watch 없이 SDK 연결만 받습니다.

```bash
kubectl config current-context
```

```bash
GLASSPOD_KUBE_CONTEXT=docker-desktop npm run dev:server
```

```bash
GLASSPOD_KUBE_CONTEXT=docker-desktop GLASSPOD_NAMESPACES=glasspod-demo,shop npm run dev:server
```

| 환경변수 | 기본값 | 뜻 |
| --- | --- | --- |
| `GLASSPOD_NAMESPACES` | `glasspod-demo` | watch할 namespace(쉼표로 나눔) |
| `GLASSPOD_KUBE_CONTEXT` | 없음 | 클러스터 밖에서 쓸 kubeconfig context. 없으면 클러스터 안에서만 watch |

## 완료 기준

2026-11-14에 로컬 클러스터(context `docker-desktop`)에서 모두 확인했습니다. 확인 스크립트와 매니페스트는 저장소에 넣지 않았습니다. 확인용 Deployment `probe`는 `glasspod-demo` namespace에 임시로 띄우고, 끝나면 지웁니다(namespace는 T15에서 쓰도록 남김). 이미지는 노트북에 이미 있는 `postgres:16`을 `imagePullPolicy: IfNotPresent`로 써서 내려받지 않습니다. 컨테이너는 `sh -c 'trap "exit 3" TERM; sleep infinity & wait'`로 띄워 `kill 1`이면 종료 코드 3으로 끝나게 합니다.
