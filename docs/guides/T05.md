# T05 SDK metrics

- 우선순위: P0 · 단계 5 · 선행 작업: T04
- 브랜치: `feat/t05-sdk-metrics`
- 작성: 2026-11-09

## 목표

Node.js SDK가 연결된 동안 정해진 주기마다 `metrics` 메시지를 보냅니다(design.md 5.1, 7.3). 값은 두 가지입니다.

- SDK가 스스로 모으는 `runtime.*` 지표: 이벤트 루프 지연과 사용률, 힙과 프로세스 메모리, CPU
- 개발자가 등록하는 `app.*` 지표: `glasspod.gauge()`(지금 값), `glasspod.counter()`(누적값)

이 메시지는 heartbeat도 겸합니다. 서버는 연결이 열려 있는데 metrics가 끊기면 앱이 멈췄다고 의심합니다(design.md 7.5).

## 결정 사항

1~3은 2026-11-09에 사용자가 정했습니다. 4~15는 이 작업의 기본값입니다.

| # | 항목 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | `runtime.*` 범위 | 기본 세트 11개(아래 'runtime 지표'). 이벤트 루프 지연 p50·p99·max, 이벤트 루프 사용률, 힙 used·total·limit, RSS, 컨테이너 메모리 한도, CPU user·system | 사용자 결정. 막힘(지연), 바쁨(사용률, CPU), 메모리 증가와 OOM 직전(힙, RSS, 한도)을 서로 구분할 수 있음. GC와 external 메모리는 넣지 않음 |
| 2 | 등록 API | gauge는 콜백 `glasspod.gauge(name, () => number)`, counter는 객체 `glasspod.counter(name).inc(n?)`. counter 누적값은 SDK가 들고 있음 | 사용자 결정. design.md 8장의 gauge 모양과 맞음 |
| 3 | 브랜치 | T04를 `main`에 fast-forward 병합하고 push한 뒤 `main`에서 `feat/t05-sdk-metrics`를 만듦 | 사용자 결정 |
| 4 | 이벤트 루프 지연 측정 | SDK 자체 타이머(20ms 간격, `unref`)가 늦게 깨어난 시간을 `perf_hooks.createHistogram()`에 마이크로초로 기록하고, 주기마다 p50·p99·max를 보낸 뒤 비움 | Node의 `monitorEventLoopDelay`는 `reset()` 직후 첫 표본을 버려, 전송 직후에 시작된 막힘을 놓침(아래 '측정 방식 비교'). 20ms보다 긴 막힘은 모두 잡힘 |
| 5 | 이벤트 루프 사용률 | `performance.eventLoopUtilization()`의 지난 전송 뒤 차이(0~1) | 누적값의 차이라 놓치는 구간이 없음. 지연은 작은데 사용률이 높으면 바쁜 것, 지연이 크면 막힌 것 |
| 6 | 보내는 때 | welcome을 받으면 지연 측정과 전송 타이머를 시작하고, 첫 metrics는 한 주기 뒤에 보냄. 연결이 끝나면(끊김, `stop()`) 둘 다 멈춤 | 첫 묶음의 지연 값이 한 주기 전체를 덮음. 연결이 없을 때는 아무 비용도 들지 않음 |
| 7 | 끊긴 동안 | 보내지도 쌓지도 않음 | 최신 값 유지와 재연결 직후 전송은 T08 |
| 8 | 주기 | welcome의 `metricsIntervalMs`. 1000ms보다 짧으면 1000ms, Node 타이머 상한(2147483647ms)보다 길면 상한으로 바꾸고 디버그 로그 | 서버 설정은 1ms도 허용하므로 앱을 지킴. 상한을 넘으면 Node가 1ms로 바꿔 버림 |
| 9 | 이름 규칙 | 스키마 이름 규칙에 `app.` 접두어를 더함: `^app(\.[a-z][a-z0-9_]*)+$`. 어기면 경고 한 줄을 남기고 등록하지 않음 | `runtime.*`, `http.*`은 SDK 자동 수집 몫(design.md 7.3). 잘못된 이름을 보내면 서버가 metrics 묶음 전체를 버림 |
| 10 | 같은 이름 | counter는 같은 객체를 돌려줌(누적값 공유). gauge는 새 콜백으로 바꿈(디버그 로그). 이미 다른 종류로 등록된 이름이면 경고하고 무시 | 여러 모듈이 같은 counter를 쓸 수 있음. 모듈을 다시 불러와도 gauge가 쌓이지 않음 |
| 11 | 등록 상한 | `app.*` 지표 100개. 넘으면 처음 한 번 경고하고 무시 | 요청마다 이름을 만드는 실수(`app.user_123`)가 메모리와 메시지 크기를 늘리지 않게 함 |
| 12 | gauge 콜백 | 전송할 때마다 동기로 부름. 예외를 던지거나 유한한 수가 아니면(NaN, Infinity, 문자열, Promise) 그 주기에 그 값만 빼고, 이름마다 처음 한 번 경고. 그 뒤로는 디버그 로그 | 앱 코드 실수 하나로 다른 값이나 앱이 망가지지 않게 함. NaN은 JSON에서 `null`이 되어 스키마를 어김 |
| 13 | `counter.inc(n)` | `n` 기본값 1. 0 이상의 유한한 수만 받음. 아니면 무시하고 counter마다 처음 한 번 경고 | counter는 줄어들면 안 됨(줄면 서버가 재시작으로 판단) |
| 14 | 등록 시점 | `gauge()`, `counter()`, `inc()`는 `start()` 전, SDK가 꺼졌을 때, `stop()` 뒤에도 됨. 보내는 것만 연결된 동안 | 앱 코드가 SDK 상태를 몰라도 됨 |
| 15 | 앱 보호 | 모든 공개 함수는 예외를 던지지 않음. 타이머는 `unref()`하고 콜백은 `guard`로 감쌈 | SDK 원칙 |

### runtime 지표

| 이름 | 종류 | 출처 | 뜻 |
| --- | --- | --- | --- |
| `runtime.event_loop.lag_p50_ms` | gauge | SDK 타이머 | 지난 주기의 이벤트 루프 지연 중앙값 |
| `runtime.event_loop.lag_p99_ms` | gauge | SDK 타이머 | 지난 주기의 이벤트 루프 지연 p99 |
| `runtime.event_loop.lag_max_ms` | gauge | SDK 타이머 | 지난 주기의 가장 긴 지연 |
| `runtime.event_loop.utilization` | gauge | `performance.eventLoopUtilization()` | 지난 주기에 이벤트 루프가 일한 비율(0~1) |
| `runtime.heap.used_bytes` | gauge | `process.memoryUsage().heapUsed` | V8 힙 사용량 |
| `runtime.heap.total_bytes` | gauge | `process.memoryUsage().heapTotal` | V8가 잡아 둔 힙 크기 |
| `runtime.heap.limit_bytes` | gauge | `v8.getHeapStatistics().heap_size_limit` | 힙 상한. 넘으면 V8가 프로세스를 끝냄 |
| `runtime.memory.rss_bytes` | gauge | `process.memoryUsage().rss` | 프로세스가 쓰는 실제 메모리 |
| `runtime.memory.limit_bytes` | gauge | `process.constrainedMemory()` | 컨테이너(cgroup) 메모리 한도. RSS가 이 값에 닿으면 OOMKilled. 알 수 없으면 보내지 않음 |
| `runtime.cpu.user_ms` | counter | `process.cpuUsage().user` | 프로세스 시작 뒤 사용자 모드 CPU 시간 |
| `runtime.cpu.system_ms` | counter | `process.cpuUsage().system` | 프로세스 시작 뒤 커널 모드 CPU 시간 |

- 지연 값은 마이크로초까지(소수 셋째 자리), 사용률은 소수 넷째 자리, 바이트는 정수로 보냅니다.
- 지연 표본이 없으면(주기가 측정 간격보다 짧은 경우 등) 지연 세 값은 보내지 않습니다.
- 컨테이너 한도는 연결할 때마다 한 번 읽습니다. 0이거나 기계의 전체 메모리(`os.totalmem()`) 이상이면 한도가 없는 것으로 봅니다(cgroup v2의 `max`는 매우 큰 수로 나옴).
- 아무 일도 하지 않을 때도 지연은 약 2ms로 나옵니다(macOS에서 확인). Node 타이머가 밀리초 단위로 돌기 때문입니다.

### 측정 방식 비교

Node 22.22.0, macOS에서 2026-11-09에 확인했습니다.

| 방식 | 전송 직후 300ms 막힘 | 유휴 CPU (5초 동안) |
| --- | --- | --- |
| 측정 없음 | - | 약 1ms |
| `monitorEventLoopDelay`(10ms) + 주기마다 `reset()` | 놓침(max 11ms) | 약 15ms |
| SDK 타이머 10ms + `createHistogram()` | 잡음(305ms) | 약 34ms |
| SDK 타이머 20ms + `createHistogram()` | 잡음 | 약 25ms |
| SDK 타이머 50ms + `createHistogram()` | 잡음 | 약 15ms |

`monitorEventLoopDelay`는 `reset()`이 직전 시각을 지워, 다음 표본 하나를 기록하지 않고 시각만 다시 잡습니다. 그래서 `reset()`과 같은 콜백이나 그 직후 10ms 안에 시작된 막힘이 통째로 빠집니다. SDK 타이머는 직전 시각을 지우지 않으므로 이 구멍이 없습니다. 유휴 CPU는 대부분 프로세스를 깨우는 비용이라, 앱이 일하는 중에는 차이가 거의 없습니다. 20ms는 놓치지 않는 막힘의 길이와 유휴 비용의 중간값입니다.

## 범위

### 포함

- `runtime.*` 수집(`runtime.ts`)과 단위 테스트
- `app.*` 등록과 값 모으기(`registry.ts`)와 단위 테스트
- 주기 전송(`metrics.ts`)과 주기 계산 단위 테스트
- 연결(`connection.ts`): 연결됨·끊김 알림, 연결된 동안만 보내는 `send`
- 공개 API(`index.ts`): `glasspod.gauge`, `glasspod.counter`

### 제외

- HTTP 자동 수집 `http.*` (T07)
- event와 처리되지 않은 예외 (T06)
- 끊긴 동안 최신 값 유지, 재연결 직후 전송, 응답 없는 연결 감지 (T08)
- 서버의 보관과 표시 (T11, T14). 서버는 지금처럼 받은 종류와 `seq`만 로그에 남김
- 데모 앱 (T10). 실제 전송은 저장소에 넣지 않는 확인 스크립트로 확인함

## 만들 파일

```text
packages/sdk-node/src/
├─ index.ts             # (고침) glasspod.gauge(), glasspod.counter() 추가, 연결과 metrics 전송 연결
├─ connection.ts        # (고침) onConnected·onDisconnected 알림, send()
├─ guard.ts             # connection.ts에서 옮긴 guard. 타이머 콜백과 WebSocket 리스너를 감쌈
├─ registry.ts          # app.* 지표 등록과 값 모으기
├─ registry.test.ts
├─ runtime.ts           # runtime.* 수집, 이벤트 루프 지연 타이머
├─ runtime.test.ts
├─ metrics.ts           # 주기 전송 타이머, 주기 계산
└─ metrics.test.ts
```

## 쓰는 법

```ts
import { glasspod } from "@glasspod/sdk";

glasspod.start({ app: { name: "orders", version: "1.4.2" } });

// 지금 값: 보낼 때마다 콜백을 부릅니다. 가볍고 동기로 끝나는 콜백만 씁니다.
glasspod.gauge("app.queue.length", () => queue.length);

// 누적값: SDK가 합계를 들고 있다가 보낼 때 그대로 보냅니다.
const created = glasspod.counter("app.orders.created");
created.inc();
created.inc(3);
```

## 로그 형식

등록 실수와 콜백 문제는 표준 오류에 한 줄 남깁니다. 같은 문제는 이름마다 한 번만 남깁니다.

```text
[glasspod] metric ignored: "queue.length" must start with "app." and use lowercase letters, digits and _ in each level
[glasspod] metric ignored: "app.jobs" is already registered as a counter
[glasspod] metric ignored: "app.user_101": at most 100 app metrics can be registered
[glasspod] gauge ignored: "app.queue.length" needs a callback that returns a number
[glasspod] gauge "app.queue.length" skipped: callback threw (boom)
[glasspod] gauge "app.queue.length" skipped: callback returned NaN, not a finite number
[glasspod] counter "app.orders.created" ignored inc(-1): the amount must be a finite number >= 0
```

`NODE_DEBUG=glasspod`이면 다음이 더 나옵니다.

```text
GLASSPOD 57390: metrics every 5000ms
GLASSPOD 57390: metrics interval 10ms from server raised to 1000ms
GLASSPOD 57390: metrics sent seq=3 values=13
GLASSPOD 57390: metrics stopped
```

## 도구 버전

새로 설치하는 패키지가 없습니다. `node:perf_hooks`, `node:v8`, `node:os`와 `process`의 Node 22.22.0 내장 API만 씁니다.

## 완료 기준

실제 전송은 저장소에 넣지 않는 확인 스크립트로 확인했습니다(43개 항목). 스크립트는 SDK를 소스 참조 조건(`@glasspod/source`)과 tsx로 불러오는 작은 앱을 띄우고, 실제 서버(`apps/server/src/index.ts`)와 `ws`로 만든 가짜 서버(받은 메시지를 모두 기록하고 `parseSdkMessage`로 검증)에 붙여 봅니다.

| 확인 | 기대 결과 |
| --- | --- |
| `npm run typecheck` | exit 0 |
| `npm test` | 모든 테스트 통과. 등록·값 모으기, runtime 수집, 주기 계산 테스트 포함 |
| `npm run format:check` | `All matched files use Prettier code style!` |
| 실제 서버(`GLASSPOD_METRICS_INTERVAL_MS=1000`) | 서버 로그에 `message received type=metrics`가 약 1초마다, `seq`가 1부터 이어짐. `message ignored` 없음 |
| 가짜 서버: 메시지 모양 | 모든 metrics가 `parseSdkMessage`를 통과. runtime 10개(macOS에는 컨테이너 한도 없음)와 등록한 app 값이 들어 있음. 간격은 welcome의 주기 |
| 이벤트 루프 막힘(300ms, 전송 직후 포함) | 그다음 metrics의 `lag_max_ms`가 280 이상 |
| 바쁜 루프(1초 동안 계산) | `utilization`이 0.9 이상, `cpu.user_ms`가 그만큼 늘어남 |
| 메모리 늘리기 | `heap.used_bytes`와 `memory.rss_bytes`가 늘어남 |
| counter | `inc()` 합계가 누적값으로 나감. 같은 이름의 `counter()`는 같은 합계 |
| gauge 콜백 문제(예외, NaN, Promise) | 그 값만 빠지고 경고는 이름마다 한 줄. 다른 값은 그대로, 앱은 계속 동작 |
| 이름 규칙 위반, 종류 충돌, 101번째 등록 | 경고 한 줄씩, 예외 없음 |
| welcome 주기 10ms | 1000ms마다 보냄 |
| 서버 끊김과 재연결 | 끊긴 동안 보내지 않음. 다시 붙으면 새 welcome의 주기로 다시 보내고 `seq`는 이어짐 |
| `stop()` | 더 보내지 않고 프로세스가 스스로 끝남 |
| 서버가 없을 때 앱이 할 일을 마침 | 프로세스가 스스로 끝남 |
| 위 모든 경우 | 처리되지 않은 예외 없음 |

직접 해 볼 때는 서버를 짧은 주기로 띄운 뒤 다른 터미널에서 실행합니다.

```bash
GLASSPOD_METRICS_INTERVAL_MS=1000 npm run dev:server
```

```bash
GLASSPOD_SERVER=ws://localhost:8080/agent POD_NAME=orders-1 POD_NAMESPACE=shop NODE_DEBUG=glasspod node --conditions=@glasspod/source --import tsx --input-type=module -e 'import { glasspod } from "@glasspod/sdk"; glasspod.start(); const jobs = []; glasspod.gauge("app.queue.length", () => jobs.length); const c = glasspod.counter("app.jobs.created"); setInterval(() => { jobs.push(1); c.inc(); }, 300);'
```

서버 로그에 `message received type=metrics`가 약 1초마다 나오고, SDK 쪽 디버그 로그에 `metrics sent seq=... values=...`가 나옵니다. 끝낼 때는 Ctrl+C로 멈춥니다.
