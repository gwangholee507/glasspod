# T15 데모 앱 배포

- 우선순위: P0 · 단계 7 · 선행 작업: T10 · 결정: D3
- 브랜치: `feat/t15-demo-deploy`
- 작성: 2026-11-14

## 목표

T10의 데모 앱을 로컬 클러스터의 `glasspod-demo` namespace에 띄웁니다. 이후 작업(T11~T27)은 이 Pod들을 보고 조치합니다.

- 데모 앱 컨테이너 이미지를 만들고, 레지스트리 없이 클러스터가 그대로 쓰게 합니다(D3).
- 데모 앱 Deployment(Pod 3개)와 Service, 같은 이미지로 띄우는 부하 Deployment를 매니페스트로 둡니다. SDK는 Pod 이름과 namespace를 Downward API로 받습니다(design.md 8장).
- 서버는 아직 클러스터에 없습니다(T16). 확인은 노트북에서 띄운 서버(`npm run dev:server`)에 Pod를 붙여서 합니다.
- T10에서 넘긴 것을 확인합니다: 관리 포트(`127.0.0.1:3001`)가 `kubectl port-forward`로 닿는지, 메모리 증가가 컨테이너 OOMKilled로 끝나는지.

## 사전 확인

Docker Desktop 4.59.1(엔진 29.2.0), Kubernetes 1.34.1(context `docker-desktop`), 2026-11-14에 확인했습니다.

| 확인 | 결과 |
| --- | --- |
| 직접 빌드한 이미지를 클러스터가 그대로 쓰는지(D3) | 쓴다. `glasspod-demo-app:dev`로 띄운 Pod의 이벤트가 `Container image "glasspod-demo-app:dev" already present on machine`. 노드의 컨테이너 런타임이 `docker://29.2.0`이라 kubelet이 Docker 엔진의 이미지 저장소를 씀. 레지스트리는 필요 없음 |
| Pod에서 노트북의 서버에 닿는지 | 닿는다. `ws://host.docker.internal:8080/agent`로 `hello accepted`. 서버가 보는 접속 주소는 `::ffff:127.0.0.1`(Docker Desktop이 넘겨줌)이라 Pod IP와 다름. 접속 IP 대조(T25)는 노트북 서버로는 확인할 수 없음 |
| `kubectl port-forward`로 `127.0.0.1:3001`에 닿는지 | 닿는다. port-forward는 Pod 안의 localhost로 붙음. `GET /faults` 200, `POST /faults/slow` 200 |
| 컨테이너 안 Node의 기본 힙 한도 | 메모리 한도 256Mi에서 `heap_size_limit` 259MiB, 512Mi에서도 259MiB. `--max-old-space-size=512`이면 515MiB. `process.constrainedMemory()`는 한도를 그대로 돌려줌 |
| PID 1의 SIGTERM | 처리기가 없는 node(`setInterval`만)는 `docker stop -t 5`에 5초 뒤 종료 코드 137(SIGKILL)로 끝남. SIGTERM이 무시됨 |
| `# syntax=docker/dockerfile:1` | 빌드 로그에 `resolve image config for docker-image://docker.io/docker/dockerfile:1`. 빼면 받아 오지 않고 `RUN --mount=type=cache`도 그대로 됨 |
| 이미지 안의 npm | Node 22.22.0에 딸린 npm 10.9.4. `npm ci` 두 번 모두 `found 0 vulnerabilities` |

## 범위

### 포함

- `examples/demo-app/Dockerfile`, 루트 `.dockerignore`, 루트 스크립트 `npm run demo:image`
- `deploy/demo/`: namespace, 데모 앱 Deployment와 Service, 부하 Deployment
- 부하 스크립트의 종료 신호 처리(결정 16)
- 로컬 클러스터에서 배포와 고장 스위치 확인, 노트북 서버에 붙여 `hello`와 snapshot 확인

### 제외

- 서버 이미지와 배포, RBAC(T16). 클러스터 안 서버 주소로 실제 연결하는 것도 T16
- 서버의 상태 판단(T13)과 화면(T18, T19). 이번에는 서버 로그, snapshot API, `kubectl`로 확인함
- 크래시 때 처리되지 않은 예외 event의 내용 확인, 서버의 OOM 판단(T27). 이번에는 컨테이너가 OOMKilled로 끝나는지와 event가 하나 도착하는지만 봄
- 접속 IP와 Pod IP 대조(T25)
- 롤링 업데이트와 Pod 삭제 때 부하에 생기는 실패(아래 '쓰는 법') 줄이기. Pod 재시작(T22)에서 다시 봄

## 만들 파일

```text
.dockerignore                 # docker build 맥락에서 뺄 파일
package.json                  # (고침) demo:image 스크립트

examples/demo-app/
├─ Dockerfile                 # 다단계 빌드: 빌드 → 실행 의존성 → 실행 이미지
└─ src/
   └─ load.ts                 # (고침) SIGTERM·SIGINT에 바로 끝냄

deploy/demo/
├─ 00-namespace.yaml          # glasspod-demo namespace
├─ demo-app.yaml              # 데모 앱 Deployment(3개)와 Service
└─ load.yaml                  # 부하 Deployment(1개)
```

## 쓰는 법

쿠버네티스 명령 전에 context를 확인합니다(`docker-desktop`이어야 함).

```bash
kubectl config current-context
```

이미지를 만들고 배포합니다.

```bash
npm run demo:image
```

```bash
kubectl apply -f deploy/demo/
```

```bash
kubectl -n glasspod-demo rollout status deployment/demo-app
```

코드를 고쳐 이미지를 다시 만들었으면 새 Pod를 띄웁니다(태그가 같아 apply만으로는 바뀌지 않음).

```bash
kubectl -n glasspod-demo rollout restart deployment/demo-app deployment/demo-load
```

노트북에서 띄운 서버에 붙입니다. 서버는 클러스터를 watch하게 띄우고, 데모 앱의 서버 주소를 잠시 바꿉니다(Pod가 새로 뜸).

```bash
GLASSPOD_KUBE_CONTEXT=docker-desktop npm run dev:server
```

```bash
kubectl -n glasspod-demo set env deployment/demo-app GLASSPOD_SERVER=ws://host.docker.internal:8080/agent
```

매니페스트대로 되돌립니다(클러스터 안 서버 주소).

```bash
kubectl apply -f deploy/demo/demo-app.yaml
```

Pod 하나의 고장 스위치를 씁니다. Pod 이름은 `kubectl -n glasspod-demo get pods`로 봅니다.

```bash
kubectl -n glasspod-demo port-forward pod/demo-app-7bbbcdc59b-62qcr 3001:3001
```

```bash
curl -s -X POST 'localhost:3001/faults/slow?delayMs=1500'
```

주문 API를 노트북에서 부르려면 Service로 port-forward합니다(Pod 하나에 붙음).

```bash
kubectl -n glasspod-demo port-forward service/demo-app 3000:3000
```

부하를 멈추고 다시 켭니다.

```bash
kubectl -n glasspod-demo scale deployment/demo-load --replicas=0
```

```bash
kubectl -n glasspod-demo scale deployment/demo-load --replicas=1
```

앱만 지웁니다. `00-namespace.yaml`까지 지정하면 namespace가 지워지므로 두 파일만 지정합니다.

```bash
kubectl delete -f deploy/demo/demo-app.yaml -f deploy/demo/load.yaml
```

- 데모 앱 로그는 `kubectl -n glasspod-demo logs <Pod 이름>`, 부하 요약은 `kubectl -n glasspod-demo logs deploy/demo-load`로 봅니다.
- 롤링 업데이트나 Pod 삭제 때 부하 요약에 `failed`가 몇 건(Pod 3개를 바꾸는 동안 10건 안팎) 나옵니다. 데모 앱은 SIGTERM을 받으면 바로 새 연결을 받지 않는데, Service에서 빠지는 것이 조금 늦게 퍼지기 때문입니다.
- 처리되지 않은 예외의 stack은 `dist/*.js`의 줄 번호입니다(소스 맵을 켜지 않음).

## 로그 형식

부하 스크립트가 종료 신호를 받으면 한 줄을 남깁니다. `inFlight`는 버린 요청 수입니다.

```text
2026-11-14T05:59:41.437Z INFO  load stopped signal=SIGTERM inFlight=10
```

Glasspod 서버가 클러스터에 없을 때 데모 앱 Pod의 로그입니다.

```text
2026-11-14T05:56:08.038Z INFO  demo-app started port=3000 admin=127.0.0.1:3001
[glasspod] cannot connect to ws://glasspod-server.glasspod.svc.cluster.local:8080/agent (Received network error or non-101 status code.); retrying in the background
```

## 도구 버전

새로 설치한 npm 패키지는 없습니다. 이미지가 쓰는 의존성은 `package-lock.json` 그대로입니다.

| 이미지 | 버전 | 빌드 | 메모 |
| --- | --- | --- | --- |
| `node` | `22.22.0-bookworm-slim@sha256:dd9d21971ec4395903fa6143c2b9267d048ae01ca6d3ea96f16cb30df6187d94` | 2026-02-24 | Docker Hub 공식 이미지. arm64판(`sha256:5e22e6fb…`) 압축 79.4MB. 2026-11-14에 처음 내려받음(사용자 승인) |

- 만든 이미지 `glasspod-demo-app:dev`는 압축 80.5MB(디스크 356MB)이고, 베이스 위에 더한 것은 실행 의존성 7.7MB와 빌드한 JS 약 0.7MB입니다.
- 베이스 이미지의 OS 패키지는 2026-02 것입니다. 로컬 확인용이라 보안 업데이트를 따라가지 않습니다.
