# T14 웹 화면용 조회 API와 실시간 갱신

- 우선순위: P0 · 단계 8 · 선행 작업: T13 · 결정: D2
- 브랜치: `feat/t14-query-api`
- 작성: 2026-11-16

## 목표

서버가 들고 있는 상태 판단(T13), 쿠버네티스 요약(T12), SDK의 지금 상태와 기록(T11)을 웹 화면이 읽을 수 있게 HTTP API와 SSE(D2)로 내보냅니다. T18 목록 화면과 T19 상세 화면이 이 API를 씁니다.

- 목록: Pod마다 판단, 쿠버네티스 요약, SDK 연결, 목록 지표 3개와 5xx/분(design.md 5.3), Deployment 요약
- 상세: Pod 하나의 판단, 마지막 지표 값, 최근 30분 event, 재시작 원인 후보, 연결 기록, 판단 변화
- 판단 변화 기록: 판단이 바뀔 때마다 저장소에 남기고 30분 동안 조회(타임라인)
- SSE: 연결 직후 목록 전체, 그 뒤 1초 판단 주기마다 바뀐 것만
- snapshot API의 오류 형식을 다른 조회 API와 맞춤(T09·T12에서 넘김)
- 웹 화면의 API 클라이언트 함수와 실시간 목록 훅. 목록·상세 자리에서 원본 값을 보여 줘 브라우저로 끝까지 확인함

## 결정 사항

1~3은 2026-11-16에 사용자가 정했습니다(착수 전에 보고한 질문 3개). 4~22는 이 작업의 기본값입니다. 결정 20의 '다시 열기'는 구현하며 확인한 것(아래 '구현하며 확인한 것')으로 더했습니다.

| 5 | 공통 형식 | 모든 `/api` 응답은 JSON, `Cache-Control: no-store`. 실패는 `{ error, detail }`(T09·T17). 성공 본문에는 `serverTime`(서버 시계, epoch ms)을 넣어 화면이 '몇 초째'를 서버 시계로 셈. 시각은 모두 epoch ms이고, `ts`가 붙은 것만 SDK 시계 | 브라우저와 서버 시계가 달라도 '판단이 시작된 지 얼마' 같은 값이 맞음 |
| 6 | 오류 코드 | `pod-not-found`(404, 판단이 없는 Pod), `invalid-query`(400, 잘못된 `namespace`), `not-found`(404, 없는 `/api` 경로), `too-many-streams`(503, SSE 상한), `internal-error`(500, 서버 예외). snapshot은 기존 코드에 `pod-not-found`를 더함: SDK 연결이 없을 때 판단도 없는 Pod면 `pod-not-found`, 판단이 있으면 그대로 `not-connected` | T09에서 넘김(오류 형식 맞추기), T12에서 넘김(Pod가 있는지 확인). 판단(StatusMonitor)이 쿠버네티스 Pod와 SDK Pod를 모두 담으므로 판단으로 확인함 |
| 7 | 있는 Pod | 상세와 snapshot의 '있는 Pod'는 지금 판단이 있는 Pod. 쿠버네티스에서 지워졌어도 SDK 상태가 남아 있으면(`terminated`) 상세가 열림. SDK가 없던 Pod는 지워지면 바로 404 | 목록과 상세가 같은 기준. 지워진 Pod의 마지막 요약은 저장소에 있으므로 필요하면 T19·T23에서 씀 |
| 8 | namespace | 목록, 판단 변화, SSE는 `?namespace=`(하나, DNS-1123)로 거름. 없으면 전부. 모르는 namespace는 빈 목록. 본문의 `namespaces`는 거르지 않은 전체: `GLASSPOD_NAMESPACES` 순서, 그 뒤 판단에만 있는 namespace(SDK만 붙은 것)를 이름순 | 왼쪽 메뉴의 namespace 고르기(design.md 5.3). watch하지 않는 namespace의 SDK Pod도 판단은 있음(T13 결정 11) |
| 9 | 목록 지표 | 이벤트 루프 지연 p99(`runtime.event_loop.lag_p99_ms`), 힙 사용·한도(`runtime.heap.used_bytes`·`limit_bytes`), HTTP 요청 p99(`http.requests.duration_p99_ms`)는 지금 instance의 마지막 값. 5xx/분은 `http.requests.errors_total`의 최근 60초(서버가 받은 시각) 증가량 합. 그 지표를 보내지 않으면 필드가 없음 | SDK가 주기마다 잰 값을 그대로 씀. 증가량은 T11의 counter 증가량(리셋 포함)을 씀 |
| 10 | 5xx 증가량 보관 | `AppStates`가 counter마다 최근 60초의 증가량(`at`, `increase`)을 지금 상태로 들고 있음(`increases`). 저장소를 읽지 않음 | 1초마다 모든 Pod의 목록을 만들 때 저장소(나중에는 DB)를 읽지 않음 |
| 11 | Pod 항목 | `pod`, `deployment`, 판단(`status`, `severity`, `reason`, `since`, `restart`), `kube`(쿠버네티스 요약, 없으면 없음), `sdk`(연결, instance, SDK, 앱, 시각, `missed`, 없으면 없음), `metrics`. 판단의 `silentMs`는 넣지 않음(1초마다 바뀌므로 `sdk.lastMetricsAt`과 `serverTime`으로 셈) | 판단 주기마다 바뀌는 값을 빼야 '바뀐 것만'이 의미가 있음 |
| 12 | Deployment | Pod의 Deployment는 판단(`StatusMonitor`)이 정함: 쿠버네티스 요약이 있으면 ReplicaSet → Deployment, 없으면(지워짐) 앞에서 알던 값. 목록의 `deployments`는 쿠버네티스 Deployment 요약(`desired`, `ready`, `available`) | 지워진 Pod도 같은 Deployment 묶음에 남음. 격리(T23)로 ReplicaSet에서 떨어진 Pod는 Deployment가 없음 |
| 13 | 상세 | `item`(목록 항목과 같음), `values`(지금 instance의 마지막 값 전부, 이름순), `events`(최근 30분, 모든 instance, 일어난 순서), `restartCauses`(`restart.previousInstanceId`가 있으면 `pickRestartCauses`), `connections`(최근 30분), `statusChanges`(이 Pod, 최근 30분) | T11·T13에서 넘김. '무슨 일이 있었나'(design.md 5.3)에 필요한 것 |
| 14 | 판단 변화 조회 | `GET /api/status-changes?namespace=`: 최근 30분, 일어난 순서, 최근 2,000건까지 | 타임라인(오른쪽, Pod를 고르기 전). SSE의 `changes.statusChanges`로 이어 받음 |
| 15 | SSE 내용 | 이벤트 이름 두 가지: `pods`(`GET /api/pods`와 같은 본문), `changes`(`serverTime`, `pods`, `removedPods`, `deployments`, `removedDeployments`, `statusChanges`, `namespaces`(바뀌었을 때만)). namespace로 거른 뒤 비면 보내지 않음. 처음에 `retry: 3000` | 한 판단 주기의 변화를 한 번에 적용함. 다시 붙는 간격을 문서와 맞춤 |

| 17 | SSE 연결 관리 | 동시에 20개(`MAX_STREAMS`)까지, 넘으면 503 `too-many-streams`. 15초마다 주석 줄(`: keepalive`). 소켓에 쌓인 데이터가 1MiB를 넘으면(느린 브라우저) 그 연결을 끊음(브라우저가 다시 붙어 `pods`부터 받음). 서버가 내려갈 때 모두 닫음 | 로그인이 없는 1차 범위(D4)에서 메모리 상한. 중간의 프록시가 조용한 연결을 끊지 않게 함. 열린 SSE가 있으면 `server.close()`가 끝나지 않음 |
| 18 | 로그 | SSE 열림·닫힘 한 줄씩(`stream opened`, `stream closed`, `remote`, `namespace`, `streams`, 닫힘 이유와 시간), 상한 초과·느린 연결은 WARN. 조회 GET은 로그 없음, 500은 ERROR | 브라우저가 다시 붙을 때만 생기므로 양이 적음 |

## 구현하며 확인한 것

Node 22.22.0, Vite 8.3.5, 내장 브라우저(Chromium)에서 2026-11-16에 확인했습니다.

| 확인 | 결과 |
| --- | --- |
| Glasspod 서버가 내려가 있을 때 Vite 프록시를 거친 `EventSource` | 다시 붙는 요청에 프록시가 502 `proxy-error`(JSON)로 답하면 `EventSource`는 SSE가 아닌 응답으로 보고 `CLOSED`가 되어 더 시도하지 않음. 서버를 다시 띄워도 화면이 붙지 않아 훅이 스스로 새로 열게 함(결정 20). 503 `too-many-streams`도 같음 |
| Vite 프록시와 `kubectl port-forward`를 거친 SSE | 모아 두지 않고 서버에 바로 붙은 것과 같은 간격으로 이벤트가 옴 |
| 열린 SSE가 있을 때 SIGTERM | `streams.closeAll()`이 응답을 끝내고, 응답 헤더 `Connection: close`로 소켓이 바로 닫혀 0.2초 만에 끝남 |
| 데모 앱의 `errors` 스위치 | SDK `exception`만 보내고 HTTP 응답은 그대로라 5xx/분이 늘지 않음. 5xx는 `slow`(DB 시간 제한 1000ms를 넘겨 `GET /orders/:id`가 500)로 확인함 |
| `block` 뒤 판단 | 풀린 직후 readiness가 같은 초에 다시 통과하면 `not-ready`를 거치지 않고 `stalled` → `ok` |
| 쿠버네티스 시각 문자열 | 처음 list로 받은 것은 `2026-11-14T06:00:59.000Z`, watch로 받은 것은 `2026-11-16T03:15:48Z`(T12의 `isoTime`). 둘 다 ISO 8601이라 그대로 둠 |

## API

| --- | --- | --- |

## 범위

### 포함

- 프로토콜: HTTP 본문 타입(`http.ts`)
- 서버: 저장소의 판단 변화 기록(인터페이스, 메모리 어댑터), `StatusMonitor`의 판단 변화 기록과 Pod의 Deployment, `AppStates`의 counter 증가량 60초, 목록·상세 항목 만들기(`views.ts`), 바뀐 것 계산(`feed.ts`), SSE(`stream.ts`), HTTP 경로와 오류 형식(`app.ts`), 종료 처리(`index.ts`)
- 웹: API 클라이언트 함수, `applyPodChanges`, `usePodStream`, 목록·상세 자리의 원본 표시
- 단위 테스트

### 제외

- 그래프용 지표 시계열, 상세의 실시간 event·지표, 쿠버네티스 이벤트 보관(T19)
- 목록·상세 화면 디자인(T18·T19), 서버가 웹 화면 파일을 내주는 것(T20)
- 지표 비교로 이상한 Pod 강조(T34). 목록 항목에 자리를 미리 만들지 않음
- 조치 API와 조치 기록(T21~T24), 인증(D4: 1차 범위는 없음)
- SDK·SDK–서버 프로토콜 변경

## 쓰는 법

설정은 늘지 않습니다. 서버를 띄우면 조회 API와 SSE가 함께 열립니다.

```bash
GLASSPOD_KUBE_CONTEXT=docker-desktop npm run dev:server
```

```bash
curl -s 'localhost:8080/api/pods?namespace=glasspod-demo'
```

```bash
curl -N 'localhost:8080/api/stream?namespace=glasspod-demo'
```

웹 화면은 `npm run dev:web` 뒤 `http://localhost:5173/`에서 실시간 목록을 봅니다.

## 로그 형식

```text
2026-11-16T09:00:00.000Z INFO  stream opened remote=::1 namespace=glasspod-demo streams=1
2026-11-16T09:05:00.000Z INFO  stream closed remote=::1 namespace=glasspod-demo streams=0 reason=client durationMs=300000
2026-11-16T09:06:00.000Z WARN  stream rejected remote=::1 reason=too-many-streams limit=20
2026-11-16T09:07:00.000Z WARN  stream closed remote=::1 streams=3 reason=slow durationMs=12000 bufferedBytes=1050000
```

- `namespace`는 거른 경우에만 붙습니다. 닫힘 이유는 `client`(브라우저가 끊음), `slow`, `shutdown`입니다.
